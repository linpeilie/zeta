# .workflow — 开发过程产物

[提示词库](../docs/prompts/README.md)里各流程的阶段产物落在这里。**这些文件入库，跟代码一起提交**，PR 评审时能看到完整思路，事后能追溯「当初为什么这么定」。

这不是 `docs/`。`docs/` 放长期有效的产品与架构文档，这里放**某一次任务的过程记录**。两者的区别是：`docs/` 描述系统现在是什么样，`.workflow/` 记录某次改动当时是怎么想的。

---

## 目录结构

```
.workflow/<流程类型>/<YYYY-MM-DD>-<任务简称>/<NN>-<阶段名>.md
```

举例：

```
.workflow/
├── feature/
│   └── 2026-08-07-模型目录分页/
│       ├── 01-需求分析.md
│       ├── 02-方案设计.md
│       ├── 03-任务拆解.md
│       ├── 04-实现记录.md
│       └── 05-验收报告.md
├── refactor/
│   └── 2026-08-07-plan-交接控制器/
│       ├── 01-动机与止损线.md
│       ├── 02-现状测绘.md
│       └── 03-安全网.md
├── perf/
├── protocol/
├── migration/
└── bugfix/
```

**类型目录用到了才建**，不要预先建一堆空文件夹占位。

任务简称用短横线连接的中文或英文，能一眼认出是哪件事就行。日期用任务**开始**的日期，中途不改。

## 落盘规则

**必须脱敏。** 这些文件会进 git 历史，比本地日志更难撤回：

- 不要粘贴 `~/.zeta/logs/` 的原始日志——摘要成「哪个 RPC 没回」这类结论
- 不要粘贴 prompt 正文、模型回复、工具输出、凭证、环境变量值
- 不要粘贴完整的用户项目路径，用 `<project>/lib/...` 代替
- 采样数据、计数、时间戳、方法名可以留

**写结论，不写过程。** 产物是给未来的人看的，不是聊天记录。一个阶段文件应该能在两分钟内读完并知道当时定了什么、为什么。

**不复制规则正文。** 引用门禁写 `G3`、引用文档写章节名，不要把 `AGENTS.md` 或 `engineering_standards.md` 的内容抄进来——那会变成第 N 份会漂移的副本。

## 生命周期

1. **进行中** —— 阶段文件随任务推进逐个增加，跟代码改动一起提交。
2. **合并后** —— 文件留在仓库作为决策记录，不删。纯文本很小，不会成为负担。
3. **毕业** —— 如果某份设计是长期有效的（比如新 Provider 的适配方案、新的架构约定），把它整理进 `docs/architecture/` 或 `docs/protocols/`，并在原文件留一行指针。**别在两个地方各留一份全文。**
4. **作废** —— 任务中途放弃时，在该任务的最后一个阶段文件末尾加一段「为什么停」，然后就放着。**放弃的原因往往比成功的方案更有价值**，下次有人想做同一件事能少踩一次坑。
