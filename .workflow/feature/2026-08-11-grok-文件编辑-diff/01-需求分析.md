# 01 · 需求分析

任务：Grok 文件编辑适配 diff 样式

开始日期：2026-08-11

状态：范围已确认；尚未进入方案设计或代码实现

## 结论先行

已确认范围是：**只在 Agent 时间线中，用一套新样式只读展示 Grok 已上报的文件编辑差异；覆盖 live、恢复历史和 replay；支持局部编辑、新建文件和整文件覆写；完整呈现 Provider 上报的 old/new 内容。**

该范围不包含审批卡，也不读取工作区文件补算差异，因此与产品范围不冲突，当前判定为 **M 档**。新样式的具体布局与交互属于下一阶段方案设计，本阶段只冻结必须可观察的内容和行为。

## 1. 问题陈述

### 用户实际要解决的问题

Grok 通过 ACP 工具调用上报文件编辑时，协议可在 `content` 中携带结构化 diff。当前 Zeta 会识别“这是一次 edit”并显示文件编辑组，但 diff block 只被压成类似 `diff: <文件>` 的普通文本；现有文件编辑组又只从另一种输出形状读取差异详情。因此用户通常只能知道改了哪个文件，看不到具体删改行、增删统计，也无法在连续时间线里审计这次编辑。

Zeta 已有按文件分组、增删行统计和 diff 高亮的基础能力，但本需求明确选择一套新样式。无论视觉形态如何，当前首要缺口仍是 Grok/ACP 的结构化差异没有进入 Provider 中立的展示链路。

### 现在怎么绕过去

仓库没有用户调研、埋点或支持工单可以证明某一种固定习惯。根据当前可见能力，现实可行但需要离开主流程的绕行是：先在 Zeta 里确认被改文件，再到外部编辑器或版本控制工具查看工作区 diff；也可能要求 Agent 在回复正文中复述改动，但这不是产品保证，也不能替代可审计的工具记录。

## 2. 可观察的验收标准

以下标准已经合并本轮六项选择；新样式的视觉规格不得削弱这些可观察行为。

| ID | 做 X | 会看到 Y |
|---|---|---|
| AC-1 | 在 Grok live 会话中触发一次带有效结构化 diff 的局部文件编辑 | 当前回合出现新样式的文件编辑展示，包含目标文件和准确的 `+N / -M` 统计，不再只显示 `diff: <文件>` 这类占位文字 |
| AC-2 | 查看该文件编辑的差异详情 | 会看到 Provider 上报的完整 old/new 内容，删除与新增内容可明确区分；不会读取本地文件补齐，也不会静默截掉尾部内容 |
| AC-3 | 同一个 Grok 工具调用依次上报开始、进度、损坏更新和有效完成更新 | 时间线始终只保留一个对应编辑项；损坏更新不伪造或清空已确认内容，有效完成信息在原位生效，界面不中断 |
| AC-4 | Grok 在一个回合中执行局部编辑、新建文件、整文件覆写或一次修改多个文件 | 各文件能被明确区分；新建显示为纯新增，整文件覆写显示完整前后差异，多文件内容不会串项；delete/move/rename 不被误归入本范围 |
| AC-5 | 关闭后重新打开该 Grok thread，或通过 history/replay 恢复同一回合 | 会看到与 live 逐位置一致的文件顺序、完整差异、增删统计和终态，不出现缺项或重复项 |

## 3. 明确不做

| 非目标 | 边界说明 |
|---|---|
| 内置编辑器或本地补算 diff | 不读取当前工作区文件来推导前后内容，不新增编辑器内 diff |
| 编辑闭环 | 不新增编辑、应用、拒绝、保存、回滚或合并文件变更的操作 |
| 权限语义改造 | 只处理执行中/完成后的时间线，不修改执行前审批卡，不改变或绕过审批决策 |
| 重做 Codex 或 Provider 专属 UI | 新样式不要求同步重设计 Codex diff，但自身必须消费中立模型；不让 Widget 读取 Grok/xAI raw 字段或按 Provider 名称分支 |
| 扩展其他文件操作 | 局部编辑、新建文件和整文件覆写在范围内；delete、move、rename 不在本次范围 |
| 仅 hunk 或内容截断 | 不以只显示局部 hunk、固定行数或固定字符数替代 Provider 上报的完整 old/new 内容 |
| 协议或 Provider 扩张 | 不升级 ACP 大版本，不新增 Provider、Bundle 端口或 capability |
| 敏感内容落盘 | 不把 old/new 文件正文、完整 diff、raw payload 写入 Zeta 配置、缓存、索引或日志 |

## 4. 已拍板范围

| # | 事项 | 选择 | 冻结后的边界 |
|---|---|---|---|
| 1 | 展示位置 | A：时间线 | 只做执行中/完成后的时间线；审批卡明确排除 |
| 2 | 目标视觉 | C：新样式 | 下一阶段单独定义布局和交互；不能回退成当前占位文本或削弱第 2 节验收标准 |
| 3 | diff 事实来源 | A：仅 Grok/ACP 上报内容 | 不读取工作区文件，不做本地补算 |
| 4 | 生命周期覆盖 | B：live、恢复历史和 replay 一致 | 三条路径必须使用同一规范化语义，并补逐位置回归 |
| 5 | 文件编辑动作 | B：局部编辑、新建、整文件覆写 | delete、move、rename 明确排除 |
| 6 | 内容完整度 | A：完整 old/new | 完整内容必须可查看，不用仅 hunk 或固定上限代替 |

本轮产品范围没有剩余歧义。第 2 项选择了“新样式”，因此下一阶段仍需在 `02-方案设计.md` 中冻结视觉结构、展开方式和大内容性能策略；这些属于实现方案，不在本文件中提前决定。

### 实施前置证据

必须取得一份基于项目基线 Grok CLI `0.2.119` 的脱敏文件编辑通知序列，确认真实 `tool_call` / `tool_call_update` 的 diff、重复更新和终态形状。当前仓库的 Grok fixture 只覆盖较早版本的其他工具场景；不能只根据 ACP 标准推断真实 CLI 已按同一形状发送。

## 5. 门禁预判与复杂度

| 门禁 | 预判 | 判断依据 |
|---|---|---|
| G1 | 条件命中，重点边界 | `acp_*` 属共享适配层；若修改共享 codec/decoder，必须只表达标准 ACP 的 Provider 中立语义且任务升 L。Grok 私有兼容不得进入共享层、Store 或 UI |
| G2 | 命中 | 同一工具调用的身份、更新去重与终态关联应由 Grok adapter/reducer 决定，TimelineStore/UI 不得根据最后一条或 raw payload 猜测 |
| G3 | 命中状态隔离验证 | live/history/replay 必须使用独立 reducer/context；若改变 reducer，仍须保持纯同步且不新增副作用 |
| G4 | 预计不命中 | 本次不新增能力入口、Bundle 端口或 capability；如果实施发现必须新增端口，应停下并升 L |
| G5 | 明确不命中 | 已选择仅做时间线，不修改执行前审批卡；diff 展示仍不得预授权、代替或合并权限决策 |
| G6 | 命中 | ACP `oldText/newText` 等协议字段只能在 data 层解释；presentation 只能消费中立模型 |
| G7 | 预计不命中 | 不新增对 `~/.grok` 或其他 CLI 私有数据的读取、迁移或改写 |
| G8 | 命中 | diff 含用户文件正文，只允许在内存中用于展示；不得进入日志、缓存或持久化，fixture 必须脱敏 |
| G9 | 命中 | 已选择新样式；必须使用主题 token、响应式布局和稳定重绘边界，不得做 Grok 名称分支 |

**当前档位：M。** 已确认范围预计横跨 Grok data 适配、中立展示数据、presentation 新样式以及 live/history/replay 测试；同时命中 G2、G3、G6、G8、G9，不符合 S 档条件。当前没有确认要修改 AgentEvent、G1 共享文件、Provider 端口、持久化或审批语义，因此尚未触发 L 档硬条件。

出现以下任一情况立即改判 **L**：新增/改变 AgentEvent 语义；修改 G1 共享适配层；加入审批卡范围；新增 Provider 端口；改持久化；或做跨 feature 结构调整。

## 6. 产品需求对照

### 一致部分

- `docs/product/product_requirements.md` §3 要求用户能在连续时间线中理解工具执行过程。
- §4、§6 和 §8 要求展示工具调用状态、在时间线回看上下文，并让工具调用清晰可读。
- §5、§7 要求 Provider 协议差异在 data 层归一化，UI 不绑定 xAI/Grok 原始协议。

### 与“暂不包含”的关系

按已确认范围，**没有冲突**：展示的是 Provider 已经上报的工具调用证据，位置在 Agent 时间线，且为只读；它不是内置代码编辑器，也不要求 Zeta 读取文件、计算工作区差异或保存变更。

本需求继续明确排除本地文件补算，以及编辑、应用、保存、回滚等能力；这些能力会直接冲突 §5 的“内置代码编辑器”与“文件内容读取、编辑器内 diff 或保存流程”，如未来需要必须另立产品决策。
