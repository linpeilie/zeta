# 01 · 需求分析

任务：三 Provider 文件变更证据通用化（由 Grok 文件编辑展示缺口触发）

开始日期：2026-08-11

重新设计日期：2026-08-12

状态：已按当前 Codex、Grok、Claude Code 真实数据重新确认范围；代码实现等待共享层改动批准

## 结论先行

当前目标不再是“让所有 Provider 都显示同一种 diff”，而是：

> **每个 Provider 只把自己确实拿到的一手文件变更证据，转换成同一套中立契约；UI 按证据类型展示。没有证据时只展示原本能确认的工具或命令，绝不从命令、raw payload 或当前工作区反推文件改动。**

三种已验证的证据形态分别是：

- Grok `diff` 与 Claude Code `Edit`：Provider 给出“替换前片段 + 替换后片段”；
- Claude Code `Write`：Provider 给出“准备写入的完整内容”；
- Codex 结构化 `fileChange` / `turn/diff/updated`：协议定义提供 unified patch。

当前本机 Codex 的真实成功编辑只产生 `commandExecution`，没有产生结构化
`fileChange` 或 `turn/diff/updated`。因此这一真实路径的正确表现是继续显示命令卡，
**不显示虚构的文件变更卡**。仓库 schema 中存在的结构化 Codex 路径仍要兼容，但不能
再把“schema 能表达”写成“当前运行时一定会产生”。

本次同时适配三个活跃 Provider：Codex、Grok、Claude Code。CLI 版本只作为实证来源
标签，不再作为进入实现的精确版本硬门；仓库 pin/schema 仍是 Codex 静态兼容基线。

## 1. 当前问题

### 1.1 用户能看到的症状

- Grok 已上报路径、`oldText`、`newText`，但共享 ACP 文本 codec 只留下
  `diff: <path>`，用户看不到实际替换内容。
- Claude Code 的 `Edit` / `Write` 输入已经带有足够的文件证据，但当前 mapper 只把它们
  保存在 `rawInput`，时间线没有中立文件变更模型可消费。
- Codex 的旧展示由 presentation 直接解析 `AgentTurnDiffEvent.diff`，或读取
  `toolCall.rawOutput['changes'][...]['unified_diff']`。这把协议/raw 形状泄漏到了 UI。
- 同一个工具的开始、进度和完成事件可能省略先前字段。如果靠共享 Store 猜测并补齐，
  Provider 身份和增量语义就会污染共享层；如果完全 latest-wins，又可能把证据冲掉。
- 最危险的误判是把 Codex `commandExecution` 中的命令字符串或
  `commandActions.type == unknown` 当成可靠文件 diff。命令成功只能证明命令执行成功，
  不能证明具体改了哪些行。

### 1.2 用户真正需要的结果

用户在同一条可审计时间线中，应能区分：

1. Provider 给出了可核验的替换片段、写入内容或 patch；
2. Provider 只给出了路径/动作摘要；
3. Provider 只执行了命令，没有提供结构化文件证据。

这三种情况必须显式不同，不能为了视觉统一而伪造完整文件、伪造 diff，或悄悄读取
当前工作区补算。

## 2. 2026-08-12 当前环境实证

版本限制已由用户明确跳过。下表中的版本用于说明证据来源，不作为实现硬门。

| Provider | 当前实测版本 | 真实成功编辑时观察到的结构 | 本次可承诺的展示 |
|---|---:|---|---|
| Grok | `1.0.0` | 同一 tool 先后上报 `kind: edit`，以及 `content[type=diff] {path, oldText, newText}`；完成更新再次携带同一 diff | 路径 + Provider 给出的替换前/后文本 |
| Claude Code | `2.1.227` | `Edit` 的 `tool_use.input` 含 `file_path/old_string/new_string/replace_all`；成功 `tool_result` 只有普通文本，没有结构化 diff | 路径 + 请求替换的前/后片段；状态说明是否成功 |
| Claude Code | `2.1.227` | `Write` 的 `tool_use.input` 含 `file_path/content`；成功 `tool_result` 只有普通文本 | 路径 + 请求写入的内容；状态说明是否成功 |
| Codex | `0.144.1` | 文件确实修改成功，但只观察到 `commandExecution`；`commandActions.type` 为 `unknown`；`fileChange`、`patchUpdated`、`turn/diff/updated` 均为 0 | 保留命令卡；不生成文件变更详情 |
| Codex schema | 仓库 pin `0.144.5`；本机匹配 schema `0.144.1` | schema 定义 `fileChange.changes[] {path, kind, diff}`、`patchUpdated` 与 turn 聚合 diff | 作为结构化兼容路径；必须与“当前实测命令路径”分开标注和测试 |

所有实测都在临时 workspace 与合成文件中完成。记录只保留方法、类型、字段名、状态和
计数；未保留 prompt、回复、命令、真实路径、文件正文、会话/回合/tool id、凭证或
stderr 原文，临时目录已清理。

## 3. 可观察的验收标准

| ID | 做 X | 会看到 Y |
|---|---|---|
| AC-1 | Grok live/history/replay 中执行一次带 ACP `diff` content 的 Edit | 同一 tool 原位更新；显示路径和“替换片段”对比，不再显示 `diff: <path>` 占位，不把片段标成完整文件 |
| AC-2 | Claude Code 分别成功/失败执行 `Edit`，并成功执行 `Write` | `Edit` 显示 old/new 片段与 `replace_all` 语义，`Write` 显示写入内容；终态只更新状态，不冲掉 tool_use 已给的证据；失败项明确是“尝试修改失败”而不是已应用 |
| AC-3 | 当前 Codex 通过 `commandExecution` 成功修改合成文件，且没有结构化 fileChange/turn diff | 只显示正常命令卡；不从命令字符串、审批参数、`commandActions`、工作区结果或 raw 猜文件卡/路径/diff |
| AC-4 | Codex 收到仓库 schema 定义的 `fileChange` / `patchUpdated` / `turn/diff/updated` fixture | 结构化 tool fileChange 显示路径、动作和 unified patch；turn 聚合只作为 tool 证据缺失时的 typed fallback；两者同回合出现时由 Codex adapter 决定唯一可见真源，Store/UI 不按路径去重 |
| AC-5 | 向三个 Provider 送入“有证据更新 → status/text-only 更新 → 终态” | 每个 Provider adapter 在进入共享 pipeline 前输出完整累计 snapshot；coalescing latest-wins 后证据仍在，Store 只按 tool id/turn entry id 机械替换 |
| AC-6 | 用各 Provider 合法的 history/replay 路径重建有 tool 证据的回合 | Grok、Claude Code，以及 Codex 结构化 fileChange 的 owner、顺序、动作、证据变体与终态逐位一致；Codex live-only turn aggregate 明确标为 fallback，不冒充可恢复历史事实 |
| AC-7 | 展开长替换片段、长写入内容和长 unified patch，并调整窗口宽度 | 宽窗/窄窗均可读，末行可达，长路径省略，滚动/展开状态不串项；resize 不重复解析内容，也不恢复 post-frame 测高反馈环 |
| AC-8 | 扫描 production presentation、Store 和日志 | presentation 不读取文件变更 raw/wire key、不按 Provider 分支；Store 不解析路径/命令/patch；日志、缓存、通知和持久化不含文件正文或 patch |

## 4. 证据强度与文案边界

| 中立状态 | 含义 | UI 允许说什么 | UI 禁止说什么 |
|---|---|---|---|
| `textReplacement` | Provider 给出旧片段与新片段 | “替换片段”“替换前/后” | “完整文件修改前/后”，除非未来协议另有明确保证 |
| `writtenContent` | Provider 给出 Write 请求中的内容 | “写入内容”或“准备写入” | 未成功前说“文件已写入”；把缺失旧内容解释为新建文件 |
| `unifiedPatch` | Provider 给出 unified patch | “补丁”“本次改动” | 从 patch 反推未提供的完整文件快照 |
| `evidence == null` | 只有路径/动作等结构化摘要 | “修改了/尝试修改该路径”（结合终态） | 编造具体行、before/after 或 patch |
| 无 file-change snapshot | 没有结构化文件证据，例如当前 Codex command-only 路径 | 保留原工具/命令卡 | 把命令执行等同于文件编辑证据 |

空字符串是 Provider 给出的合法内容值，不等于“文件不存在”。文件新建/删除/移动只能由
Provider 的结构化动作字段决定，不能根据 old/new 是否为空猜测。

## 5. 明确不做

| 非目标 | 边界说明 |
|---|---|
| 本地补算 diff | 不读取当前工作区文件，不运行 Git diff，不应用/逆应用 patch 反推 before/after |
| 命令语义分析 | 不解析 shell/PowerShell/脚本内容来猜路径、动作或结果 |
| 编辑闭环 | 不新增应用、拒绝、保存、回滚、合并或手工编辑功能 |
| 权限语义改造 | 不修改 permission/question/plan approval/plan handoff，不预授权任何文件或命令 |
| 强制证据互转 | 不把 old/new 片段有损转成 patch，也不把 patch 伪造成完整 before/after |
| 暗示全 Provider 全覆盖 | Claude `NotebookEdit`/`MultiEdit` 和未知工具本轮只做摘要，除非先取得对应真实 fixture；当前 Codex command-only 路径明确无 diff |
| Provider port/capability 扩张 | 不新增或修改 `AgentProviderBundle` 端口，不新增 capability；这是已有工具事件的 typed payload 扩展 |
| 敏感内容落盘 | 文件证据只在当前内存时间线存在，不进入 Zeta 配置、状态、缓存、日志、通知或用量索引 |
| 精确 CLI 版本门 | 不要求安装指定 Codex/Grok/Claude CLI 才能开始；fixture 与记录必须如实携带来源版本，不得冒充别的版本 |

## 6. 已拍板的产品与架构边界

| 事项 | 决定 |
|---|---|
| 通用化对象 | 三个活跃 Provider：Codex、Grok、Claude Code |
| 统一内容 | owner、路径、动作、顺序、状态、证据类型与证据正文；不统一 Provider 没给出的事实 |
| 主要 owner | Grok/Claude/结构化 Codex fileChange 使用 tool owner；Codex turn aggregate 仅作 tool 证据缺失时的 turn fallback |
| Provider 责任 | 在自有 mapper/tracker 内决定 identity、动作、change id、累计 snapshot、终态和 fallback 抑制 |
| 共享层责任 | domain 保存中立模型；Store 只按现有 tool/turn id 机械携带；coalescing 仍是 typed latest-wins，不读 raw |
| UI 责任 | 只按 evidence 变体选择 renderer；不解析 Provider 字段、不按 Provider 名称分支、不访问工作区补全 |
| Codex 当前行为 | command-only 就是 command-only；不为了让三列都“有 diff”而制造假能力 |
| Codex turn aggregate | 暂不按旧方案直接退役；先改为 typed fallback，并用 provider-local 规则避免与 tool snapshot 双显 |
| 历史一致性 | 对可恢复的 tool evidence 要求 live/history/replay canonical 一致；不可恢复的 turn fallback 显式降级，不计作历史完整通过 |

## 7. 门禁、规模与当前停线

本需求最终仍为 **L 档**，但比旧方案减少了不成立的 Codex 假设，也不再要求修改
Provider 端口或共享 coalescing 策略。

| 门禁 | 判定 | 处理方式 |
|---|---|---|
| G1 | 命中且当前停线 | `AgentConversationTimelineStore` 必须机械携带新增 typed snapshot；不允许 Provider 分支/raw 解析。按用户要求，开始生产代码前必须取得明确批准 |
| G2 | 命中 | 三个 Provider 各自在 data mapper/tracker 输出完整累计 snapshot；Store 不保存 provider-local last-valid 规则 |
| G3 | 命中 | live/history/replay 各自创建独立 tracker/identity/reducer；状态在 turn/runtime 终止时清理 |
| G4 | 不扩能力面 | 无证据时诚实降级，不用空 diff 伪造支持 |
| G5 | 不命中 | 不改四种审批语义 |
| G6 | 命中 | ACP/Claude/Codex wire key 只在 data；domain 与 UI 只见中立 evidence |
| G7 | 命中 | evidence 不落盘；fixture 只用合成 sentinel；日志前先完成正文抑制 |
| G8 | 命中 | 新组件走 Graphite token、稳定 key、有界列表与响应式布局 |

新方案还需要扩展 `AgentToolCall` 中立模型，并把 turn diff 迁移为 typed payload；这会触及
共享 TimelineStore，但**不需要修改任何 Provider port**。依照用户的硬停线规则，本文档
重设可以完成，生产代码从 `03-任务拆解.md` 的步骤 1 起保持阻塞，等待用户明确批准这项
共享层机械透传改动。停线原因已写入 `04-实现记录.md`。
