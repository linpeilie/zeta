# 01 · 需求分析

任务：对话流文件编辑 diff 通用化（由 Grok 适配缺口触发）

开始日期：2026-08-11

状态：范围已按通用化方向重新确认；尚未开始代码实现

## 结论先行

需求已从“为 Grok 单独适配 diff 样式”收敛为：**Codex 和 Grok 各自在 data adapter 中解析自己的文件变更格式，统一输出 Provider 中立的文件变更契约；时间线只消费该契约，不再解析 ACP、Codex wire 字段或 `rawInput/rawOutput/raw`。**

“统一”指同一容器、身份、动作、顺序和渲染入口，不强行把不同强度的证据伪造成同一文本形态：

- Grok ACP 的 `oldText/newText` 完整保留为 before/after 证据；
- Codex 当前的 `fileChange.changes[].diff` 完整保留为 unified patch 证据；
- Provider 只给路径/动作时，统一输出 `evidence == null` 的摘要状态，不猜测详情。

新样式用于 before/after 证据；Codex unified patch 保持当前可见信息和高亮行为，但详情的唯一时间线真源收口到可合规恢复的 tool-scoped `fileChange`。`turn/diff/updated` 作为不可恢复的派生聚合通知，最终只在 Codex data 层做白名单诊断，不再产生第二份时间线详情。最终状态不保留 presentation raw fallback。

本需求明确修改中立 domain / AgentEvent payload、G1 共享 Store 及两个 Provider adapter，因此最终判定为 **L 档**。

## 1. 问题陈述

### 用户实际要解决的问题

当前对话流的文件变更展示没有统一语义入口：

- Grok 按 ACP 上报 `type: diff` 时，共享 codec 只留下 `diff: <path>` 占位文本，`oldText/newText` 没有进入 domain，用户通常只能知道改了哪个文件。
- Codex 可以显示 unified diff，但目前由 presentation 直接拆 `AgentTurnDiffEvent.diff` 或读 `toolCall.rawOutput['changes'][...]['unified_diff']`。这是 Provider/native shape 上浮，而不是中立契约。
- 因此相同的“Agent 修改文件”语义会随 Provider 切换而改变审计能力；新 Provider 也容易被迫在 UI 再加一条 raw 解析分支。

用户要的不是“让所有 Provider 长得一模一样”，而是：在同一可审计时间线里，稳定地看到 Provider 实际上报的文件、动作、顺序、统计和详情，且不会因换 Provider 就失去信息或出现重复项。

### 现在怎么绕过去

仓库没有调研、埋点或工单可以证明固定的用户习惯。当前可合理推断的绕行是：

- Grok 用户先在 Zeta 看文件名，再去外部编辑器或版本控制查工作区 diff；
- 或要求 Agent 在回复正文里复述改动，但这不是可审计的工具证据；
- Codex 用户虽能看到旧 diff 卡，但这条 Provider 特例不能保证 Grok 或后续 Provider 有等价能力。

## 2. 可观察的验收标准

| ID | 做 X | 会看到 Y |
|---|---|---|
| AC-1 | 分别在 Codex 和 Grok live 回合触发一次带可恢复 tool 证据的文件变更 | 两者都在相同的“文件变更组 → 单文件”信息层级中显示路径、动作、统计和详情；Grok 不再只显示 `diff: <path>`，Codex 不会因迁移丢掉 fileChange diff 信息，也不同时出现 tool 和 turn 两份同源详情 |
| AC-2 | 展开两种 Provider 的文件变更详情并滚动到内容末尾 | Grok 显示其上报的完整 before/after；Codex 显示其上报的完整 unified patch/hunks。两者都不截断、不读工作区补全，也不伪造 Codex 未上报的未变更行或完整文件快照 |
| AC-3 | 向 Grok 送入“开始 → 有效 diff → 省略/status-only → 损坏更新 → 有效终态”，并向 Codex 送入同 itemId 的 full `fileChange` → status/text-only → 有效终态及 `turn/diff/updated` | 同一 Provider source identity 的 tool 项在原位更新且只留一项；两边 status/text-only 或损坏/省略更新都不清空 last-valid，终态不丢详情；Codex aggregate 不生成另一条时间线项，Store/UI 不按路径猜测去重 |
| AC-4 | 让两种 Provider 上报其协议能表达的新建、修改/整文件覆写或多文件变更 | 各文件的身份、Provider 顺序、动作、统计和证据不串项；Provider 只给路径/动作时只显示摘要；delete/move/rename/unknown 保留真实分类或降级，不被伪装成 modified before/after |
| AC-5 | 通过每个 Provider 合规的 history/replay/恢复路径重建同一回合 | 会看到与 live 的中立容器签名逐位一致的 scope、owner identity、文件顺序、动作、证据形态、统计和工具终态，无缺项或重复项；仅有 CLI 私有 session 文件可用时明确阻塞，不算验收通过 |

Codex `fileChange.changes[]` 是 live 与合法 `thread/read` 都能提供的稳定真源，因此本方案将 tool-scoped `fileChange` 定为唯一时间线详情。`turn/diff/updated` 不可通过 `thread/read` 恢复，且是已有 fileChange 的派生聚合；它最终不再产生 `AgentTurnDiffEvent`/时间线条目，只由 Codex data adapter 记录无正文的白名单计数诊断。

## 3. 明确不做

| 非目标 | 边界说明 |
|---|---|
| 内置编辑器或本地补算 diff | 不读取当前工作区文件，不应用 patch 反推 before/after，不新增编辑器内 diff |
| 编辑闭环 | 不新增编辑、应用、拒绝、保存、回滚或合并文件变更的操作 |
| 权限语义改造 | 只处理执行中/完成后的时间线，不修改文件审批卡、pending registry 或 permission response，不预授权 |
| 有损强制统一 | 不把 Codex unified patch 伪造成完整 before/after，也不把 Grok 完整 before/after 丢成客户端生成的最小 patch |
| Codex diff 组件视觉重设计 | 将 Codex 数据链迁移到中立 target，但不重做 unified diff 的高亮、预览、展开和信息密度；详情真源从不可恢复的 turn aggregate 收口到 tool 是明确的去重/恢复契约，不是 UI 猜测 |
| 保留 Codex 回合聚合卡 | `turn/diff/updated` 不可合规恢复且与 tool fileChange 同源；本次在 tool target 可见链齐备后退役该卡，不把它作为 live-only 例外 |
| 新增 delete/move/rename 产品能力 | target 宽容保留现有 Provider 已给的动作真值，但本次不为 Grok 新增这些操作的详情样式或交互 |
| 协议或 Provider 扩张 | 不升级 ACP/Codex 协议版本，不新增 Provider、Bundle port 或 capability；只对仓库已锁定的当前格式做等价归一 |
| 全面清理 Agent raw | 本次必须删除“文件变更展示”对 raw 的依赖，但不顺手重构其他工具卡仍可能使用的 `AgentToolCall.raw*` |
| 敏感内容落盘 | 不把 before/after、unified patch、raw payload 或完整路径写入 Zeta 配置、状态、缓存、索引、日志或系统通知 |

## 4. 已拍板边界

| 事项 | 决定 |
|---|---|
| 通用化目标 | 所有活跃 Provider 的文件变更都由自有 data adapter 转为同一 domain target；本任务同时迁移 Codex 与 Grok |
| 证据模型 | 中立 target 有 before/after 与 unified patch 两种 typed evidence；无详情摘要是 `evidence == null` 的展示状态，不是第三种 evidence；都不表示 Provider 身份 |
| 事实来源 | 仅使用 Provider 已上报数据；Grok 解析 ACP content，Codex 将锁定 app-server `fileChange` 归一为 target，并把 turn diff 仅作为无正文诊断消费 |
| 渲染 | 公用文件变更组/文件行只按 evidence 变体选详情 renderer；不按 Provider 分支 |
| Codex 叙事真源 | tool-scoped `fileChange` 是可恢复的唯一时间线详情；turn aggregate 退役为 data 层无正文诊断，Store/UI 不去重 |
| 完整度 | 完整保留 Provider 真实上报的证据，不截断、不有损互转、不用工作区补齐 |
| 生命周期 | live、history 和 replay 必须归一到同一 target，并使用独立 mapper/reducer 状态 |
| 迁移策略 | 可临时 target-first + raw fallback 以保持每个提交可回滚；但双 Provider target 链路齐备后，本任务内必须删除 presentation raw fallback |

本轮已按上述决定收口，无剩余产品歧义。

## 5. 实施前置证据与阻塞

1. 取得 Grok CLI `0.2.119` 的真实脱敏文件编辑序列，确认 ACP list/replace、字段省略、终态、新建/修改/多文件形状。
2. 以仓库 pin 的 Codex app-server `0.144.5` schema 和脱敏 fixture 固定 `fileChange.changes[] {path, kind, diff}`、`item/fileChange/patchUpdated`、`turn/diff/updated` 和 `thread/read` 历史形状，并确认 tool snapshot 是可合规恢复的 full 详情真源。如真实证据不成立，本方案阻塞并回修 01/02，不使用 live-only turn aggregate 补洞。当前本机 CLI 与文档技能缓存对应 `0.144.1`，不能代替仓库 `0.144.5` 验收；也不自动升级到当前更高 release。
3. 更新 G1 Issue 的评审范围：对象从 before/after-only 扩为双 evidence 中立 target、Store 机械透传，以及最后删除 `AgentEventCoalescingPolicy` 中已无 producer 的 turn diff case；必须在真实证据后获得最终明确批准，且不得改变其余事件的 key/barrier/latest-wins 语义。
4. 先修复 `AgentIgnoredMessageLogger` 串行化 ignored raw payload 的 G8 问题；在此前不让 Grok before/after 或 Codex patch 进入新 live target 链。
5. 为两个 Provider 建立 G7 合法恢复路径。当前 Grok 扫描 `~/.grok/sessions`，Codex 也会优先读本地 session JSONL；这些都不能作为 AC-5 合规签收证据。注入 fixture/canonical 可先验证算法，但不能代替真实 reopen。

## 6. 门禁与复杂度

| 门禁 | 判定 | 满足方式 |
|---|---|---|
| G1 | 命中 | `acp_*` 只解标准 ACP，Grok 兼容留在 Grok mapper；TimelineStore 只机械合并中立 snapshot；最终只删除 CoalescingPolicy 中无 producer 的 turn diff case，其余机制不变；共享守卫不出现 Provider 分支。G1 Issue 必须覆盖这些共享改动并重新批准 |
| G2 | 命中 | Codex/Grok 各自决定 tool scope、source identity、稳定 change id/revision、顺序、动作、partial/full snapshot 与终态；Codex adapter 明确不将 turn aggregate 映射为时间线事件；Store/UI 不根据 path/raw/最后一条猜测 |
| G3 | 命中 | 合并状态保持纯同步；live/history/replay 使用各自独立 mapper/reducer/context，不共享 seen/snapshot/generation |
| G4 | 不改能力面 | 不新增 port/capability；Provider 没有详情证据时显示 typed summary，不伪造静默成功 |
| G5 | 明确不命中 | 时间线 diff 不是审批，不修改 permission/plan/question 语义，不预授权 |
| G6 | 命中 | ACP `oldText/newText`、Codex `changes/diff/kind/move_path`、`unified_diff` 等 wire key 只在 data 层；domain 只有中立 change/evidence；presentation 最终不读 raw |
| G7 | 命中且阻塞 | 不新增或谅解 CLI 私有目录读取；只有 Provider 合法协议路径可签 AC-5，未解决前功能不得宣称全验收 |
| G8 | 命中且前置 | 两种证据只在内存；ignored/transport/文件日志、fixture、系统通知都用白名单与脱敏 sentinel 测试固定 |
| G9 | 命中 | 通用文件卡按 evidence 渲染，使用 Graphite token、稳定 key、有界虚拟行、`RepaintBoundary` 和响应式布局；补 Windows Profile |

**最终档位：L。** 不再是“如果改共享层才升 L”；新决定已确定会扩展 `AgentToolCallEvent` payload、退役 `AgentTurnDiffEvent`、修改 G1 Store、两个 Provider adapter、history/replay canonical 和时间线热路径，必须完整走 01—05。

## 7. 产品需求对照

新范围与 `docs/product/product_requirements.md` 不冲突，而且更直接落实：

- §3/§4/§8 的“在连续时间线理解工具执行、清晰回看”；
- §5/§7 的“Provider 差异在 data 层归一，UI 不绑定 Codex/xAI 原始协议”。

这里的“展示文件内容证据”是被动消费 Provider 已上报 payload，不是 PRD “明确不做”里的主动文件系统读取、编辑器内 diff 或保存流程。本需求继续排除本地补算、编辑/应用/保存/回滚和权限改造，因此没有越过产品边界。
