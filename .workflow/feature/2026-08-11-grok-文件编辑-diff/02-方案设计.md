# 02 · 方案设计

任务：三 Provider 文件变更证据通用化（由 Grok 文件编辑展示缺口触发）

日期：2026-08-12

状态：已按当前真实数据重新设计；代码实现等待 G1 共享层改动批准

最终档位：**L**

## 结论先行

采用“**中立文件变更 snapshot + 证据变体 + 无证据诚实降级**”方案：

1. `AgentToolCall` 新增可选的 `AgentFileChangeSnapshot`；
2. Grok、Claude Code、Codex 各自在自有 data mapper/tracker 中把 wire 数据变成完整、
   累计、带稳定 owner/change identity 的 snapshot；
3. evidence 只保留 Provider 实际给出的形态：替换片段、写入内容、unified patch；
4. 当前 Codex 只有 `commandExecution` 时不生成 snapshot，继续显示命令卡；
5. Codex `turn/diff/updated` 不再直接把字符串交给 UI，也不再假定必须退役；它迁移为
   typed turn fallback，仅在同 turn 没有 tool-scoped fileChange 时可见；
6. Store 只按既有 tool id / turn entry id 机械替换，presentation 只按 evidence 变体渲染；
7. 不新增 Provider port/capability，不读取工作区补算，不解析命令猜 diff，不把正文落盘。

这套方案统一的是“证据容器和审计语义”，不是强迫三个 Provider 产生同一种数据。

## 1. 为什么旧方案必须推倒重来

旧方案把 Codex tool-scoped `fileChange` 视为当前编辑路径必然存在、可由
`thread/read` 完整恢复的唯一真源，并据此计划直接退役 `turn/diff/updated`。当前
Codex `0.144.1` 的真实成功编辑推翻了这个前提：

- 文件实际改动成功；
- 只出现 `commandExecution`；
- `commandActions.type` 为 `unknown`；
- `item/started(fileChange)`、`item/fileChange/patchUpdated`、
  `item/completed(fileChange)`、`turn/diff/updated` 都没有出现。

schema 能表达 `fileChange`，不代表当前模型/工具路径一定使用它。若继续旧方案，只能在
以下错误做法中选一个：

- 从命令字符串或审批参数猜文件改动；
- 把仓库 schema 合成 fixture 冒充当前真实行为；
- 删除 turn aggregate 后假定 tool item 总会补上详情。

三者都不符合 G1/G2/G6，也不符合用户要求。因此新方案把 Codex 分成两个明确路径：

```text
当前实际 commandExecution 路径
  → 普通命令卡
  → 不产生文件变更证据

协议结构化 fileChange / turn diff 路径
  → Codex data mapper 解析
  → 中立文件变更 snapshot
  → typed 文件变更卡
```

## 2. 当前代码与真实数据对照

### 2.1 Grok

当前链路：

```text
session/update
  → AcpSessionUpdateDecoder
  → AcpToolCallUpdate(content: Object?)
  → GrokSessionUpdateMapper
  → AcpContentCodec.toolContentText
  → AgentToolCall(rawInput/rawOutput/raw)
  → TimelineStore
  → presentation raw fallback
```

真实 Grok `1.0.0` 序列：

```text
tool_call(rawInput keys: file_path/old_string/new_string)
  → tool_call_update(kind: edit,
      content: [{type: diff, path, oldText, newText}])
  → tool_call_update(status: completed,
      content: [{type: diff, path, oldText, newText}])
  → turn_completed(end_turn)
```

断点不是 Grok 没给数据，而是 `AcpContentCodec.toolContentText` 把 diff block 压成了
`diff: <path>`。新方案不要求共享 ACP codec 承担 Provider 状态：Grok 自有 mapper 使用
Grok-owned tool content projection 读取 diff block，再由 Grok tracker 产生累计 snapshot。

### 2.2 Claude Code

当前链路：

```text
assistant.tool_use
  → ClaudeCodeEventMapper
  → AgentToolCall(inProgress, rawInput: input)

user.tool_result
  → ClaudeCodeEventMapper
  → AgentToolCall(completed/failed, rawOutput: text)

两者同 tool id
  → TimelineStore 的共享 partial merge
```

真实 Claude Code `2.1.227`：

```text
Edit tool_use.input:
  file_path, old_string, new_string, replace_all

Write tool_use.input:
  file_path, content

成功 tool_result:
  普通字符串；未观察到结构化 diff，也通常省略 is_error
```

因此文件证据来自 `tool_use`，终态来自 `tool_result`。Claude mapper 必须在 Provider-local
tracker 中保存 tool_use 的中立 projection，并在 tool_result 事件中重新携带同一 snapshot；
不能让 TimelineStore 通过 rawInput 或“上一条 tool”替 Claude 补语义。

Claude history reader 已用独立 identity + 同一个 `ClaudeCodeEventMapper` 重放 JSONL；新 tracker
作为 mapper 的一部分即可复用算法，但 live/history/replay 必须分别实例化。

### 2.3 Codex

当前结构化链路：

```text
item/started | item/fileChange/patchUpdated | item/completed
  → CodexNotificationMapper / codex_app_server_helpers
  → AgentToolCall(kind: edit, raw/rawOutput)
  → presentation 读取 changes/unified_diff

turn/diff/updated
  → AgentTurnDiffEvent(diff: String)
  → TimelineStore
  → presentation 拆 unified diff
```

当前真实命令链路：

```text
commandExecution request approval
  → commandExecution item (commandActions.type: unknown)
  → command completed
  → 文件实际变化
  → 没有 fileChange / patchUpdated / turn diff
```

新方案严格分离两者。`commandExecution` 保持 execute tool，不解析命令、不读修改后的文件、
不生成 `AgentFileChangeSnapshot`。只有结构化 Codex 消息才进入 Codex file-change mapper。

### 2.4 当前 presentation 泄漏

`agent_timeline_grouping.dart` 当前包含：

- `_fileEditChangesFromToolCall`：读取 `rawOutput['changes']` 与 `unified_diff`；
- `_fallbackFilePathsFromToolCall`：从 raw/rawInput/rawOutput 猜路径；
- `_fileEditItemsFromUnifiedDiff`：从 turn aggregate 字符串猜文件身份；
- Context panel 也会把 rawInput/rawOutput 暴露为展示数据。

最终状态必须删除这些文件变更 raw fallback。unified patch 的行统计/高亮仍可在纯
presentation projection 中处理，但文件路径、动作、owner 和 evidence 类型必须已经由
data adapter 确定。

## 3. 目标中立模型

以下为设计形状，命名可在实现时按仓库惯例微调，但语义不得改变：

```dart
enum AgentFileChangeKind {
  created,
  modified,
  deleted,
  moved,
  unknown,
}

enum AgentFileChangeReplayability {
  replayable,
  liveOnly,
}

sealed class AgentFileChangeEvidence {
  const AgentFileChangeEvidence();
}

final class AgentTextReplacementEvidence
    extends AgentFileChangeEvidence {
  const AgentTextReplacementEvidence({
    required this.oldText,
    required this.newText,
    this.replaceAll,
  });

  final String oldText;
  final String newText;
  final bool? replaceAll;
}

final class AgentWrittenContentEvidence extends AgentFileChangeEvidence {
  const AgentWrittenContentEvidence({required this.content});

  final String content;
}

final class AgentUnifiedPatchEvidence extends AgentFileChangeEvidence {
  const AgentUnifiedPatchEvidence({required this.patch});

  final String patch;
}

final class AgentFileChange {
  const AgentFileChange({
    required this.id,
    required this.path,
    required this.kind,
    this.destinationPath,
    this.evidence,
  });

  final String id;
  final String path;
  final String? destinationPath;
  final AgentFileChangeKind kind;
  final AgentFileChangeEvidence? evidence;
}

final class AgentFileChangeSnapshot {
  const AgentFileChangeSnapshot({
    required this.revision,
    required this.replayability,
    required this.changes,
  });

  final int revision;
  final AgentFileChangeReplayability replayability;
  final List<AgentFileChange> changes;
}
```

### 3.1 模型硬语义

1. `textReplacement` 表示 Provider 给出的替换片段，不表示完整文件快照。
2. `writtenContent` 表示 Write 工具请求写入的内容；是否已成功由 tool status 决定。
3. `unifiedPatch` 原样保留 Provider 给出的 patch，不反推完整文件。
4. `evidence == null` 是“只有结构化摘要”，不是第四种 evidence。
5. `AgentToolCall.fileChanges == null` 表示该 tool event 没有文件变更 snapshot；对于已被
   识别的 file-change tool，Provider mapper 必须在每次后续事件中携带完整 snapshot。
6. `changes.isEmpty` 是权威清空，可用于撤下先发出的 turn fallback。
7. 空 `oldText/newText/content/patch` 是合法值，不能解释为文件不存在或字段缺失。
8. `revision` 由 Provider-local tracker 在证据/顺序/动作变化时单调递增；状态或普通文本
   更新不改变 revision。UI 缓存不 hash 大段正文。
9. change id 在 owner scope 内稳定。Provider 无原生 change id 时，由 adapter 使用
   owner id + Provider 顺序 + 路径/目标路径的规范化 key 生成；Store/UI 不重算。
10. evidence 字符串只存在于内存 domain/timeline；不得进入持久化 JSON、日志、通知或
    thread summary raw。

### 3.2 Owner 设计

主要路径继续复用现有 `AgentToolCallEvent`：

```text
AgentToolCallEvent
  → AgentToolCall.fileChanges
  → AgentUpsertToolCallTimelineMutation
  → AgentToolTimelineEntry
```

Codex turn aggregate 迁移为 Provider-neutral typed event：

```text
AgentTurnFileChangesEvent(sessionId, turnId, snapshot)
  → AgentUpsertTurnFileChangesTimelineMutation
  → AgentTurnFileChangesTimelineEntry
```

它替代旧的 `AgentTurnDiffEvent(diff: String)`，但只作为 fallback，不与 tool snapshot
竞争同一个 Store key，也不由 Store 按路径去重。

## 4. 三 Provider 映射规则

### 4.1 Grok

新增 Grok-owned `GrokToolContentProjection` 与 `GrokFileChangeTracker`：

```text
ACP content[type=diff]
  path       → AgentFileChange.path
  oldText    → AgentTextReplacementEvidence.oldText
  newText    → AgentTextReplacementEvidence.newText
  tool kind  → modified/created/deleted/unknown（只按明确字段，不看空文本猜）
```

- 实测 update 没有明确 created/deleted 动作时，默认 `modified` 只来自已确认的 edit 工具语义；
  未知/损坏则 `unknown`。
- `rawInput.replace_all` 只在字段为 bool 且与同一 tool 对齐时映射；不从标题猜。
- diff content 在 inProgress 与 completed 重复时，tracker 复用同一 change id/revision。
- status-only/text-only update 要带回 last-valid snapshot；损坏的新 diff 不覆盖已有有效证据。
- 普通 content block 仍进入 tool 文本；`diff: <path>` 占位最终删除。
- history/replay 使用新的 tracker 实例和同一 mapping 算法。
- 不修改共享 `AcpContentCodec` 的 Provider identity/state 责任；若实现时发现必须改
  `acp_*` 共享文件，按停线规则再次记录并询问。

### 4.2 Claude Code

新增 `ClaudeCodeFileChangeTracker`，key 至少包含
`runtimeScope + sessionId + turnId + toolUseId`：

| Claude tool | 映射 |
|---|---|
| `Edit` | `file_path` + `AgentTextReplacementEvidence(old_string, new_string, replace_all)`；kind=`modified` |
| `Write` | `file_path` + `AgentWrittenContentEvidence(content)`；动作在没有协议保证时为 `unknown`，不根据文件是否存在猜 `created/modified` |
| `NotebookEdit` / `MultiEdit` | 本轮仅 typed path/unknown summary；取得真实 fixture 后再扩 evidence，不解析未知结构 |
| 其他 tool | 不生成 file-change snapshot |

生命周期：

```text
assistant.tool_use
  → tracker 记录 title/kind/location/snapshot
  → 发 inProgress AgentToolCall（语义完整）

user.tool_result
  → tracker 取回同一 tool 的 title/kind/location/snapshot
  → 发 completed/failed AgentToolCall（语义完整）
```

- failed/cancelled 仍保留“尝试执行的证据”，但 UI 必须随 status 标成未成功。
- turn 完成、invalidate、runtime epoch 变化和 dispose 时清理 tracker。
- history reader 已通过同一 mapper 重放；每次 history parse 使用独立 tracker。
- 不从 tool_result 的普通字符串解析路径或 diff。

### 4.3 Codex

新增 Codex-owned `CodexFileChangeMapper/Tracker`：

| Codex 输入 | 行为 |
|---|---|
| `fileChange` ThreadItem / `item/fileChange/patchUpdated.changes[]` | `path/kind/move_path/diff` 映射为 tool snapshot + `AgentUnifiedPatchEvidence` |
| `item/fileChange/outputDelta` | 仅兼容旧文本进度；没有结构化 changes 时不制造 evidence，已有 snapshot 则由 tracker 带回 |
| `turn/diff/updated` | 在 Codex data 层拆为 per-file typed unifiedPatch turn snapshot，标 `liveOnly` |
| `commandExecution` | 永远保持 execute tool；不解析 command/commandActions/approval params，不生成 file-change snapshot |
| 未知/损坏结构 | 宽容降级为原工具或 ignored 诊断；不清空 last-valid evidence，不记录正文 |

Codex tool 与 turn fallback 的唯一真源规则由 Codex tracker 决定：

```text
尚未见 tool fileChange + 收到 turn aggregate
  → 发 typed turn fallback

已经见 tool fileChange + 收到 turn aggregate
  → 忽略 aggregate（只记无正文计数）

先发过 turn fallback + 后来收到 tool fileChange
  → 先发 empty turn snapshot 清除 fallback
  → 再发 tool snapshot
```

Store/UI 不看路径、不看 Provider、不跨 owner 猜重复。`thread/read` 能恢复结构化 fileChange
时，live/history 以 tool owner 对齐；turn fallback 标为 `liveOnly`，不把缺失的历史数据
伪造成恢复成功。

当前 `0.144.1` command-only 实证要形成负向 fixture：文件操作命令即使完成，也断言
`fileChanges == null`。仓库 pin `0.144.5` schema fixture 单独验证结构化兼容路径，二者
不能互相冒充。

## 5. 共享层行为

### 5.1 TimelineStore

必须做的共享改动只有机械透传：

- `AgentToolCall` 构造/copy/Store replacement 带上 `fileChanges`；
- Store 不解析 evidence、路径、命令、raw 或 Provider；
- Provider mapper 已保证同一 file-change tool 的每个事件语义完整，因此 Store 不负责
  “incoming null 时保留旧 snapshot”的 Provider 规则；
- typed turn fallback 仍按 `turnId` 原位 upsert，empty snapshot 隐藏/清除详情；
- 同 tool id 更新、异 tool id 新建的现有身份规则不变。

这项改动命中 G1，也是当前实现停线点。它不要求新增/修改 Provider port。

### 5.2 Coalescing / Pipeline / Reducer

- `AgentToolCallEvent` 继续使用现有 typed tool key 与 latest-wins；不改 policy。
- 新 typed turn event 继承旧 turn diff 的 `threadId + turnId` latest snapshot 语义；只替换
  payload，不拼 patch。
- Provider adapter 在事件进入 buffer 前输出累计 snapshot，故同批
  `tool_use → tool_result` 被 latest-wins 后仍保留证据。
- turn completion 等现有 barrier 在处理前 flush pending；文件变更本身不是新 barrier。
- reducer 仍同步，只产生 tool/turn timeline mutation 与既有 UI update；tracker 位于
  Provider data mapper，不在共享 reducer 中创建 Timer/Future/副作用。

## 6. Presentation 设计

### 6.1 投影层

新增 Provider-neutral projection：

```text
AgentFileChangeSnapshot
  → ordered AgentTimelineFileEditItem
  → renderer by evidence runtime type
```

缓存 key：`ownerEntryId + snapshot.revision + change.id`。窗口宽度不是内容 key。

presentation 可以解析 unified patch 的行标记以做统计和高亮，因为这是中立内容格式；
但不得从 patch header 决定 owner/path/kind，也不得读取 wire/raw 字段。

### 6.2 三种详情

| Evidence | 展示 |
|---|---|
| `AgentTextReplacementEvidence` | 宽窗口左右对比，窄窗口上下排列；标题明确为“替换片段” |
| `AgentWrittenContentEvidence` | 单侧“写入内容”视图；tool 未完成时显示尝试/进行中语义 |
| `AgentUnifiedPatchEvidence` | 复用现有 unified diff 高亮、折叠和统计视觉 |
| `null` | 路径/动作摘要，不可展开，显示“Provider 未提供内容证据” |

`liveOnly` turn fallback 显示“本回合实时汇总”提示；不把它描述为可恢复历史。

### 6.3 热路径与可访问性

- 长内容使用有界 viewport 与 lazy builder，不把 10,000 行塞进单个 RichText。
- 每个 detail 用稳定 `ValueKey(owner + change.id)` 与 `RepaintBoundary`。
- 长路径有界 + 省略号；宽/窄断点用 `LayoutBuilder`。
- 内层代码滚动不改变外层 conversation anchor/follow-end。
- 非颜色语义区分删除/新增，提供 semantics 与键盘滚动。
- 使用 Graphite token；禁止裸色、手写 shadow、临时 radius。
- 不使用 post-frame 测高、`GlobalKey` 查高或 layout 后 `setState` 反馈环。

### 6.4 删除 raw fallback

三个 Provider 的 typed producer、history/replay 与 UI 均通过后，原子删除：

- `_fileEditChangesFromToolCall`；
- `_fallbackFilePathsFromToolCall`；
- presentation 对 `oldText/newText/unified_diff/changes/rawInput/rawOutput` 的文件变更解析；
- 旧 `AgentTurnDiffEvent.diff` 字符串链。

保留其他工具卡仍需要的 `AgentToolCall.raw*`，本任务不扩成全面 raw 清理。

## 7. 日志、隐私与持久化

文件证据可能包含源代码或用户内容，按 G7 处理：

1. 在 typed evidence 接入 live 主链前，先修复 `AgentIgnoredMessageLogger` 对 ignored raw
   payload 的正文串行化；只记录 provider-neutral method/type/reason/count 白名单。
2. fixture 只使用合成 sentinel，真实采样先脱敏；不保留 prompt、回复、命令、真实路径、
   session/turn/tool id、凭证、stderr 原文。
3. `AgentFileChangeSnapshot` 不进入 Zeta 持久化 JSON、thread summary raw、用量索引、系统
   通知或诊断文件。
4. Context panel 只消费 typed summary/evidence，不回显整份 rawInput/rawOutput。
5. 异常解析只增加无正文计数；不得把 malformed block 原样写日志。

## 8. AgentEvent 16 项接入清单

本方案扩展现有 `AgentToolCallEvent` payload，并用 typed
`AgentTurnFileChangesEvent` 替代旧 `AgentTurnDiffEvent`，逐项回答如下：

| # | 问题 | 决定与测试固定方式 |
|---:|---|---|
| 1 | 规范化 identity 由谁产生 | Grok/Claude/Codex 各自的 data mapper + file-change tracker；owner/change id 在进入 application 前完成 |
| 2 | Thread/turn 与接收条件 | tool 事件使用 mapper 已解析的 sessionId/turnId；turn fallback 必须同时有 threadId/turnId；reducer 继续用当前 binding/thread/turn 条件接收 |
| 3 | detached runtime | 不允许；不加入 critical detached allowlist，旧 generation/epoch 继续丢弃 |
| 4 | 是否可合并及 key | tool 继续按现有 thread/turn/tool id key；turn fallback 按 thread/turn/typed-kind key；key 不含 path/raw |
| 5 | merge 语义 | 两者都是完整 snapshot replacement/latest-wins，不追加 patch、不跨 owner 合并 |
| 6 | 输入 barrier | 文件变更事件自身不是 barrier；turn completion/session terminal 等现有 barrier 处理前 flush pending |
| 7 | critical event | 不是新 critical event；由有界 pipeline 正常 coalesce，terminal/barrier 保证前序 snapshot 先 flush |
| 8 | Reducer mutation | tool 产生现有 `AgentUpsertToolCallTimelineMutation`；turn fallback 产生 typed turn-file-change upsert/clear mutation；不改其他 state |
| 9 | UI region | `liveTurn`，以及读取同一 typed timeline 的 context panel；不触发 header/composer/catalog |
| 10 | urgency | in-progress tool 为 next-frame；completed/failed 和 turn fallback/clear 为 immediate，保持现有可见终态与自动滚动语义 |
| 11 | 一次性 UI effect | 只复用既有 `AgentRequestAutoScroll`，不新增 effect |
| 12 | scope-aware conversation effect | 无；不启动 I/O、timer、回调或 Provider 操作 |
| 13 | ThreadSnapshot | 不新增 thread-level 持久字段；history reducer 只在内存 timeline/tool snapshot 中重建证据 |
| 14 | live/history/replay 隔离 | 必须独立 identity/tracker/reducer；canonical 测试逐位比较 tool owner、change order/id/kind/evidence/status |
| 15 | Provider 契约测试 | Grok real-shape ACP Edit、Claude real-shape Edit/Write、Codex current command-only 负向 fixture + pinned schema structured fixture，另有 Provider-neutral Store/Buffer 测试 |
| 16 | raw/source/provider 泄漏 | 不允许；presentation/Store 静态守卫禁止文件变更 wire key、raw 读取和 Provider 分支，identity 只由各自 adapter 决定 |

## 9. 测试策略

### 9.1 真实形状 fixture

| Fixture | 来源 | 固定内容 |
|---|---|---|
| Grok Edit lifecycle | 当前 `1.0.0` 临时 workspace 实测 | tool_call → kind edit + diff content → completed + same diff；正文/path/id 换成合成 sentinel |
| Claude Edit lifecycle | 当前 `2.1.227` 临时 workspace 实测 | tool_use input 四字段 → string tool_result；成功与 is_error 失败变体 |
| Claude Write lifecycle | 当前 `2.1.227` 临时 workspace 实测 | tool_use input `file_path/content` → string tool_result |
| Codex command-only lifecycle | 当前 `0.144.1` 临时 workspace 实测 | request approval + commandExecution completed；不保留命令正文，断言零 file-change event |
| Codex structured lifecycle | 仓库 pin `0.144.5` schema | fileChange started/patchUpdated/completed + turn aggregate；明确标为 schema fixture，不标真实当前 capture |

版本是 fixture metadata，不是测试运行时的 `expected-version` 硬门。

### 9.2 单元与合同测试

- domain：三种 evidence、空字符串、unknown action、move destination、不可变集合；
- Grok mapper/tracker：partial/status-only/重复 diff/损坏 diff/终态保留；
- Claude mapper/tracker：Edit/Write、成功/失败、tool_result 省字段、turn/runtime 清理；
- Codex mapper/tracker：command-only 不误报、structured tool snapshot、turn fallback 抑制/clear；
- Store：Provider-neutral snapshot 原位替换，不解析/保留 Provider partial；
- Buffer/Pipeline：latest-wins 后累计 snapshot 不丢，barrier 顺序不变；
- history/replay canonical：每个 Provider 使用独立 tracker/reducer；
- presentation projection：证据变体、统计、缓存 revision、稳定 key；
- widget：宽/窄、长内容、失败状态、summary、live-only 标记、键盘/semantics；
- architecture guard：共享层与 presentation 不出现 Provider 分支和文件变更 raw key。

### 9.3 真实验收

- 当前环境重新运行 Grok、Claude Edit/Write 与 Codex command-only 脱敏 smoke；
- 若当前 Codex 能实际触发结构化 fileChange，再追加真实 fixture；触发不了时如实标记
  “schema compatibility 已测、当前真实结构化路径待观察”，不得推断通过；
- Windows Profile 在 100+ turn、10,000 行 evidence、1280→1000→1280 resize 下记录
  UI/Raster p95、慢帧率与投影/挂载行计数；Debug 数据不作性能结论。

## 10. 迁移顺序

```text
当前实证与方案重设（已完成）
  → 用户批准 G1 TimelineStore 机械透传范围
  → 日志正文止血
  → domain evidence + tool/turn typed payload
  → Provider-neutral Store/Buffer 合同
  → Grok producer
  → Claude Edit/Write producer
  → Codex command-only guard + structured producer + turn fallback
  → 三 Provider live/history/replay normalization gate
  → projection + 三种详情 Widget
  → 生产 UI 原子切换
  → 删除文件变更 raw fallback/旧 turn diff 字符串链
  → 长期文档、CHANGELOG、全量验收
```

每个步骤都按 `03-任务拆解.md` 单独执行 `dart format .`、`flutter analyze` 和该步
相关测试，并立即更新状态。任何一步发现需要修改 Provider port、共享层职责超出本文所列
机械透传，或改动量明显超过表内估算，立即停线并写入 `04-实现记录.md`。

## 11. 方案比较

| 方案 | 优点 | 问题 | 结论 |
|---|---|---|---|
| UI 继续解析 raw，并加 Claude 分支 | 看似改动小 | 继续违反 G1/G2/G6；每个 Provider 都会增长 UI 特例 | 拒绝 |
| 从命令/工作区/Git 补算 diff | 当前 Codex 也能“看起来有 diff” | 证据不是 Provider 上报，存在竞态、权限和误归属；越过产品边界 | 拒绝 |
| 只做 Grok + Claude，Codex 保持旧链 | 能较快交付两条新路径 | presentation 仍有 Codex wire/raw，通用契约不完整 | 拒绝 |
| 所有证据强转 unified diff | renderer 单一 | old/new 或 Write 内容会被有损/伪造转换 | 拒绝 |
| 中立 snapshot + evidence union + honest fallback | 保留真实强度，三 Provider 同一消费面，无证据不猜 | 需要 domain + G1 Store 机械改动及三套 adapter 测试 | **采用** |

## 12. 风险与回滚

| 风险 | 预防/回滚 |
|---|---|
| Claude tool_result 冲掉 tool_use 证据 | Provider-local tracker 输出累计终态；Buffer 同批 latest-wins 测试 |
| Grok status-only/malformed update 冲掉 diff | Grok tracker last-valid；损坏更新只记无正文计数 |
| Codex tool 与 turn 双显 | Codex tracker 决定 fallback 抑制/empty clear；Store/UI 不去重 |
| Codex command 被误判为编辑 | current real-shape 负向 fixture + 静态禁止 command/raw 解析 |
| Write 被误标“新建” | 没有明确动作时 kind=`unknown`；不检查文件系统 |
| 片段被误称完整文件 | evidence 命名与 UI 文案固定“替换片段/写入内容” |
| 大正文导致 resize 卡顿 | revision cache、有界列表、RepaintBoundary、Profile 门禁 |
| 内容泄漏日志/持久化 | 日志止血先行，sentinel fixture，G7 静态/行为测试 |
| 共享层职责继续膨胀 | G1 只允许字段机械透传；一旦需要 Provider 分支/partial 推断立即停线 |

每一步独立提交、独立验证。若某个 Provider producer 未通过，不启用该 Provider 的 typed UI，
也不删除其旧可见链；绝不恢复“UI 猜 raw”作为长期回滚方案。
