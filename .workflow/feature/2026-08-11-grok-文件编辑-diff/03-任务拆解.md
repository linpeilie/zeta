## 执行约定

- 下表每一行是一个独立提交边界；每步完成后仓库必须可编译、可单独回滚。
- 每个涉及 Dart 的步骤先跑表内定向测试，再跑统一全量绿门：`dart format .`、`flutter analyze`、`flutter test`、`git diff --check`，均必须退出码为 0。定向测试只用于快速定位，不代替全量测试。
- 实施前先将当前工作树的无关改动隔离到其他分支/工作树，并确认基线全绿；不在混合工作树上运行全库 format 或重算架构守卫指纹。
- 严格“先加后删”：先加 domain target、双 Provider tool 生产者和可独测 UI；只有 tool target 的 live/history/replay contract gate 全过后，才原子切换生产展示并停止 Codex turn diff event，最后删除 presentation raw fallback 和旧 turn diff 链。
- 表内文件名都相对仓库根目录；同一单元格内的后续裸文件名与前一个完整路径处于同一目录。

## 硬停线

1. 步骤 1 必须基于 Grok `0.2.119` 与仓库 pin 的 Codex app-server `0.144.5` 完成实证，并用“双 evidence target + 双 Provider tool producer + Store 机械合并 + 无 producer 的 turn 分支退役”获得 G1 Issue 最终批准。未批准不得开始步骤 4‑6。
2. 当前本机 Codex CLI/技能 schema 缓存是 `0.144.1`，不能代替仓库 `0.144.5`；不自动升级到更高 release。无 `0.144.5` 环境时，Codex 真实证据/smoke 步骤保持“待做”。
3. 步骤 2 的 G8 双 Provider 日志安全测试未过，不得开始步骤 6 或 9，避免 Grok old/new 或 Codex patch 进入新 live target 后落日志。
4. 步骤 12 的双 Provider normalization contract gate 未过，不得开始步骤 17；不能用 raw fallback 掩盖某一个 live/history/replay producer 没有归一。
5. 独立 G7 任务未为 Codex/Grok 提供合法 Provider history source 前，按本表严格顺序的步骤 18‑20 均保持“待做”；注入 fixture/canonical 不代替真实 reopen，也不得放宽 `~/.codex`/`~/.grok` 例外。
6. 无 Grok `0.2.119`、Codex `0.144.5` 或 Windows Profile 环境时，步骤 20 标记待执行/阻塞，不用 fake、旧版 CLI、macOS 或 Debug 数据推定通过。
