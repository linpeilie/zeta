# Pi Provider 实现计划

## 实施结论

实现以 Pi `0.84.1`、源码基线 `6d520c58d` 为首个受测版本，协议固定为 **Pi RPC**。Pi RPC 是 LF 分帧的自定义 JSONL，不是 JSON-RPC 2.0，也不是 ACP；不得接入 `ProviderRuntimeJsonRpcPeer` 或共享 ACP mapper。

按四个可独立评审的批次推进：

1. **中立契约批次**：先落第二轮批准的四个可选端口、launch configuration、scope-aware catalog 与现有 Provider 回归。
2. **Pi data 批次**：实现 transport、codec、reducer、history、文件证据、交互与目录发现，不接 UI。
3. **组合与产品批次**：接入 kind/factory/管理页，并以 capability/port 驱动通用 Composer 和工作区资源选择入口。
4. **隔离与验收批次**：补齐序列、Binding、并发、架构守卫和真实 CLI smoke，再更新长期文档。

每个批次必须先通过自身测试再进入下一批次。若实现要求修改 `AgentEventPipeline`、`AgentEventCoalescingPolicy`、`CoalescingEventBuffer`、`BoundedEventDispatcher` 或 `AgentConversationTimelineStore`，立即停线开 Issue；Pi 接入本身没有修改这些共享机制层的理由。

## 十二步实现顺序

### 1. 冻结现有 Bundle 能力映射

以 `01-能力盘点.md` 为唯一能力范围，先把 Pi 的目标 Bundle 写成契约测试，不实现 transport：

- 必选：`runtime`、`conversation`。
- 非空：`threadCatalog`、`threadMutations`、`threadBranching`、`turnSteering`、`queuedInput`、`interactions`、`modelCatalog`、`scopedModelCatalog`、`skills`、`localThreadList`、`sessionConfiguration`、`workspaceResourcePolicy`、`permissionPolicy`。
- `null`：`threadSubscription`、`conversationModes`、`planApproval`、`usageQuota`。
- 部分能力严格由现有细粒度 capability 或端口内 typed capability 门控；archive、unarchive、delete、through-turn fork、permission response、Guardian approval、resource mention 和 service tier 的误调均抛 `UnsupportedError`。

先新增一个不含 Pi 类型的 Bundle contract fake，证明“端口为空时入口不可见、端口内不支持变体会失败”。这一阶段不增加 Pi wire 字段，也不修改共享事件层。

**阶段测试**：`agent_provider_bundle_test.dart`、`agent_provider_capabilities_test.dart`，以及 ViewModel/ProjectThreads 的 unsupported-path 回归。禁止以空列表、空 answers 或 `Future<void>.value()` 代表不支持。

### 2. 定义静态能力与 bootstrap policy

新增 `AgentProviderKind.piRpc`、稳定 provider id、`AgentProviderConfig.defaultPi` 和 `AgentProviderCapabilities.piRpc`。默认配置只保存命令 `pi`；`--mode rpc`、安全参数和会话参数由 Pi data 层按请求组装，不能让 UI 拼 CLI flag。

- `bootstrapPolicy = workspaceScoped`，禁止应用启动时预拉起 session 进程。
- 静态能力只声明第一轮已确认的能力；CLI 版本探测后可以收紧，不得把未知版本能力放大。
- 首个受测版本为 `0.84.1`。低于最低版本 fail-closed；高于基线标记 `newerUntested` 并保留保守能力集，直到 fixture 与 smoke 更新。
- Pi 没有 sandbox。权限目录的描述必须明确“工具可见性不是 OS 隔离”，默认工具选项为禁用全部工具。

`AgentProviderCapabilities.defaultsFor`、配置宽容解码、provider icon/展示映射中的 exhaustive switch 一并补齐；会话 UI 仍只读 capability 和端口，不按 `piRpc` 分支。

**阶段测试**：默认能力逐字段断言、旧 settings 解码、未知/旧版本降级、Pi 默认不 eager preload、所有不支持入口保持关闭。

### 3. 在 data 层建立 Pi RPC 实现骨架

新增 `lib/src/features/agent/data/datasources/pi_rpc/`，职责拆分如下：

- `pi_rpc_peer.dart`：进程、LF-only 分帧、request id、pending response、事件流、超时与关闭。
- `pi_rpc_codec.dart`：command/response/event 的白名单解析和错误类型，不保存对话状态。
- `pi_rpc_process_starter.dart`：稳定组装 `--mode rpc`、cwd、resume、模型、工具策略和工作区资源策略。
- `pi_rpc_agent_provider.dart`：生命周期、Bundle 组合和操作编排。
- `pi_rpc_event_reducer.dart`：Pi-local identity、segment、reasoning phase、去重和终态状态机。
- `pi_rpc_interaction_coordinator.dart`：Extension UI pending registry、timeout 与回写。
- `pi_rpc_file_change_tracker.dart`：`edit`/`write` 的完整 typed snapshot。
- `pi_session_history_reader.dart`：受限目录下的 v1-v3 JSONL list/read/replay。
- `pi_rpc_model_catalog.dart`、`pi_rpc_skills_catalog.dart`：scope-aware 短命 discovery RPC。
- `pi_permission_policy_adapter.dart`、`pi_workspace_resource_policy_adapter.dart`：两套完全独立的启动策略编码。
- `pi_hidden_thread_store.dart`：只保存被本地隐藏的 session id 白名单。

另增 `pi_cli_locator.dart`，复用现有跨平台 CLI 定位与 Windows shim 解析机制。`initialize()` 只做命令/版本就绪检查，不启动 session；`startSession` / `resumeSession` 收到 cwd 与 launch snapshot 后才拉起常驻 RPC 进程。

进程参数门禁：

- 新建不传 `--session-id`；恢复只用 `--session <完整 session id>`，找不到必须失败，不能创建同 id 新会话。
- 未解析到工作区资源选择时显式 `--no-approve`。
- 未解析到工具策略时显式 `--no-tools`。
- global list/history 不启动常驻进程；模型/Skill discovery 使用 `--no-session` 的短命进程，且不发送 prompt。
- stderr、协议错误和 transport 日志只记录长度、类型、command 名与计数，不记录原文、参数值、路径、prompt、文件内容或凭证。

**阶段测试**：字节分块、LF/CRLF、字符串内 U+2028/U+2029、超长行、坏 JSON、非对象、缺失 type、并发乱序 response、未知/重复 id、command 不匹配、timeout、进程提前退出、串行写、幂等关闭、关闭后拒绝新请求、stderr 脱敏，以及 macOS/Linux/Windows 启动参数快照。

### 4. 将 Pi 事实归一化为中立模型

Pi-local reducer 使用 Zeta 生成的 session/turn/segment identity，Pi 的 entry id、message 信息和 toolCallId 只作为 source metadata 或工具关联证据。核心状态机固定为：

- `sendMessage` 接受后创建 Zeta logical turn；Pi 的 `turn_start` / `turn_end` 只是同一 logical turn 内的单次模型调用，不直接成为 Zeta turn 边界。
- `message_update` 按 `contentIndex` 组装 text/thinking/tool-call block；`message_end.message` 是权威快照。重复 end、迟到 delta 和旧 generation 一律丢弃或按 last-valid 规则收敛。
- `steer` 保持当前 logical turn；`follow_up` 在入队时预留新的 logical turn identity，进入执行时切换边界。
- `agent_end` 不是稳定终态。自动 retry、compaction retry 和 steer continuation 保持当前 turn；已知 follow-up 开始时完成前一 turn；最后一个 turn 仅在 `agent_settled` 后完成。
- first-terminal-wins，进程 exit、abort、协议错误与正常 settled 不能重复完成同一 turn。
- 输入 encoder 支持 text 与本地 image；图片只在当前模型声明 image input 时读取并编码。Pi 不支持的 mention、text element、image detail，以及一次消息中的多个 Skill 都在发送前抛 `UnsupportedError`。单个 Skill 只按当前 scoped catalog 的稳定名称编码为 `/skill:<name> <用户文本>`，不发送 Skill 路径。
- assistant usage 在 Provider-local reducer 内按 logical turn 累加，输出 `isSessionCumulative=false`；context window 单独输出，不把 session stats 当账号 quota。
- `tool_execution_*` 只按稳定 `toolCallId` upsert。`edit`/`write` 由 tracker 输出完整 `AgentFileChangeSnapshot`；`bash`、未知 extension tool 和命令文本不推测文件变化。
- Extension UI 的 `select` / `confirm` / `input` / `editor` 映射为 `AgentQuestionRequest`；空 answers 映射 cancel。permission、Plan 和 Guardian 回写始终抛 `UnsupportedError`。
- fire-and-forget UI 只有在能无损映射现有 typed status/name/system event 时才输出；widget/editor 改写不穿透到 presentation。

live、history 和 replay 各自创建独立 reducer/tracker。`raw` 只保留经过白名单化且确有诊断价值的 metadata；默认使用空 map。

**阶段测试**：正常文本、图片与模型 input gate、单 Skill 展开、所有不支持输入变体、多 content block、thinking→text、tool loop、多次模型调用、steer、单个/多个 follow-up、auto retry、compaction retry、abort、模型错误、重复/乱序消息、进程 exit、并发 Extension UI、timeout 与迟到 response、edit/write 成功和失败、bash 不产生文件证据、turn usage 聚合。

### 5. 先落新的中立可选端口

这一阶段单独提交并先让现有 Provider 全绿，再让 Pi 使用。具体顺序：

1. 从 `AgentThreadCatalogPort` 移出 `unsubscribeThread`，新增 `AgentThreadSubscriptionPort`。Codex 暴露真实端口；Grok、Claude Code 与 Pi 为 `null`，旧必选门面中的不支持实现改抛 `UnsupportedError`。
2. 新增 `AgentQueuedInputPort`、`AgentQueuedInputDelivery` 与 typed capabilities。Codex 暴露 `beforeNextModelInvocation`；Pi 暴露两种 delivery；`AgentTurnSteeringPort` 暂保留为前一种 delivery 的兼容视图。
3. 新增 `AgentWorkspaceResourcePolicyPort` 及 catalog/selection/apply/snapshot 模型。默认 snapshot 必须表示保守拒绝，不能委托 CLI 已保存的 trust 猜测。
4. 新增 `AgentSessionLaunchConfiguration`，聚合 permission snapshot 与 workspace-resource snapshot。新的 `AgentConversationPort.startSession/resumeSession` 和 `AgentThreadBranchingPort.forkThread` 只接收该不可变配置；旧 `AgentProvider` 门面由中立 legacy adapter 仅转发 permission 部分。
5. 为新实现增加 Provider 无关的 native Bundle 贡献接口，使 Pi 可直接提供新 conversation/branching 端口；`AgentProviderBundle.adapt` 只能按接口判断，禁止按 kind/id 判断。
6. 新增 `AgentCatalogScope` 与 `AgentScopedModelCatalogPort`；`AgentSkillsPort.listSkills` 同样接收 scope 和 resource snapshot。
7. 扩展 `AgentModelCatalogRepository` 的 cache、single-flight、generation 与 last-known-good key：`provider + config fingerprint + includeHidden + scope key + resource option`。模型缓存升为宽容读取的 V2；V1 条目按 global scope 迁移。
8. 新增独立的 `AgentWorkspaceResourcePolicyController/State/Store`。它与 permission controller、pending registry、Plan 状态和持久化 key 均不复用。磁盘只保存 provider id、不可逆 workspace scope key 和 option id；为生成稳定的 SHA-256 scope key，把 `crypto` 声明为直接依赖，不落原始工作区路径。
9. Composer 只在端口与 delivery capability 存在时展示排队时机；工作区资源选择器只在对应端口存在时展示，并明确它不控制工具执行。application/data 层再次校验，误调抛错。

资源选择为 `nextRuntime` 时不修改当前进程；下一次 start/resume/fork 冻结新 snapshot。global scoped discovery 可以使用该 snapshot，但不得创建 session runtime。

**阶段测试**：四个端口的 null/非 null 组合、每个不支持变体的 `UnsupportedError`、Codex unsubscribe 迁移、Codex steer 兼容、工作区资源默认 deny、permission/resource 2×2 组合互不推导、旧 generation 结果丢弃、两 workspace 缓存不串、resource option 切换不复用 LKG、V1/V2/损坏缓存、持久化 JSON 不含项目路径，以及 capability-driven widget 测试。

### 6. 明确 ACP 复用边界

本步骤结论是 **不复用 ACP 协议层**：Pi RPC 没有 ACP initialize/session/update 语义，不能送入 `AcpSessionUpdateDecoder`、`AcpPermissionMapper`、`AcpContentCodec` 或 `AcpSessionConfigMapper`。

可复用的只有 Provider 无关的 domain model、Bundle port、operation scheduler 和应用级 repository。Pi 的 codec/reducer/file tracker 均留在 `datasources/pi_rpc/`。

**阶段测试**：架构守卫断言 Pi data 文件不 import `mappers/acp_*`，共享 ACP 文件不出现 Pi 名称、kind、id 或 fixture；现有 Grok ACP contract tests 原样通过。

### 7. 接入 kind、factory、产品目录与管理页

在 `DefaultAgentProviderFactory` 增加 `piRpc → PiRpcAgentProvider`，factory 仍只由 runtime registry 调用。同步完成：

- 配置 codec 宽容识别 `piRpc`，旧配置中补入默认关闭的 Pi 定义，不改变 active provider。
- `AgentDefinition.pi`、管理页 repository 注册、CLI 检测、版本读取、JSON 配置检查与显式连接测试。
- 连接测试只执行 `--version` 和无 prompt 的 RPC probe（`get_state` / model catalog）；Pi 无统一账号登录态时报告 `notRequired` 或 `unknown`，不能伪报 logged-in。
- provider icon/展示名、管理页 setup 文案和 exhaustive switch 补齐；对话页面仍不按 kind 分支。
- usage statistics 的 built-in source 对 Pi 显式返回 `null`：live `AgentTokenUsageEvent` 不等于账号 quota，也不自动授权新增历史统计源。
- app 组合层注入 Pi hidden-thread store 与 workspace-resource store 的具体文件；feature/application 不自行拼 Zeta 数据目录。

连接测试和模型刷新复用 global runtime/repository，不通过真实模型 turn。配置与日志展示继续走脱敏白名单。

**阶段测试**：factory 唯一调用方守卫、同 config 创建 Pi、Cursor 仍 fail-closed、旧/损坏 settings、默认禁用/显式启用、管理检测未安装/版本不兼容/协议失败/成功、连接测试零 prompt、管理页列表和图标 widget、usage source 为 null。

### 8. 按非 JSON-RPC 生命周期实现 Pi peer

开发者指南的 JSON-RPC 包装要求对 Pi 不适用，但必须实现等价的 fail-closed 生命周期：

- `stopped → starting → initializing → ready → closing → closed`；启动失败进入 `failed`。
- session peer 启动后先发送带 id 的 `get_state`，响应成功才标记 ready；不存在独立 initialize/initialized 消息。
- `beginClosing` 后拒绝新 command，先拒绝 pending request/interaction，再串行关闭 stdin、订阅与进程；超时才强制终止。
- 每次主进程连接生成新的 `AgentRuntimeScope(runtimeId, connectionEpoch)`；旧 scope 的 response/event/onDone 不能污染新连接。
- global runtime 的 `initialize()` 不启动 Pi 常驻进程；短命 discovery peer 每次独立关闭，不能发布为 session event source。

**阶段测试**：并发 initialize single-flight、start failure、get_state failure、ready 前拒绝业务 command、close 时 pending 全部失败、重复 dispose、旧进程迟到 output/onDone、重启 epoch 变化、discovery process 不泄漏且不占 session scope。

### 9. 所有 thread 操作接入 OperationScheduler

Pi adapter 按以下资源键调度，禁止在持有同键时再次 schedule：

| 操作 | 资源键 | 模式 | 实现 |
|---|---|---|---|
| list threads | Project | `sharedRead` | 受限扫描 Pi session 目录，按 cwd/filter/page 读取 header/摘要 |
| read history | Thread | `sharedRead` | 按完整 session id 定位并宽容解析 v1-v3 |
| scoped model/Skill discovery | Project | `sharedRead` | 短命无 prompt RPC |
| resume | Thread | `exclusive` | 精确 `--session <id>`，失败不回退新建 |
| rename | Thread | `exclusive` | 当前 peer 或短命 resumed peer 的 `set_session_name` |
| compact | Thread | `exclusive` | 当前 session peer 的 `compact`；明确可能产生模型费用 |
| fork current head | Thread | `exclusive` | 短命 resumed peer 执行 `clone` 并读取新 session id |
| session config write | Process | `exclusive` | 对当前 peer 的 typed setter |

Pi 不实现 archive/unarchive/delete；这些操作在调度前即因 capability 失败。普通 fork 使用短命 peer，避免把 A 的常驻进程切换成 B；返回 B 后不提前创建 B 的 session runtime。

**阶段测试**：同 thread FIFO、read/read 并发、write barrier、不同 thread 并发、失败释放 key、同键重入失败、关闭取消排队任务；另测 rename/compact/fork 与 history read 的真实调用顺序。

### 11. 增加流式序列与 canonical signature 回归

fixture 放在 `test/fixtures/pi_rpc/0.84.1/`，manifest 只记录 CLI 版本、源码基线、平台类型和场景名；内容使用合成 id、合成文本与虚拟相对路径，不放真实 prompt、回复、工具输出、凭证或本机路径。

必须覆盖的序列：

1. 单段文本与多个 text block。
2. thinking/text 交替和同 contentIndex 的 start/delta/end。
3. assistant toolCall + tool execution start/update/end + tool result。
4. `edit`、`write` 和 command-only `bash`。
5. steer 保持同 turn。
6. 一个及多个 follow-up 形成新 logical turn。
7. `agent_end → auto retry/compaction retry → agent_settled`。
8. abort、error stop reason、进程提前退出和重复终态。
9. 并发 Extension UI、timeout、cancel 与迟到 response。
10. session v1/v2/v3、compaction、branch summary、abandoned branch 和 custom entry。

每条 fixture 先断言 `raw update → AgentEvent` 的逐位置 canonical signature，再用 **独立** reducer 分别跑 live/history/replay，比较 entry kind/id、turn id、segment、phase、tool id、status、usage、文件快照 revision/replayability 与相对顺序。若某类历史无法重建等价文件 evidence，明确输出 `liveOnly` 并用测试固定，不能伪报 `replayable`。

最后用 Provider 无关 fixture 原样回归 CoalescingPolicy/Buffer/Pipeline/TimelineStore；这些测试不得引用 `PiRpc*` 或 Pi fixture。新增 `pi_rpc_shared_layer_purity_test.dart`，守卫 G1 文件无 Pi import、名称、kind/id 分支，Bundle 只出现中立端口接口。

### 12. 完成 Binding、多会话和真实 CLI 验收

在现有 Binding harness 上增加 Pi factory/peer fake，覆盖：

- 新建/打开/读历史/模型与 Skill discovery 都不创建 session runtime；首次 `beginTurn` 才创建。
- 同一 global scope 并发租约只创建一个 provider；同一 session Binding 最多一个常驻 Pi 进程。
- 不同 thread 使用不同 session scope、peer、reducer、interaction registry 和 file tracker；A 的恢复、发送、settled、exit 或 dispose 不影响 B。
- draft→thread 原子晋升保持同一 runtime；TTL、运行中 turn/RPC、重叠 sweep、ABA identity、dispose/acquire 屏障、配置失效、旧 generation 丢弃与 global 永不回收全部回归。
- fork A→B 通过 Shell 通用登记/选择流程：A 不改绑；clone 的短命 peer 退出；B 有独立 Entry/Binding；B 首次发送前没有 session runtime；后续 rename/send 只作用 B。
- permission 与 workspace-resource snapshot 分别冻结；两 thread、两 Canvas 选择互不串；resource allow 不产生工具预授权。
- follow-up 入队成功只表示 Provider 接受，不表示已执行；进程退出时未执行队列以错误/终态收敛。

新增 `tool/smoke_pi_rpc.py --expected-version 0.84.1`，真实平台验收分两层：

1. **无模型 smoke**：版本、严格 JSONL 启动、`get_state`、模型/推理目录、session config setter、关闭；使用临时 workspace、`--no-session --no-tools --no-approve`。
2. **需凭据 smoke**：最小非破坏性 prompt、text/thinking 流、cancel、steer、follow-up、settled；持久化/恢复/rename/clone/history 使用临时 session dir，结束后只清理该临时目录。

记录只包含 OS/架构、CLI 版本、协议类型、场景名、事件/响应计数和通过/失败；不得记录 prompt、回复、文件内容、原始 payload、session/turn id、stderr 原文或凭据。没有对应平台、模型账号或版本时标记“待执行/阻塞”，不能用 fake 测试推断通过。目标平台为 macOS、Windows、Linux；外部 CLI 自动化不能替代三平台人工验收。

## 测试执行顺序

1. 中立 domain/application 契约测试先绿，再提交契约批次。
2. Pi peer/codec/process starter 的纯 data 测试。
3. Pi reducer/history/file tracker 的 fixture 序列测试。
4. Pi provider 端口与 OperationScheduler 契约测试。
5. Bundle、model/Skill/resource controller、ViewModel、ProjectThreads 与 widget 回归。
6. Binding registry/manager、多会话、fork 与 architecture guards。
7. `dart format .`、`flutter analyze`、`flutter test`。
8. 执行 AGENTS.md G1 自查命令，并确认共享机制层 diff 为空。
9. 执行真实 Pi smoke，把结果写入同目录的 `04-验收报告.md`。

单文件失败时先跑对应最小测试；合入前仍必须跑完整测试。`dart_test.yaml` 的并发配置保持不变。

## 最终交付门

- 四个中立端口已经独立评审，现有 Codex/Grok/Claude Code 行为无回归。
- Pi 的所有 source identity、segment、reasoning、去重、终态与文件 evidence 均在 Pi-local adapter/reducer 中闭合。
- unsupported 始终表现为端口 `null` / capability false / `UnsupportedError`，没有 no-op 或近似语义。
- Pi wire 字段只存在于 data 层；domain/application/presentation 无 Pi raw key。
- 模型/Skill scope、工作区资源策略、工具权限、用户提问和 Plan 四类状态互不推导。
- Zeta 持久化不含 prompt、回复、工具输出、文件 evidence 正文、raw payload、session path 或原始 workspace path。
- 同步长期文档：Provider 契约与能力清单、架构总览中英文、开发者指南、glossary 中英文、贡献指南中英文、Pi RPC 协议基线、AGENTS 事实清单；用户可见变化写入 CHANGELOG 的未发布区。
- `04-验收报告.md` 如实记录自动化、架构自查和真实平台 smoke；任何未执行项保持阻塞，不写“推定通过”。
