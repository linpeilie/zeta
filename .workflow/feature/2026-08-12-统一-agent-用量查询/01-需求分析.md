# 统一 Agent 用量查询 · 需求分析

- 日期：2026-08-12
- 状态：已确认，T00 已完成
- 档位：L
- 类型：跨 Provider 用量查询收敛 + Claude Code Token 历史能力补齐

## 1. 问题陈述

当前套餐额度已通过中立 `usageQuota` 端口隔离 Provider 协议，但 Token 历史的组合、缓存和 UI 装配仍显式知道 Codex/Grok；新增 Provider 需同时修改面板聚合仓储、索引 Store 和 `IdeHome`，并且 Claude Code 已有 Token 解析却无法进入全局统计。

可验证的痛点是：**每增加一个 Token 历史来源，必须修改至少一个共享聚合类和共享索引类，而不是只注册 Provider 自有实现。**

设计核对曾发现一项前置冲突：当前 Grok 统计代码和开发者文档要求读取 `$GROK_HOME/sessions/**/updates.jsonl`，但当时的权威规则 G7 禁止读取 `~/.grok`。用户于 2026-08-12 明确决定删除这条读取禁令，允许 Provider data 层按功能读取其他 CLI 私有数据；原 G8/G9 顺延为新 G7/G8。

## 2. 当前的用户可见行为

1. 侧栏 Agent 用量面板按已启用 Provider 展示当日 Token 和可用套餐额度，支持逐 Provider 加载、局部失败和静默刷新。
2. 完整使用统计页按时间、项目、Provider 和模型聚合 Codex/Grok 本地历史。
3. Codex/Grok 的套餐失败不影响本地 Token 历史展示；单个历史来源失败不丢弃其他来源。
4. 历史索引为版本化可重建数据，损坏时不阻断启动，不保存 Prompt、回复、工具输出、凭据、原始错误正文或 session 文件路径。
5. 回合完成会驱动侧栏用量静默刷新，不改变当前会话 Provider。

## 3. 目标

1. 为两种不同语义保留独立端口：
   - 套餐/限额：Provider 账号实时快照；
   - Token 历史：按回合的本地或远程派生记录。
2. 新增一个 application 级统一查询与组合边界，侧栏和完整统计页不再自己拼装 Provider 数据源。
3. 每个 Provider 在 data 层实现自己的 Token 查询、差分、去重、路径解析和索引 codec；共享查询层只消费中立结果。
4. 新增 Provider 的 Token 统计时，正常改动范围收敛为“Provider 自有实现 + app 组合注册 + 自有测试”。
5. 在新边界稳定后接入 Claude Code Token 历史，使其当日 Token 和完整统计与 Codex/Grok 一致。
6. Provider 自有 source 可以读取其查询逻辑需要的 CLI 私有数据；读取、协议解析和路径处理全部留在 data 层，不把 raw 或私有路径上浮。

## 4. 可观察验收标准

1. 打开 Agent 用量面板时，Codex/Grok 仍展示与重构前相同的今日 Token、套餐窗口、加载和错误状态。
2. 打开完整使用统计页时，筛选、趋势、排名和任务明细与重构前一致，Provider 局部失败仍只产生 warning。
3. 仅套餐查询失败时仍显示该 Provider 的本地 Token 统计；仅历史扫描失败时仍可显示套餐。
4. 实现一个测试 Provider Token source 只需向 app 组合注册；共享 query/index 源码无需新增 kind/id 分支。
5. 升级后能宽容读取现有 v2/v3 索引；损坏、缺字段和未知分区不阻断应用，并且并行刷新不丢失其他 Provider 分区。
6. Claude Code 有可读历史时，侧栏显示当日 Token，完整统计页可用 Provider 筛选查到其回合；单条回合 Token 不重复计算。
7. `IdeHome` 不再 import 或实例化 `usage_statistics/data` 的具体仓储、扫描器或索引实现。
8. 架构守卫保证 Provider 私有数据读取只发生在自有 data adapter；共享 query/store 不接收 raw、环境值或 session 路径，派生索引仍只保存规范化白名单字段。

## 5. 明确不做

- 不改变套餐购买、续费、计费单位或价格语义。
- 不伪造 Provider 未提供的额度、成本或 TTFT；缺失数据保持缺失。
- 不将 Prompt、回复、工具输出、原始错误、凭据或 session 文件路径写入 Zeta 索引。
- 不改 `AgentEvent`、TimelineStore、CoalescingPolicy/Buffer/Pipeline 或 Provider identity 语义。
- 不在首阶段修改 `AgentProviderBundle`、`AgentUsageQuotaProvider` 或其他 Provider 端口。
- 不因统计查询切换会话 active Provider，也不创建 session runtime。
- 不将 Provider 自有历史 codec 上提到共享 application/domain 层。
- 不把 CLI 私有数据读取能力上提到 domain/application/presentation，也不把“允许读取”解释为自动授权迁移、改写或删除。

## 6. 不做的代价

- Claude Code 已有 live/history usage 解析，却会长期在全局 Token 统计中缺席。
- 下一个 Provider 仍会复制 Codex/Grok 分支，扩大 `ProviderAgentUsagePanelRepository` 和 `UsageStatisticsIndexStore`。
- 侧栏与完整统计页会继续存在两套路径解析、扫描和缓存语义，显示结果可能漂移。
- 在 UI 组合层继续新增 data 实现，会使分层依赖进一步反向。

## 7. 命中门禁与复杂度

| 门禁 | 原因 |
|---|---|
| G1/G2 | 需确保统计重构不向共享事件管线上浮 Provider 分支或 identity 推断 |
| G4 | 套餐仍以可选端口表达，Token source 不支持时必须是明确 unsupported，不得 no-op 伪造成功 |
| G6 | 要移除 UI 对 data 具体类的装配，Provider 原始历史只留在 data |
| G6/G7 | Provider 私有数据读取只留在 data；索引演进必须版本化、宽容、白名单且可重建 |

本任务定为 **L 档**：同时涉及跨层装配收敛、中立数据源契约、持久化格式演进和 Claude Code 新的用户可见能力，需完整走需求、设计、拆解、实现和验收。

## 8. 用户决策

用户已确认本文、`02-方案设计.md` 和 `03-任务拆解.md`，并明确要求：

- 删除原 G7“不得读取其他 CLI 私有数据”的门禁；
- 允许 Provider data adapter 按功能读取其他 CLI 私有数据；
- “允许读取”不自动扩大为迁移、改写或删除授权；
- 原 G8“敏感持久化”与 G9“主题 token”分别顺延为新 G7、G8。

因此不再采用精确路径白名单前置方案，T00 先同步权威规则、长期文档和门禁引用，再进入业务实现。
