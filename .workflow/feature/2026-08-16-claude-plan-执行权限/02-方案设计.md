# 02 · 方案设计

任务：Claude Code Plan 下点「执行」仍以只读规划继续；厘清两种 Plan 机制并给出可落地修法

日期：2026-08-16

状态：待实现

档位：**L**（权限 / Plan 交接 / 多 Provider 能力边界，命中 G4 G5）

## 结论先行（唯一推荐）

**不对外做「两种都叫 Plan 的平行产品」；对内承认两种能力，执行路径按能力收口。**

1. **对话 Plan**：`bundle.conversationModes` 目录含 Plan。入口是斜杠 / More / Plan Chip。点执行 = 新开 Default **对话**回合。Codex / Grok 走这条，行为保持现状。
2. **权限 Plan**：`permissionPolicy` 目录里该项带中立标记 `planningOnly`。入口只在权限下拉。点执行 = 本会话离开只读规划，新开可干活回合，工具栏跟着变，**不写**用户持久化默认。Claude Code 走这条。
3. 共享层 **不**按 `providerId` / kind 分支，**不**解析 `:plan`。只认端口是否存在 + 目录标记。
4. **不改** G1 共享适配层（Pipeline / Coalescing / TimelineStore / 共享 ACP mapper）。不是中立事件缺口。
5. **不合并** `ExitPlanMode` 审批卡与本地交接卡（那是另一次产品决策）。本方案只修交接「执行」真正离开只读。

用户感知一句话：在只读规划里点交接「执行」后，这一句和工具栏都不能再停在只读；高风险工具仍按新权限询问。

## 1. 现状

### 1.1 两套已经存在的机制

| 机制 | 端口 | 谁有 | 改的是什么 |
|---|---|---|---|
| 对话 Plan | `conversationModes` | Codex、Grok | 下一回合协作模式 |
| 权限 Plan | `permissionPolicy` | Codex / Grok / Claude 都有目录；**只有 Claude 的一项是只读规划** | 进程允许干什么 |
| Provider 计划审批 | `planApproval` | Claude（`ExitPlanMode`）、Grok | 阻塞回合的方案确认 |
| 本地执行交接 | 无端口，Zeta application | 成功 Plan 终态后 | 要不要新开干活回合 |

Claude Bundle **不挂** `conversationModes`。Composer 的 Plan Chip / 斜杠 Plan 对 Claude 本来就不出现。用户进 Plan 的路是权限下拉里的 Plan。

### 1.2 关键符号

| 符号 | 职责 |
|---|---|
| `AgentConversationModeController` | 对话模式目录、draft / confirmed、`selectMode`、`snapshotForNewTurn` |
| `AgentConversationPermissionSelectionController` | 权限目录、apply、persist、`effectiveSelection`、`selectionBeforeCurrentUserSelection` |
| `AgentPlanExecutionHandoffController` | 非持久化交接；`stageProviderApprovedPlan` / `offerCompletedPlan` / `reconcileExecutionPermission` |
| `AgentConversationViewModel.startPlanExecution` | 点交接「执行」：Default 模式 + `sendMessage` + 权限快照覆盖 |
| `AgentConversationViewModel.respondToPlanApproval` | 审批卡「执行」= 回写 `accepted`；若 `localExecutionHandoff` 则暂存交接 |
| `ClaudeCodePermissionModeCodec` / `catalog()` | `:ask` / `:accept-edits` / `:plan` / `:bypass` ↔ CLI `--permission-mode` |
| `ClaudeCodeAgentProvider._applyTurnPermissionSnapshot` | 本回合快照有 optionId 且与当前不同才重启 peer |
| `ClaudeCodeAgentProvider._switchPermissionMode` | tearDown + `--resume` + 新 `--permission-mode` |

### 1.3 调用链（Claude，出问题的那条）

```text
用户在权限下拉选 Plan
  → PermissionSelectionController.selectOption
  → permissionPolicy.apply → 重启 CLI（--permission-mode plan）
  → runtime generation 常 +1
  → selectionBeforeCurrentUserSelection 因 generation / 身份对不上变为 null

助手发出 ExitPlanMode
  → PlanApprovalAdapter → 审批卡（按钮也叫「执行」）
  → 用户点执行 → respondToPlanApproval(accepted)
  → 只 allow 该工具，不改权限、不开新回合
  → stageProviderApprovedPlan(executionPermission: selectionBefore… ≈ null)

回合成功终态
  → offerCompletedPlan → reconcile
  → 记忆失效则 catalogDefault（:ask）或 providerFallback（无 optionId）

用户点交接「执行」
  → startPlanExecution
  → selectMode(Default)          // Claude 无 conversationModes，空操作
  → sendMessage(planExecutionPrompt, permissionSnapshotOverride)
  → 若快照无 optionId：_applyTurnPermissionSnapshot 直接 return
  → 进程仍是 --permission-mode plan
  → 工具栏仍显示 Plan
```

Codex / Grok 对话 Plan 的链是：`selectMode(Plan)` → 终态 `offerCompletedPlan`（要求 `modeId.kind == plan`）→ `startPlanExecution` → `selectMode(Default)` + 新回合。权限通常不是只读档，所以「没切权限」看不出来。

### 1.4 根因（一句话）

交接把「离开 Plan」实现成 **对话模式 Default**，没有「离开只读权限」这条能力路径；Claude 只有后一条，所以点执行等于只发了一句「去执行」的 prompt，进程还在规划。

## 2. 分层归属

| 改动 | 层 | 为什么 |
|---|---|---|
| `AgentPermissionOption.planningOnly` | domain | 中立目录属性。application 不得解析 optionId |
| 交接 reconcile：丢弃 planningOnly 种子；有端口时禁止空 fallback | application | 执行策略是 Zeta 工作流，不是厂商协议 |
| `selectionBeforePlanningOnly`（记忆不绑 generation） | application | 进只读规划会重启 Claude 进程，generation 门闩过严是工作流问题 |
| `adoptSessionPermission(..., persistDefault: false)` | application | 「执行」= 本会话离开只读，不是改用户默认 |
| `startPlanExecution` 按 **能力** 组合：有对话 Plan 则 Default；有权限 Plan 则 adopt 非 planning | presentation/application（VM） | VM 已是交接编排点；禁止 `if (claude)` |
| Claude `catalog()` 给 Plan 打 `planningOnly: true` | data | 唯一允许出现 Claude 语义的地方 |
| `_applyTurnPermissionSnapshot` 对空快照保持不切；有 optionId 必须切 | data | 已有行为；补测试即可 |
| Composer 权限项副文案（只读） | presentation | 按 option.planningOnly 渲染，不按厂商 |
| 审批卡文案（接受方案 ≠ 开始执行） | presentation | 降点错；不改协议 |
| Pipeline / Store / Coalescing / 共享 ACP | **不改** | 见 §4 G1 |

不新建 feature，不新建顶层目录。

## 3. 契约变更

### 3.1 Domain

- `AgentPermissionOption` 增加 `planningOnly`，默认 `false`。相等性计入该字段。
- **不**新增 bundle 端口、**不**新增 AgentEvent、**不**改 `AgentConversationMode*`。
- 不把 `planningOnly` 理解成「这是 Claude」。Grok/Codex 权限项保持 false。

### 3.2 Bundle / capability

- 端口集合不变。
- 派生（不必进 `AgentProviderCapabilities` 也能做）：
  - 对话 Plan 可用 ⇔ `conversationModes` 非空且目录含 Plan；
  - 权限 Plan 可用 ⇔ `permissionPolicy` 非空且存在 `planningOnly && allowed`。
- UI 继续「端口空则入口不出现」。

### 3.3 事件

无。交接仍是本地 `AgentPlanExecutionRequest`。审批仍是 `AgentPlanApprovalRequestedEvent`。

### 3.4 持久化

- **不**新增 `~/.zeta` 字段。
- 点执行 **不**调用 `persistOptionId`。用户默认仍可以是 Plan；新 thread 进 Plan 的方式和现在一样。
- 会话内 `effectiveSelection` 变为非 planning，只活在当前 Binding。

### 3.5 行为契约（执行）

```text
reconcile 之后的 executionPermission：
  - 无权限端口 → 仍可 providerFallback（Codex 对话 Plan 无权限选择时）
  - 有权限端口 → 必须有 optionId，且对应项 !planningOnly
  - 否则禁用「执行」，不得发送

startPlanExecution：
  1. 上述校验
  2. 关闭交接卡
  3. 若对话 Plan 能力可用 → selectMode(Default)
  4. 若权限端口存在 → adoptSessionPermission(该选择, persistDefault: false)
  5. sendMessage(..., override = resolved 快照)
```

`ExitPlanMode` 审批「执行」仍只 `accepted`，本方案不改语义，只改按钮文案以免和交接混淆。

## 4. 门禁合规

### G1 · 共享适配层零 Provider 依赖

**不改** Pipeline / CoalescingPolicy / Buffer / Dispatcher / TimelineStore / 共享 `acp_*.dart`。

论证：缺口是「执行交接如何离开只读权限」，属于 Zeta 本地工作流 + 权限目录标记，不是某条 ACP/JSON-RPC 乱序或 id 要共享层猜。Claude 的 `--permission-mode` 留在自有 adapter。

### G2 · 身份由 Provider 决定，Store 不猜

不改 TimelineStore，不改 entryId。optionId 仍不透明；共享层只读 adapter 打好的 `planningOnly`。

### G3 · reducer 纯同步

不改 reducer。权限切换仍走既有 Effect / Provider 异步 apply。

### G4 · 按 capability 渲染，禁止静默成功

- Plan Chip / 斜杠：仍只看 `conversationModes`。
- 权限 Plan：看目录 `planningOnly`，不看厂商名。
- 有端口却无法得到非 planning 选择 → 禁用执行，不发假成功回合。
- adopt / apply 失败 → 表面错误，不带着 plan 进程发送。

### G5 · 四种审批隔离，绝不预授权

| 类型 | 本方案 |
|---|---|
| 权限审批 | 不动 registry |
| 用户提问 | 不动 |
| Plan 审批 | 仍只走 `respondToPlanApproval` |
| 本地交接 | 仍新开 Default/干活回合，不调 `AgentPlanApprovalPort`，不 steer |

离开只读 **不等于** 预授权计划里的命令。Ask 仍逐项问。  
相对现行开发者文档「卡内改选零 apply」：本方案只对 **点交接执行** 允许一次会话 apply；卡上改选仍不 apply、不持久化。实现时改 `developer_guide` 对应段，不改 G5 编号。

### G6 · 分层单向，协议只在 data

`planningOnly` 是中立布尔。`:plan` / `permission-mode` 只在 `claude_code_*`。application 不 import Claude 类型。

### G7 · 不落盘敏感内容

不新增落盘。不把计划正文、快照 raw 写入权限记忆（记忆只有不透明 optionId + thread/provider）。

### G8 · 主题 token

文案微调走现有 Chip / 交接卡，无新色值。

## 5. 兼容性

### 旧数据

无 schema 版本要迁。缺 `planningOnly` 的构造 / 测试夹具 = `false`，Codex/Grok 交接与现在一致。

### 旧调用方

- `reconcileExecutionPermission` / `startPlanExecution` 签名可保持，行为变严：有端口时不再用空 fallback 发出去。
- Fake Provider 测试若未标 planningOnly，黄金路径不变。
- Claude 假目录必须给 Plan 打标，否则测不到本 bug。

### Capability

不减端口。Claude 不会突然出现对话 Plan 选择器（仍无 `conversationModes`）。  
用户若希望 Claude 也有斜杠 Plan：超出本方案，以后用「斜杠按权限 Plan 能力分发」另开任务。

### 两者皆有的 Provider（今天没有）

先定死以免以后分叉：点执行 **两步都做**（Default 对话 + 离开 planning 权限）。本任务不实现假「双有」Provider，单测用组合 fake 锁优先级即可。

## 7. 风险与取舍

### 推荐里已消化的风险

- **resume 忽略 `--permission-mode`**：Zeta 仍必须传对；真 CLI 用冒烟。若官方忽略，另开「会话内退出 Plan」（前序讨论的 F），不塞进本任务。
- **adopt 重启慢**：与用户手动改权限相同；先 adopt 再 send，第二次 apply 应 no-op。
- **用户默认就是 Plan**：本会话切到 Ask（或进规划前的 Accept edits）；新 thread 默认不变。

### 否决的做法（只列考虑过的，不是候选清单）

| 否决 | 原因 |
|---|---|
| 对外做两套都叫 Plan 的产品（斜杠一套、权限一套、两套交接） | 修 bug 过重；入口分裂；本任务用不完。能力标记足够让以后再拆文案 |
| `if (providerId == claude)` | G4 |
| application 解析 `:plan` | 打破 optionId 不透明，G2/G6 |
| 把离开只读写进共享 Pipeline | 不是事件语义缺口，G1 论证不成立 |
| 点审批「执行」= 批准 + 立刻干活（合并双卡） | 改变 G5 时序与「执行必须新回合」；另立项 |
| 默认改成 `ThemeMode` 那种改内存默认 | 类比不成立；把默认权限改 Ask 会害「我就想默认只读」的用户 |
| 执行仍零 apply，只靠 send 快照、工具栏保持 Plan | 修得了这一句，下一句普通发送又回到 Plan，用户仍认为没切 |

### 本方案刻意不做

- Claude 斜杠 Plan
- 合并两张「执行」卡的协议语义（只改审批卡文案）
- 持久化「上次执行用的权限」
- 预授权计划中的任何工具

## 实现顺序（供 03 拆解，此处不定工时）

1. domain `planningOnly` + Claude catalog + reconcile 收紧 + 单测（执行快照不再能是规划档）。
2. `selectionBeforePlanningOnly` + `adoptSessionPermission` + `startPlanExecution` 接线。
3. 审批卡 / 权限项文案；`developer_guide` Plan 段；CHANGELOG。

第 1 步即可消除「执行回合仍挂 plan 进程」；第 2 步消除「工具栏还是 Plan」。
