## 0. 一句话结论

**seam 位置已经对了，缺的是维度和回收。**
`AgentProviderRuntimeRegistry._entries` 是 `Map<providerId, entry>` —— 只需把 key 扩成「providerId + 会话作用域」，并给 entry 加空闲回收。`AgentRuntimeScope`（runtimeId@epoch）、`AgentProviderEventListenerGate`（listener generation）、`AgentProviderRuntimeIdentity`（providerId+generation）这三套隔离机制**已经存在且已按「实例」而非「provider」建模**，回收 / 重建能直接复用，不需要新造。

代价在别处：**懒启动**要改的是 `AgentConversationViewModel` 里 11 个 `_ensureProvider()` 调用点中「打开 thread 就调」的那一条。

## 1. 当前结构

### 1.1 所有权链

```
app.dart / ide_shell_controller.dart
  └─ AgentProviderRuntimeRegistry            ← 进程内唯一所有者，Map<providerId, entry>
       ├─ providerFactory: DefaultAgentProviderFactory  (kind → Codex / Grok / 未实现)
       └─ permissionStateStore                ← 按 AgentProviderRuntimeIdentity 分区

AgentThreadWorkspaceController
  └─ AgentThreadWorkspaceEntry[]              ← 每个会话/草稿一个，常驻
       ├─ ActiveAgentProviderController       ← 每 entry 一个（!），但共享同一个 registry
       └─ AgentConversationViewModel          ← 每 entry 一个
```

**关键事实：会话级的东西已经是每会话一份了**（entry / VM / providerController）。唯一共享的是最底下那个 registry entry ——也就是真正的 CLI 子进程。这正是痛点的物理位置。

### 1.2 现在的实例生命周期

| 阶段 | 现状 |
|---|---|
| 创建 | `registry.acquire(config)` → `providerFactory.create(config)`；同 providerId 已存在则复用 |
| 复用判据 | `_requiresRuntimeRestart`：kind / command / arguments / environment 变了才重建 |
| 引用计数 | `_AgentProviderRuntimeEntry.leaseCount`，`_createLease` +1，`_release` −1 |
| **销毁** | **只有三条路径：`invalidateProvider`（配置变更/禁用）、`close`（应用退出）、身份错配的防御分支。`leaseCount` 归零不销毁任何东西。** |
| 身份 | `AgentProviderRuntimeIdentity(providerId, generation)`，generation 单调递增 |

`AgentProviderRuntimeLease.release()` 的注释写得很清楚：「Provider 仍由应用注册表保温，直到配置失效或应用退出」。**这就是要改的那一句。**

### 1.3 已有的隔离机制（回收可直接复用）

| 机制 | 位置 | 作用 |
|---|---|---|
| `AgentRuntimeScope(runtimeId, connectionEpoch)` | `domain/agent_runtime_models.dart` | 标识一次具体连接；`ProviderRuntimeJsonRpcPeer` 每次 `start()` 递增 epoch，旧 epoch 的响应被 `sendScopedResponse` 明确拒绝 |
| `AgentProviderEventListenerGate` | `application/` | listener generation + runtimeScope 双重校验，拒绝旧连接的迟到事件 |
| `AgentProviderLifecycleState` | domain | stopped→starting→initializing→ready→failed→closing→closed，`_ensureRpcAllowed` 按状态 fail-closed |
| `ProviderOperationScheduler` | `data/datasources/transport/` | 已有 `RuntimeOperationKey` / `ThreadOperationKey` / **`ProcessOperationKey(runtimeId, processId)`** 四级资源键 + 共享读/独占语义 |
| `AgentPermissionStateStore` | `application/` | 状态按 `AgentProviderRuntimeIdentity` 分区，`activateRuntime` / `retireRuntime` 已是实例粒度 |

`ProcessOperationKey` 的存在说明：**「一个 provider 对应多个进程」这件事在调度层已经预留了位置，只是上面没人用。**

### 1.4 Grok 侧的现状证据

`grok_acp_agent_provider.dart:2338` 注释原文：「多 session 共享进程时，只有全部 turn 结束后才广播 ready」。
`agent_provider.dart:74` 注释原文：「共享 Provider 中切换到其他会话不得自动退订仍被其他 Pane 使用的 thread」。

即：**当前代码是明确按「一个进程多会话」写的**，这不是疏漏，是设计。改造是推翻这条设计假设，不是修 bug —— 与 01 的定性一致。

### 3.3 基础设施缺口

- `AgentProviderRuntimeRegistry` **不接受可注入的 clock**，也没有 Timer 抽象。10 分钟 TTL 的测试必须靠假时钟，否则测试要真等 10 分钟。**这是 03 阶段第一件要做的事**，且它是纯增量、不改行为。
- `dart_test.yaml` 并发固定为 2 —— 并发会话测试要自带隔离，不能依赖测试级并行。

## 4. Zeta 专项检查

### Q1 · 搬迁后依赖方向会不会反向？（G6）

**不会，但有一个陷阱。** 新的会话绑定与回收器落在 `features/agent/application/`，与现有 registry 同层，只依赖 `AgentProvider` / `AgentProviderFactory` 接口。domain 不引入 Flutter / `dart:io` / Provider 协议。

陷阱：**回收器需要 `Timer` 和时钟**。这两个必须留在 application（或由 EffectRunner 承担），**绝不能下沉到 domain**。会话 key 若要放 domain，只能是纯数据类，参照 `AgentRuntimeScope` 的写法（不可变、值相等、无引用）。

### Q2 · 字段名会不会被持久化 codec 当 JSON key？（G8）

**不触发。** 涉及的三个身份类型全是内存态：

- `AgentProviderRuntimeIdentity(providerId, generation)` —— `AgentPermissionStateStore` 的 map key，不落盘
- `AgentRuntimeScope(runtimeId, connectionEpoch)` —— 连接期有效
- 新增的「会话↔实例」绑定 —— 按 01 的边界，只存内存

`AgentProviderConfig` 的持久化 JSON key（`selectedPermissionOptionId` / `extra` / `enabled` 等）**本次一个都不动**。

⚠️ **一条待确认**：`AgentThreadWorkspaceEntry.entryId` 是否参与工作台恢复的落盘？若是，会话 key 直接复用 entryId 就等于把内存身份和持久化身份耦合起来。**进入 04 之前必须确认。**

### Q3 · 涉及的 Widget 有没有参与 IdeHome 跨页保活或稳定 Key？

**Widget 树本次不动**，但有一条隐性风险：
`AgentThreadWorkspaceEntry._handleRuntimeChanged()`（`agent_thread_workspace_controller.dart:163`）监听 runtime 变化并 `_notify()`。**回收实例会触发这条通知** —— 若它导致 entry 重建或 VM 状态重置，用户会看到「闲置十分钟后回来，草稿/滚动位置没了」。

必须在 03 钉住：**回收只销毁 provider 实例，entry / VM / 时间线 / 草稿 / 滚动位置一律不动。**

### Q4 · 涉及的 reducer 是不是 live/history/replay 共用算法但必须各自独立实例？（G3）

**本次不动 reducer，也不动事件管线。** 回收 / 重建走的是既有路径：新实例 → 新 `runtimeId` → 新 epoch → Gate 换 generation → 旧事件被拒。

红线：**回收与重建都是副作用，必须在 EffectRunner / application 侧发生，reducer 保持纯同步。** 一旦出现「在 reducer 里启停 provider」，触发 01 的 L4，回滚。

### Q5 · 有没有把 Provider 专属逻辑上提到共享层？（G1）

**这是本次最大的架构判断点。**

改动集中在 `agent_provider_runtime_registry.dart`（application 层，当前已完全 provider 无关：只认 `AgentProvider` 接口与 `AgentProviderConfig`）。共享适配层（Pipeline / CoalescingPolicy / Buffer / Dispatcher / TimelineStore / 共享 ACP mapper）**一行不碰**。

**红线**：「Grok 一进程一会话、Codex 一进程多会话」这个差异，**绝不能写成 `if (config.kind == AgentProviderKind.acp)`**。必须表达成中立能力（例如由 `AgentProviderCapabilities` 或 factory 声明「每实例最大并发会话数」），由各 provider 的 adapter 自己声明。写成 kind 分支即违反 G1，触发 01 的 L3。
