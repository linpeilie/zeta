## 2. 补了哪些测试，各自钉住什么

### 2.1 `test/src/features/agent/application/agent_provider_runtime_registry_test.dart`（扩展 +5）

新增 group `实例保温与销毁语义（会话级改造前的 characterization）`：

| 用例 | 钉住的行为 |
|---|---|
| 同一 Provider 的多个消费者共享同一实例与同一 runtime identity | **痛点本身**。改造后这条断言必然要改，它就是行为变更的可见证据 |
| 全部租约释放后实例仍被保温，再次获取复用同一实例与同一 generation | 现状「release 不销毁」，且复用不递增 generation。回收器要改的正是前半句 |
| 仍有活跃租约时 invalidateProvider 照样销毁实例 | 现状销毁**不看引用计数**。回收器必须改成看 —— 否则会在会话正跑时把进程掐掉（AC5） |
| 重复释放同一租约不会让计数变负，也不会误伤其他租约 | 引用计数的健壮性。回收判据直接建在这个计数上，它一旦能变负，回收就会误判 |
| 实例 dispose 抛错时 invalidateProvider 不外泄异常且可立即重建 | 回收发生在后台定时器里，销毁抛错**不能**冒泡出来炸掉整个回收循环 |

### 2.2 `test/src/features/usage_statistics/data/provider_agent_usage_panel_repository_test.dart`（新建 +3）

02 的 **N4**，改造前零覆盖。用量面板是「会话之前的全局信息」最典型的消费者。

| 用例 | 钉住的行为 |
|---|---|
| 成功路径：租约被释放，共享实例不被关闭 | **借了要还、还了不关**。这条不变量在改造前后都必须成立 |
| 读取套餐抛错时仍然释放租约，并按无套餐继续返回 | `finally` 里的归还路径。失败不能泄漏租约，否则回收器永远等不到引用计数归零 |
| 多个已启用 Provider 各借各还，结束后没有租约残留 | 多 Provider 并行读取时的租约收支平衡 |

### 2.3 `test/src/features/agent/presentation/agent_conversation_runtime_recycle_test.dart`（新建 +2）

02 的 **Q3 隐性风险**：闲置回收后回到 Pane，用户不能发现自己的会话没了。

用现有的 `invalidateProvider` 作为「实例被销毁并重建」的等价触发 —— 回收器落地后直接复用这两条。

| 用例 | 钉住的行为 |
|---|---|
| 实例被销毁并重建后，已有会话时间线不被清空 | 销毁的只应是子进程实例，会话内容原样保留 |
| 实例重建后 runtime identity 递增，旧实例已退役 | 权限状态按新实例分区，旧 identity 不再是 current —— 回收→重建复用的就是这条既有机制 |

配套加了 `_MultiInstanceProviderFactory`：现有 `AgentPaneFakeProviderFactory` 每次返回**同一个**
实例，观测不到「销毁后重建」，所以另写了一个每次 create 返回新实例的 factory。

## 3. 明知裸奔但这次不补的路径

| 路径 | 为什么不补 |
|---|---|
| **N2 · 两个会话并发向同一 provider 发 turn** | 这是 **AC1，不是安全网**。写出来现在就是红的（那正是痛点）。安全网必须改动前全绿，红的测试放进来会污染阶段门。它属于 04 的验收用例，届时由「从红变绿」来证明重构生效 |
| **N5 · 两个 management repository 的 `ownsRegistry = true` 临时 registry 分支** | 这条分支的行为**本来就要改**（改造后必须绑到全局实例，不能再自建）。给一条即将删掉的分支写 characterization test 是浪费。改到它时直接补新行为的测试 |
| **N7 · 流式输出中的会话不被回收** | 回收器还不存在，没有现状可钉。属于 AC5，随回收器一起写 |
| **可注入 clock 的测试基础设施** | 它是生产代码的结构改动（虽是纯增量），按流程属于 **04 的第 1 步**，不该混进安全网提交。10 分钟 TTL 的测试要等它 |
| **`_ensureProvider` 的 11 个调用点逐一覆盖** | 其中 9 个的行为不变（都是"已经在会话里"的操作）。只有 `sendMessage`(1808) 和"打开 thread"(2124) 两条会变，且它们的目标行为是 AC2/AC3，同样属于验收而非安全网 |
| **真实 grok CLI 冒烟** | 按 01 的确认，AC1 必须真机验证。但它不是单元安全网，放在 04/05 执行 |

## 4. 改动前的基线：不是全绿

**必须如实写明：仓库在本次改动之前就有 15 条测试失败。**

用 `git stash -u` 前后各跑一次全量对照：

| | 结果 |
|---|---|
| 改动前（stash 后） | `+1270 ~1 -15` |
| 改动后 | `+1280 ~1 -15` |

失败数完全一致，新增 10 条全部通过 —— **本次改动没有引入任何失败**。

### 15 条失败的分类（均为既有问题）

| 类别 | 数量 | 根因 |
|---|---|---|
| 测试文件整体加载失败 | 7 | `package:platform` 3.0.0 与当前 Dart SDK 不兼容：`local_platform.dart:46` 引用了已被移除的 `Platform.packageRoot` |
| 日志断言不匹配 | 4 | 断言期望消息以 `Agent provider error event: ` 开头，实际记录带 `[zeta] [logger.name] ` 前缀；另有一条日志捕获为空 |
| 字体加载相关 widget test | 3 | 环境缺字体资源 |
| Popover 展开 widget test | 1 | 待查 |

### 对本次重构的影响

**有一条值得单独点名**：
`agent_conversation_effect_runner_test.dart` 的「logs provider errors only for matching provider generation and runtime」**落在本次的影响面内**（provider generation 正是回收/重建要动的东西）。

已确认它失败的原因**只是日志前缀字符串不匹配**，被断言的行为（按 generation + runtimeId 过滤事件）
仍在正常执行 —— 从上面那条断言的 `Actual` 内容可以看到 `listenerGeneration` / `runtimeId` /
`connectionEpoch` 都正确带上了。所以它不构成安全网空洞，但**它现在没法当安全网用**：
重构后即使把这条行为改坏，它也还是红的，看不出区别。

**处理方式**：不在本次修它（超出 01 的范围边界，且是既有问题）。改到 EffectRunner 的
generation 过滤逻辑时，用 §2.3 新增的那两条 runtime identity 测试作为替代保护。
建议单开一个 issue 修这批日志断言 —— 那是独立的、有价值的清理。
