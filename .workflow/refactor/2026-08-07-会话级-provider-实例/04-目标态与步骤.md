## 0. 关键设计判断（先说清楚，后面步骤都建在这上面）

### 0.1 回收 ≡ 对单个 scope 执行一次 invalidate

这是让本次改动变小的核心。`invalidateProvider` 的**下游行为已经全部存在**：

```
dispose 实例 → lease.isCurrent 变 false
            → ActiveAgentProviderController._provider 返回 null
            → 下次 activeProvider() 自动重建
            → 新 runtimeId / epoch → EventListenerGate 换 generation → 旧事件被拒
            → permissionStateStore.retireRuntime(旧) / activateRuntime(新)
```

**回收器不需要发明任何新的失效语义**，只需要决定"何时对哪个 scope 调用它"。
这条链路已由 03 §2.3 的两条测试钉住。

### 0.2 引用 ≠ 正在使用：拆成 lease 与 pin

现状 `leaseCount` 混了两件事。会话侧的 controller 会**长期**持有一个 lease（只要 entry 存在），
所以 `leaseCount == 0` 永远等不到，不能作为回收判据。

| 概念 | 含义 | 是否阻止回收 |
|---|---|---|
| **lease** | 谁引用着这个实例（controller 持有到 entry 销毁） | **否** |
| **pin** | 谁**正在用**它（运行中的 turn、进行中的 RPC） | **是** |
| **lastActiveAt** | 最近一次 `touch()` 的时刻 | 计时起点 |

回收判据：`pinCount == 0 && now - lastActiveAt >= 10min`。
**AC5（流式输出中不被回收）由 pin 保证，不靠计时。**

### 0.3 每会话一实例，不按 provider 分档

按 01 的要求，绑定是**统一**的：每个会话最多一个实例，Codex 和 Grok 一视同仁。

这顺带避开了 **G1 最大的红线** —— 不需要在共享层写 `if (kind == acp)`，因为根本没有分支。

**代价要说清楚**：Codex app-server 本可一进程多 thread，统一改造后同时开 5 个 Codex 会话
会有 5 个进程。用回收器（§0.2）和懒启动（§0.4）缓解。若日后进程数成为问题，中立的扩展点是
让 `AgentProviderCapabilities` 声明"每实例最大并发会话数"，由各 adapter 自己填 —— **那是另一次改动，本次不做。**

### 0.4 全局实例承担"会话之前"的一切

V1/V2 已确认：用量、skill、模型列表、**以及打开 thread 时的历史读取**都能在全局实例上完成。

关键区分（现有 `AgentProvider` 接口本来就是分开的）：

| 操作 | 归属 | 理由 |
|---|---|---|
| `readThreadHistory` | **全局实例** | 只读目录能力，不建立订阅 |
| `listThreads` / `listModels` / skills / 用量 | **全局实例** | 会话之前的信息 |
| `resumeSession` / `startSession` / `sendMessage` / `steerTurn` / `cancelTurn` | **会话实例** | 建立订阅、产生 turn |

02 已验证这个切分与现状一致：`switchThread` 只调 `read:thread-1`，`resume` 发生在 `sendMessage` 里。

## 1. 目标结构

```
domain/  agent_runtime_models.dart
  └─ AgentProviderRuntimeScopeKey          ← 新增。纯不可变值类型，global | session(id)
                                              参照 AgentRuntimeScope 的写法：无 Timer、无引用

application/  agent_provider_runtime_registry.dart
  └─ AgentProviderRuntimeRegistry          ← 改造：Map<(providerId, scopeKey), entry>
       ├─ acquire(config, {scope})          ← scope 默认 global
       ├─ invalidateScope(providerId, scope)
       ├─ clock / timerFactory 可注入       ← 新增，测试用
       └─ entry: + pinCount + lastActiveAt

application/  agent_provider_idle_reaper.dart   ← 新增文件
  └─ AgentProviderIdleReaper               ← 周期扫描，命中即调 registry.invalidateScope
                                              副作用容器，绝不进 reducer（G3）

lib/src/ui/.../active_agent_provider_controller.dart
  └─ + final AgentProviderRuntimeScopeKey scope   ← 默认 global

application/  agent_thread_workspace_controller.dart
  └─ _createEntry 为每个 entry 分配 session scope 并传给它的 controller
```

**层归属理由**：

- scope key 是纯数据 → domain。它必须不带 Timer / 进程引用，否则 domain 就被拉进 dart:io（**G6**）。
- registry 与 reaper 是副作用与进程所有权 → application。**reducer 保持纯同步**（**G3**）。
- 共享适配层（Pipeline / Coalescing / Buffer / Dispatcher / TimelineStore / 共享 mapper）**一行不碰**（**G1**）。
- 绑定关系只存内存，不落盘（**G8** 不触发；V3 已确认 entryId 本就不持久化）。

## 3. 每步之间的绿状态保证

| 步 | 为什么此步结束时仓库是可编译且绿的 |
|---|---|
| S1 | 纯增量参数，默认值等于现状 |
| S2 | `scope` 是可选具名参数且默认 global，现有调用方一行不改 |
| S3 | 两个新入口在此步返回同一个 global 实例，纯改名 + 分类 |
| S4 | 只改 `_createEntry` 一处的构造参数；行为变化被新增测试覆盖，既有测试不驱动多会话 |
| S5 | 新字段无人读取 |
| S6 | reaper 只对 `scope != global` 生效；global 不受影响，全局功能路径不变 |
| S7 | 从"默认 global"改成"显式 global"，等价 |
| S8 | 删除的分支在 S7 后已无生产调用方 |

## 4. 与止损线的对应

| 止损线（01） | 会在哪一步暴露 |
|---|---|
| **L1** 全局实例拿不到全局信息 | V1 已验证为「可以」，风险已解除。若 S7 发现某个消费者仍必须依附会话，就地止损 |
| **L2** 回收后重连恢复不了上下文 | **S6**。命中则退回 S5，只保留懒启动与会话隔离 |
| **L3** 生命周期管理侵入共享适配层 | **S2/S6**。任何时候发现要往 Pipeline/Coalescing/TimelineStore 塞 provider 概念，立刻退回 |
| **L4** reducer 里启停 provider | **S5/S6**。pin 与回收都必须在 EffectRunner/application 侧 |
| **L5** 回收器竞态 flaky | **S6**。关掉回收，先发 S1–S5 |
| **L6** 2 个工作日 AC1 仍不绿 | **S4**。回滚到当前 `dev` |
