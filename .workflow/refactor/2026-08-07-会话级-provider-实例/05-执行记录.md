## S2 · `_generationByProviderId` 未按字面改成复合键

**04 原文**（S2 行）：

> `_entries` / `_generationByProviderId` 的 key 改为复合键。

**实际实现**：`_entries` 的 key 改成了 `(providerId, scope)` 复合键（record 类型
`_RuntimeKey`），但 `_generationByProviderId` **保留了原来 `Map<String, int>`
的键类型**，仍然只按 `providerId` 计数，不区分 scope。

### 为什么偏离

`AgentProviderRuntimeIdentity` 的相等性只看 `(providerId, generation,
isProvisional)`（见 [`agent_permission_state_store.dart:24`](../../../lib/src/features/agent/application/agent_permission_state_store.dart)），
不含 scope。`AgentPermissionStateStore._activeByProvider` 也只按 `providerId`
索引"当前" runtime，同样不含 scope（见同文件 `_activeByProvider` 字段，及
`isCurrent`/`activateRuntime`/`retireRuntime` 的实现）。翻遍 04 的 S1–S9，
没有任何一步计划修改 `agent_permission_state_store.dart`。

如果 `_generationByProviderId` 也按 `(providerId, scope)` 复合键独立计数，
两个不同 scope 的 generation 会各自从 1 开始。同一个 providerId 下，
global scope 的第 1 个实例和某个 session scope 的第 1 个实例就会拿到**完全相同**
的 `AgentProviderRuntimeIdentity`（`providerId@1`）。`AgentPermissionStateStore`
无法区分这两个不同的运行时实例——`activateRuntime`/`retireRuntime`/`isCurrent`
会把它们当成同一个 runtime，后创建的会覆盖/污染先创建的权限状态。这正是
[`01-动机与止损线.md`](01-动机与止损线.md) 反复强调要避免的"旧 runtime 的异步
apply/广播污染新进程"类问题，只是触发条件从"重启"变成了"另一个 scope"。

保留 `_generationByProviderId` 按 providerId（不分 scope）单调递增，
generation 数字在整个 provider 生命周期内全局唯一，避免了这个碰撞，
且不需要改动 `agent_permission_state_store.dart`（超出 S2 声明的涉及文件范围）。

### 是否影响 S2 的完成判据

不影响。04 给 S2 定的完成判据是：

- 现有调用方一行不改仍编译通过 ✅（`_generationByProviderId` 对外不可见）
- 03 的 5 条 characterization 全绿 ✅（它们只走 global scope，generation 计数方式不变）
- 新增测试证明"两个不同 session scope 拿到两个实例、global 与 session 互不干扰" ✅

没有任何判据要求 generation **按 scope** 独立计数；新增测试里专门加了一条
"不同 session scope 各自维护独立的 runtime generation，identity 不会撞车"，
钉住的正是"全局递增、不会撞车"这个实际实现的行为。

### 后续步骤要注意什么

S4 翻开关、S6 接回收器之后，同一个 providerId 会**真的**同时存在 global +
多个 session 实例。届时如果要给 `AgentPermissionStateStore` 补 scope 维度的
状态隔离（例如每个会话有独立的权限选择），那是一次单独的、需要同步更新
`agent_permission_state_store.dart` 及其测试的改动，不在本次 04 的步骤范围内，
届时应先补一条 characterization 测试钉住当前"权限状态不区分 scope，只区分
providerId"的行为，再动手改。

### 两处存疑：rename / archive

02 §2.4 把这两个点标注为"视 provider 而定"——不同 provider 的 `renameThread` /
`archiveThread` 实现是否要求先有一个已建立的会话连接，02 没有下结论；04 的 §0.4
表和 S3 完成判据里也都没有点名这两个操作该归 catalog 还是 session。

选择把它们归为 **session**，理由是风险不对称：

- 这两个方法只有在 `sessionId != null`（即这个 workspace entry 已经有一个活跃
  thread）时才可调用，天然是"这个 entry 自己的会话"语境，归到该 entry 专属的
  session 实例是最贴近语义的选择。
- 更重要的是分错的代价不对称。归 session 之后如果实际上 provider 允许在 catalog
  实例上直接改名/归档，代价只是多起一个本可以不起的会话进程；反过来如果归
  catalog，但某个 provider 的这两个 RPC 实际要求先 `resume` 会话，S4 翻开关后
  会直接在没有会话上下文的全局实例上调用失败——这是功能性 bug，不是资源浪费。
  两者代价不对等时选保守的一边。

S3 阶段这个判断不影响任何测试结果（两个入口都还是同一个 global 实例）；只有
S4 让 session scope 真正生效后才可能暴露"归错了"的问题。如果 S4/后续冒烟发现
某个 provider 的 rename/archive 其实可以走 catalog，届时把这两个调用点的入口
和这段注释一起改，不需要动 registry/controller 层。

## S4 · 卡住：「catalog 入口继续走 global」不是免费的，且需要的改动会破坏既有断言

**状态：本步骤已回滚到 S3 结束时的状态，未完成。** 三条硬约束里第二条明确要求
"某个断言必须改才能过 → 立刻停下来告诉我"——这正是发生的事。

### 试了什么

按 04 字面描述，`_createEntry` 翻开关只需要给 entry 专属的 `ActiveAgentProviderController`
传 `scope: session(entryId)`。但这样做之后立刻发现："catalog 入口继续走 global"
这句话不会自动成立——S3 里 `_ensureCatalogProvider` 和 `_ensureSessionProvider`
都是 `_ensureProvider` 的薄包装，而 `_ensureProvider` 内部固定调用
`providerController.activeProvider()`。`activeProvider()` 只有一个租约缓存字段
（`_providerLease`），受 controller 构造时固定的 `scope` 支配。一旦 `_createEntry`
把这个 scope 设成 session，**catalog 调用点也会跟着变成 session**——打开一个
thread 就会拉起该 entry 专属的会话进程，AC2/AC3 直接不成立。

要让 catalog 真的走 global，`_ensureCatalogProvider` 必须绕开
`providerController.activeProvider()` 的单租约缓存，改用不受 `scope` 支配、
每次都强制 global 的获取路径（复用已有的 `acquireProvider(config)`，改造成
始终 `scope: AgentProviderRuntimeScopeKey.global`，借还配对）。这部分本身是
安全的——单独验证过，`project_threads_controller.dart:741` 这个 `acquireProvider`
现有调用方不受影响（它的 controller 本来就是 global）。

### 卡在哪：`_ensureConversationModeCatalog` 的去重和 `_provider` 强耦合

问题出在 `_ensureCatalogProvider` 要不要顺带触发 `_ensureConversationModeCatalog`
/ `_ensureSkillsCatalog`（`loadModels()` 等既有调用方靠 `_ensureProvider` 自动
水合对话模式目录，自己不会再调一次）。

`_ensureConversationModeCatalog` 的去重完全靠 VM 的 `_provider` 字段：

```dart
Future<void> _ensureConversationModeCatalog(AgentProvider provider) async {
  ...
  await _conversationModeController.loadCatalog(...);   // 无条件执行，会清空 draftMode
  if (_disposed ||
      generation != _conversationModeCatalogLoadGeneration ||
      !identical(_provider, provider)) {                // 去重承诺建立在这里
    return;                                              // 不提交，但 loadCatalog 已经跑完了
  }
  _conversationModeCatalogProvider = provider;            // 只有走到这里才算"记住已加载"
  ...
}
```

这个"已加载"的记忆（`_conversationModeCatalogProvider`）**只有在 `_provider`
先被设成同一个 `provider` 时才会被提交**——而这正是 `_ensureSessionProvider`
（session 独占）才做的事。如果从 `_ensureCatalogProvider` 里调用它，`_provider`
永远对不上，"记住已加载"永远提交不了，于是**每一次** catalog 或 session 调用
都会重新触发 `loadCatalog(...)`，而 `loadCatalog` 一上来就把 `draftMode` 清空
再按"是否已有值"回填默认值。

实测坍缩点：`sends an immutable Plan snapshot without changing model preference`
——用户 `selectConversationMode(plan)` 之后调 `sendMessage`，`sendMessage` 走
session 路径，session 路径又触发一次 `_ensureConversationModeCatalog`，因为
去重从未提交成功，这次调用重新 `loadCatalog`，把刚选的 `plan` 冲回 `default`。
断言 `expect(selection.modeId, AgentConversationModeId.plan)` 因此失败。

加上这条注释掉 `_ensureConversationModeCatalog`/`_ensureSkillsCatalog` 调用后，
反过来 `loadModels()` 单独调用就无法再让 `canSelectConversationMode` 变
`true`（因为目录从没被水合过），这条断言以另一种方式失败。**两种写法都会改动
一个既有断言，不是"改一行让测试适配"能绕过去的**——问题在 `_ensureConversationModeCatalog`
的去重设计本身只支持"恰好一个绑定点"的用法，不支持"两个独立入口各自水合"。

实测：17 个失败（15 个新增 + 2 个已知基线），已确认并非因为遗漏某个 case，
是设计层面的耦合。已把 `_ensureCatalogProvider`、`_createEntry`、`acquireProvider`
三处改动**完整回滚**到 S3 结束时的状态，重新跑过 `agent_conversation_view_model_test.dart`
确认回到 92 passed / 2 known failures（与 S3 完全一致）。

### 再次卡住：`_provider` 不只是"目录去重"用，还是事件处理的门禁

去重修好后，我把 `acquireProvider`（强制 global scope）和 `_ensureCatalogProvider`
（改走 `acquireProvider`，不写 `_provider`）重新接了回去，跑 `agent_conversation_
view_model_test.dart`：从 17 个失败降到 10 个（2 个是已知基线，8 个新增）——
比第一次尝试好，但仍然是真失败，不是"改一行适配"能绕过去的。

挑第一个查：`updateWorkspace unsubscribes previous thread on project change`。
`switchThread` 打开 thread 后离开项目应该退订该 thread 的事件，但断言
`Expected: ['thread-1'], Actual: []`——退订压根没发生。原因：`updateWorkspace`
里退订逻辑是 `final provider = _provider; if (provider != null) { unsubscribe(...); }`
——如果 `_ensureCatalogProvider`（`switchThread` 走的入口）不写 `_provider`，
这里永远拿不到要退订的对象。

顺着这条线把整个文件里 `_provider` 字段的用法翻了一遍（不止这一处），发现它是
VM 里"当前实时连接的是哪个 provider"这个概念的唯一载体，被下面这些地方直接
读取：

| 用途 | 代码位置 | 后果 |
|---|---|---|
| **事件是否被处理** | `_replaceProviderEventSubscription` 里 `processEvent` 回调：`if (!identical(_provider, provider)) return;`（3105/3118 行） | **最严重**：如果 catalog 调用改绑 `_provider`，会让正在流式输出的 turn 的后续事件被**静默丢弃**——不是测试失败，是真实的"轮到一半突然卡住" |
| 离开项目/thread 时退订旧事件 | `updateWorkspace`（1643/1679 行） | 已实测：退订不会发生，事件订阅悄悄泄漏 |
| 权限策略是否展示 | `showPermissionPolicy` getter（631 行） | UI 状态可能显示错误 |
| Guardian/权限交互 | `_provider?.bundle.interactions`（2237/2280 行） | 交互操作可能拿不到 port，静默失败 |
| Plan 审批 | `_provider?.bundle.planApproval`（2310 行） | 同上 |
| 还有几处未逐条验证 | 401/1257/1997/3457 行 | 未逐条追踪，不排除还有更多 |

而 `switchThread`（04 例子里明确点名的"catalog"操作）**现状代码本身就会**在
读完历史后显式调用 `_replaceProviderEventSubscription`，建立一条真实的事件订阅
——这与 04 §0.4 表格写的"`readThreadHistory` 不建立订阅"不一致：`readThreadHistory`
这个 RPC 本身确实不建立订阅，但 VM 层面 `switchThread` 的现状实现在读完历史后
主动订阅了该 thread 的事件，让用户还没发消息就能看到 thread 的实时状态变化。
这是现状代码的既有行为，有测试覆盖（"switchThread does not wait for stale event
subscription cancellation" 等），不能删。

也就是说 `_provider` 承担的不是"session 独占"的语义，而是"VM 当前正在实时监听

## S5 · 完成：pin 与 lastActiveAt，只记录不消费

### `touch()` 落在哪：`acquire()` 自动 touch，不需要在每个业务调用点重复调用

04 原文说"每次 provider 操作 touch()"，字面读容易理解成要在 `sendMessage`/
`switchThread`/`loadModels` 等每一个业务方法里插一行 `touch()`。实际选择是把
它落在 registry 的 `_createLease`（`acquire()` 唯一的出口，不管是新建实例还是
复用已有实例都会经过这里）——因为**任何一次 provider 操作在能发起之前都必须先
`acquire()`**，在这一个位置 touch 就能覆盖所有调用方，不用在业务代码里到处插
桩。`AgentProviderRuntimeLease.touch()` 仍然单独暴露，留给以后需要更细粒度打点
的调用方，本步骤没有这样的调用方。

### `pin()` 精确设计：只在 turn 生命周期，不在别处

只有 [_ensureSessionProvider]（`sendMessage` 用的那条路径）会 pin；catalog 入口
（`_ensureCatalogProvider`，给 `loadModels`/`ensureSkillsCatalog`/`switchThread`
用）**完全不碰** `_turnPin`。理由和 S4 里 `_provider`/`_eventPipeline` 的教训
一样：如果 catalog 调用也去 pin/unpin，一次后台目录读取就可能在会话正在流式
输出时把 pin 提前释放掉——S6 接上回收器之后这会导致真实的"边输出边被回收"的
correctness bug，不只是记录不准。

### pin 释放的四个落点（对应三条终结路径 + 一条安全网）

`sendMessage` 里 `_turnPin ??= providerController.pinActiveProvider();` 紧跟在
`_ensureSessionProvider` 成功之后——早于 `_ensureSession`，因为万一 session 建立
失败，pin 已经拿到但还没有 `requestSession`，这个时序细节决定了下面第一条释放
点不能用 `requestSession != null` 做判断依据：

| # | 触发条件 | 释放点 | 覆盖的场景 |
|---|---|---|---|
| 1 | `isNewTurn && !modeRequestAccepted`（不要求 `requestSession != null`） | `sendMessage` 的 `finally` 块 | turn 从未被 server 接受：`_ensureSessionProvider`/`_ensureSession` 抛异常，或 `conversation.sendMessage(...)` 本身抛异常。这类失败根本不会有后续的 `turn/completed` 事件，必须在这里自己收 |
| 2 | `!isTurnRunning` | `AgentFinalizeTurnCompletedChange`（reducer 处理 `AgentTurnCompletedEvent`，覆盖 `completed`/`failed`/`interrupted` 三种 server 上报状态——见 `_turnCompleted` 对 `event.status` 的统一处理） | server 确认 turn 结束，不管是正常完成、失败还是用户 `cancelActiveTurn()` 之后 server 确认的取消 |
| 3 | `!isTurnRunning` | `AgentFinalizeInterruptedTurnChange`（`settleInterruptedTurn`：provider 事件流 `onDone`/连接断开触发） | 连接中断导致的中断收尾——和 #2 是两条不同代码路径，都要覆盖 |
| 4 | 无条件（`_releaseTurnPin()` 本身是安全空操作） | `dispose()` | 安全网：VM 在 turn 进行中被释放（用户关掉 Canvas），前三条正常路径都不会再触发 |

`cancelActiveTurn()` 本身**不**释放 pin——它只发 `cancelTurn` RPC，不直接结束
turn；真正的结束仍然是 #2（server 之后发一个 `status: interrupted` 的
`AgentTurnCompletedEvent` 确认）。这一点在新增测试里专门断言了
`cancelActiveTurn()` 之后、server 确认事件之前 pin 还没释放，确认释放确实是
挂在 server 确认这一步，不是提前在客户端发起取消时。

## S6 · 完成：接上回收器

### 计划之外的一处新增：registry 的 `snapshotEntries()`

04 §1 目标结构没有明确写出 `agent_provider_runtime_registry.dart` 在 S6 要变，
但"回收器命中即调 `registry.invalidateScope`"（§1 对
`agent_provider_idle_reaper.dart` 的描述）意味着回收器自己要能判断"哪些
scope 命中了空闲条件"——这需要读到每个 entry 的 `providerId`/`scope`/
`pinCount`/`lastActiveAt`，而这些字段在 `_AgentProviderRuntimeEntry` 里是私有
的。两个方案：(a) 把"扫描决策"逻辑整个塞进 registry 内部，回收器只是一层
定时器包装；(b) registry 只新增一个只读快照方法
（`List<AgentProviderRuntimeSnapshot> snapshotEntries()`），决策逻辑留在
回收器自己那边。

选了 (b)：更贴合 §0.1"回收器不发明新的失效语义，只决定何时对哪个 scope 调
`invalidateScope`"——决策权应该在回收器，registry 只负责暴露只读状态和执行
失效。`AgentProviderRuntimeSnapshot` 是纯数据（providerId/scope/pinCount/
lastActiveAt），不携带 provider 引用，不违反"回收器不该拿到 provider 去做业务
操作"这条边界。这个新增没有改动任何既有断言，是这一步"做什么"里"回收器命中
即调 invalidateScope"这句话在代码层面必然要求的最小配套，不算顺手改无关代码。

### reaper 的启动/停止只挂在两个"真所有者"上，判据用现成的 `_ownsXxxRegistry` 标记

`app.dart` 和 `ide_shell_controller.dart` 都已经有一个
`_ownsAgentProviderRuntimeRegistry` 标记——true 表示这个组合根自己
`AgentProviderRuntimeRegistry(...)` 建的 registry（会在自己 `dispose()` 里
`close()` 它），false 表示 registry 是外部注入的（调用方——通常是测试——保留
生命周期控制权）。回收器直接复用这个既有判据：`_ownsAgentProviderRuntimeRegistry`
为真时才 `AgentProviderIdleReaper(registry: ...)..start()`，`dispose()` 里
`_agentProviderIdleReaper?.stop()` 紧挨着 `registry.close()` 一起调。这样：

- 注入 registry 的测试/宿主不会意外多出一个在背景里跑的 Timer——它们如果需要
  回收行为，会自己接一个。
- 两个 management repository（`codex_agent_management_repository.dart`、
  `grok_agent_management_repository.dart`）和
  `active_agent_provider_controller.dart` 默认构造里的自建临时 registry
  fallback（`ownsRegistry` 分支，S8 要删的那批）**没有被这一步碰**——它们不是
  "唯一真所有者"，不启动回收器，符合"不在任何 fallback 自建分支里起 Timer"。

`AgentProviderRuntimeRegistry` 的 `timerFactory` 接缝从 S1 开出来后一直没有

### 唯一的真实风险点：`ActiveAgentProviderController.dispose()` 不再关闭它拿到的 registry

旧行为：`_ownsRuntimeRegistry` 为真时（也就是测试没传 `runtimeRegistry`），
`controller.dispose()` 会顺手 `registry.close()`，间接把 provider 也 dispose 了。
改造后 `runtimeRegistry` 永远是外部注入的，`dispose()` **绝不能**再关它——不然
一个 controller 消亡就会拖垮所有其它借用同一个 registry 的消费者，这在会话级
改造后是真实的正确性问题（不只是这一步的技术债）。

动手前逐个排查了所有会在 `controller.dispose()` 之后紧接着断言
`provider.disposeCount`/使用 registry 状态的测试用例（`active_agent_provider_controller_test.dart` 的
"does not dispose the active provider..."、"moves active provider to an enabled
fallback..."、"rejects and disposes a provider with the wrong identity" 三条），
确认它们断言的 dispose 行为全部来自**别的机制**（`setProviderEnabled` 触发的
`registry.invalidateProvider`、`acquire()` 内部的身份错配立即销毁），跟"registry
是谁关的"完全无关，不受这次改动影响——因此新增的 `addTearDown(registry.close)`
