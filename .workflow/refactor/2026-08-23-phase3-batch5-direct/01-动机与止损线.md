# 第 5 批直接迁移：动机与止损线

## 痛点

desktop attention 仍把状态转移与系统副作用放在一个 controller；conversation
workspace 仍由 Shell 与 application→presentation 的 controller 共同持有 entry、选择、
project home 和持久化映射，并保留 Phase 2 的 ViewModel 直连回退。

## 不迁移的代价

- `IdeShellController` 无法退出 feature 状态 owner；
- application 的 presentation 反向依赖和四个 Flutter import 燃尽项无法清零；
- desktop notification、workspace 与 composer 无法获得稳定的 MVI state/selector；
- 第 6 批插件化会继续背负 conversation compatibility 接缝。

## 止损线

- 任何既有 Provider wire、Binding identity、审批语义或持久化 schema 必须改变；
- 流式事件开始进入 Riverpod state，或 Shell rebuild 基线明显恶化；
- 无法维持两个常驻 conversation 的 Binding、草稿与滚动状态隔离；
- 必须通过双写或恢复旧 ViewModel 直连才能通过验收。

命中任一项即停止并回滚本批，不以兼容 flag 掩盖问题。

## 范围边界

仅迁 desktop attention、conversation workspace 外壳、conversation composer 的
mode/model/skills owner，以及 Phase 2 fallback。Provider 协议、event pipeline、
TimelineStore、四种审批模型、IDE Session schema、页面视觉和第 6 批插件目录均不改。
