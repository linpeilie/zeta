### 12. 守卫里发现的一个真问题：正则被我自己的工具改坏了

给守卫加"UI 层不得构造 Repository"断言后，mutation check **没能让它变红**。查下去发现
守卫源码里那条正则是：

```
RegExp(r'<0x08>[A-Z]\w*Repository\(')
```

开头是一个**真实的退格控制字符 0x08**，不是两个字符 `\` + `b`。原因是我用
`python - <<'PY'` 打补丁时，`\b` 在非 raw 的 python 字符串里被解释成了退格符
（同一批 `\w` 触发了 `SyntaxWarning: invalid escape sequence`，当时没在意）。

**后果**：这条守卫看起来完全正常、测试也是绿的，但它**永远不可能匹配任何东西**。
如果没做 mutation check，它会作为"零容忍守卫"一直挂在仓库里，一行都保护不了。

修法：改成与 `06-等价性验收` 用的 `grep -rEn 'Repository\('` **同一口径**的朴素
`line.contains('Repository(')`——守卫和验收检查用同一个判据，就不会各说各话。
同时全库扫了一遍控制字符（`grep -rlP '[\x00-\x08\x0b\x0c\x0e-\x1f]' lib test tool`），
确认没有第二处。

### 13. 排查过程中的两个环境坑（会误导判断，记下来）

1. **`python3` 在本机是 Windows Store 的占位 stub**（`WindowsApps/python3`），
   执行任何脚本都**静默成功、什么都不做**。我用它跑 mutation 时 `grep -c` 显示
   探针为 0，却没有任何报错，一度让我以为"守卫没抓到"。**本仓库的脚本一律用

2. `python -c "...\n..."` 在双引号 shell 串里 `\n` 会被吃掉导致语法错误

## P4-4：Conversation 切片组合去 ViewModel 耦合（2026-08-24）

### 28. 先纠正一个定性：这层不是一比一转发

P4-3b 的 adapter 是纯转发，删掉即可。**`AgentConversationSliceBinding` 不是**——
它含有三处承重逻辑，删不掉，只能搬：

1. **帧预算合并**：五个 region 同帧变化只产生**一次** publish（Phase 0 要求），
   带 `flushCount` 供帧预算回归断言；
2. **两阶段作用域校验**：命令执行前 `matchesForExecution`、结果回写前
   `matchesForCommit`，防止换代后的迟到结果写进当前切片；
3. **outcome 翻译**：`forkCurrentThread()` 用 `null` 表示失败，必须显式翻译，
   不能让 Future 正常结束冒充成功。

所以本批的实质**不是删除，而是解耦**：让这层不再持有整个 ViewModel。

### 29. 做法：两个窄端口

| `AgentConversationCommandPort` | 23 个命令方法（5 个 toggle + dismiss + 17 个返回 `AgentCommandOutcome` / `AgentSession?` 的命令） |

`AgentConversationViewModel` 声明 `implements` 这两个端口——**一行实现代码都没写**，
它本来就有这些成员，签名完全对齐（analyze 零缺失成员即是证明）。这也印证了
计划书"保留 ViewModel 作为中立命令/typed-listenable facade"的判断。

`AgentConversationSliceBinding` → `AgentConversationSliceComposition`，
`git mv` 到 `lib/src/app/conversation_slice/`，构造参数从 `viewModel` 变成
`regions` + `commands`。内部 `_AgentConversationViewModelEffectRunner` 相应改名为
`_AgentConversationCommandEffectRunner`，只依赖命令端口。

**合并逻辑、两阶段校验、outcome 翻译的代码一行未改**，只换了它们调用的接收者类型。

### 38. ~~P4-5b 的另一半没有做~~ —— **这一节的结论是错的，见 §40**

### 40. 更正 §38：那个"前置阻塞"不存在，P4-5b 已完整完成

§38 断言「Shell 有 19 处 workflow 编排通知不对应任何 slice，所以 IdeHome 不能改定向
订阅」。**这个结论是错的**，我当时只看了"Shell 内部订阅了 4 个源"就下判断，
没有逐个追 `_notifyStateChanged()` 到底在通知什么。逐个查完之后：

| 我当时以为是 Shell 自有状态的 | 实际归属 |
|---|---|
| 项目打开进度 | `workspaceSliceStore.state.isLoadingProject`（**slice 里**） |
| 会话恢复阶段 | `_releaseInitialRestoreWait()` → `ideSessionOperations.releaseInitialRestoreWait()` → reducer 置 `initialRestoreCompleted` → **slice 会通知** |
| `_homeRefreshToken` | Shell **内部**的 stale guard，IdeHome 根本不读它 |
| 命令级错误 | 走 `_statusReporter`（toast 端口），不经状态通知 |

再核 IdeHome 侧：它从 Shell 读的每一项——`workbenchLayout` /
`initialRestoreCompleted`（IDE Session）、`projects` / `activeProjectPath`（Workspace）、
`selectedEntry` / `projectHomeActive`（Conversation Workspace）——**全部是这三个 slice
的投影**；三个副作用（首页预热 / Attention 可见性 / 面板宽度）的依赖也全在这三个里。

其余对 `_shellController` 的引用经核实都不是重建依赖：
`projectThreadsSliceStore` / `workspaceSliceStore` 的四处要么在**明确不注册 listener**
的诊断快照里，要么是往 `ProviderScope` 传 store **实例**（实例不变）；
`agentProviderController` 早有自己的 `subscribe`。

**因此改动是安全且可证的**，已完成：

- `IdeHome` 的 `_shellController.addListener(_handleShellChanged)` 换成三个定向订阅；
- `_handleShellChanged` 拆成 `_handleIdeSessionChanged` / `_handleWorkspaceChanged` /
  `_handleConversationWorkspaceChanged`，每个只做该 store 影响的那几件事；
- `IdeSessionSliceOperations` 补 `subscribe(listener) → unsubscribe`（此前接口上没有
  任何订阅 API，只有具体 store 有），与 Workspace / ProviderSettings 的既有形状一致。

**教训**：§38 是这次 Phase 4 里我犯的最实质的一个错误——它差点让一条本可完成的
关批标准被写成"有前置阻塞、需另立改动"。**根因是从"Shell 订阅了什么"倒推
"Shell 通知了什么"，这两件事根本不等价。** 下判断前应当逐个追调用点，
而不是看一眼订阅列表就外推。
