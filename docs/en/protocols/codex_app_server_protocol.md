## 1. Purpose

Zeta's default agent provider (`CodexAppServerAgentProvider`) adapts to the JSON-RPC protocol of the Codex
CLI's `app-server`. The protocol evolves with the CLI, and field names, notification methods and request
schemas can change silently.

This repository pins the adaptation baseline with a **pinned schema snapshot**: when upgrading Codex, diff
the schema first, then change the adapter, avoiding the drift of "the local CLI upgraded but the code still
parses the old protocol".

> Note: this snapshot was taken directly from the pre-generated stable JSON Schema in the
> `codex-rust-v0.144.5` release source. Experimental APIs are excluded, as is the v2 aggregate file whose
> key ordering is unstable.

The runtime still resolves `codex` via PATH / install directory. **The runtime CLI version need not match
the pin exactly**, but before upgrading you should diff the schema and confirm the adapter still covers the
key methods.

Plan-mode catalogs, `turn/start.collaborationMode`, `thread/settings/updated`, `item/plan/delta` and
`item/tool/requestUserInput` are experimental surface; `turn/plan/updated` is a pre-existing notification.
The stable snapshot and experimental verification use two baselines:

| Baseline | Version / mode | Use |
| --- | --- | --- |
| Repository contract | `0.144.5` stable | code review, stable-method diffs; excludes experimental fields |
| Real-run verification | the experimental schema generated by the actual CLI + smoke | runtime plan capability probing; records the actual version and result |

A locally generated experimental schema from a version below the pin counts only as compatibility evidence
and **must not** overwrite the stable pin in `third_party/codex_app_server_schema`.

## 3. Snapshot contents

The generated output mainly includes:

- Four union types: `ClientRequest.json`, `ClientNotification.json`, `ServerNotification.json`,
  `ServerRequest.json`
- An aggregate file: `codex_app_server_protocol.schemas.json`
- Per-method schemas: the `v1/` and `v2/` directories
- Metadata: `PINNED_VERSION`, `GENERATED.json`

> Note: the CLI-exported `codex_app_server_protocol.v2.schemas.json` has unstable `definitions` key
> ordering, so the script excludes it deliberately; the equivalent information is stored per method in
> `v2/*.json`.

Never hand-edit the JSON; always overwrite via the generation script.

## 4. Regenerating

### macOS / Linux / Git Bash

```sh
./tool/gen_codex_schema.sh
```

### Windows PowerShell

```powershell
./tool/gen_codex_schema.ps1
```

Common options:

| Option | Effect |
| --- | --- |
| `--diff` / `-Diff` | only compares the current CLI export with the committed snapshot; writes nothing |
| `--force` / `-Force` | allows overwriting the snapshot when the CLI version differs from `PINNED_VERSION` |
| `--experimental` / `-Experimental` | includes experimental methods/fields |
| `CODEX_BIN` / `-CodexBin` | specifies the Codex executable path |

On Windows, if the global npm `codex` on PATH is stale, the script first tries
`%LOCALAPPDATA%\Programs\OpenAI\Codex\bin\codex.exe`; you can also pass it explicitly:

```powershell
./tool/gen_codex_schema.ps1 -CodexBin "$env:LOCALAPPDATA\Programs\OpenAI\Codex\bin\codex.exe"
```

## 5. Recommended upgrade process

1. Install the target Codex CLI version and confirm with `codex --version`.
2. Run the generation script (add `--force` / `-Force` when the version changes).
3. Run `git diff --stat third_party/codex_app_server_schema`, focusing on:
   - methods added to or removed from the four union types
   - params / notification field changes on already-adapted methods
   - server request/response schemas (to avoid invalid replies)
4. Update the `packages/codex_app_server_client/` adapter layer and its tests according to the diff.
5. Update the pinned version note in this document.
6. Smoke against a real `codex app-server --stdio`:
   - core path: `python tool/smoke_codex_app_server.py --expected-version 0.144.5`
   - experimental plan path: `python tool/smoke_codex_plan_mode.py --expected-version 0.144.5`
7. If the local version is not the target version, you may omit `--expected-version` for a compatibility
   diagnosis, but the result does not substitute for the target version's release gate and must not be used
   to overwrite the stable schema.

## 6. 0.142.5 → 0.144.5 adaptation conclusions

- `turn/steer` must send the active turn's `expectedTurnId` and must not send `cwd`.
- `thread/read` sends only `threadId` and `includeTurns`, no longer carrying `itemsView`.
- `thread/rollback` is no longer a Zeta product capability; edit-and-retry creates a new branch via
  `thread/fork.lastTurnId`.
- `on-failure` is no longer emitted; persisted legacy values migrate to `on-request`.
- Permission profiles declare stable discovery only and promise no experimental runtime selection.
- The `initialize` return maps to the runtime version, compatibility status and dynamic capabilities;
  unknown or older versions degrade conservatively.
- `account/rateLimits/read.rateLimitResetCredits.availableCount` maps to the available reset-credit count in
  the neutral quota snapshot. That total may exceed the length of the `credits` detail list, so statistics
  UI must not infer it from the detail count; it is currently read-only display and does not wire up
  `account/rateLimitResetCredit/consume`.

## 7. Relationship to the adapter layer

- The UI, Blocs and Repositories consume only neutral models such as `AgentEvent` from
  `agent_provider_contracts`; they never read the schema JSON directly.
- The schema snapshot is the **human- and CI-diffable source of protocol truth**, not a runtime dependency.
- Fine-grained logs and diagnostic counters for unmatched notifications (A7) exist to discover methods
  outside the pin; once adaptation is confirmed necessary, the snapshot and mapper are updated together.

## 8. Experimental plan protocol and degradation

Plan capability can only be negotiated through `experimentalApi: true` in the single `initialize` call.
After the handshake, an unpaginated `collaborationMode/list` with empty params is called, and the selector is
exposed to the UI only when the catalog contains at least Default and Plan. The explicit mode is sent with
every new `turn/start`; when `collaborationMode.settings` is sent, conflicting top-level model / effort are
not. Leaving sticky plan mode requires explicitly sending Default — omitting the field is not a substitute.

Degradation rules:

- If `initialize` rejects the experimental capability, the catalog method returns method-not-found, the
  response is corrupt, or built-in modes are missing: this runtime generation treats the mode port as
  unavailable, hides the selector and keeps the existing Default send path; ordinary conversation, model
  selection and history reads keep working.
- Transport and timeout failures are temporary unavailability that the user can retry; the provider re-probes
  after a provider or process rebuild, and an old generation's failure is never recorded as a permanent
  capability.
- Once in plan mode but before `turn/plan/updated` arrives, the timeline may still use `item/plan/delta` /
  completed plan items; structured steps must never be fabricated.
- Collaboration mode is sticky state in Zeta's local thread snapshot. When `thread/read` does not replay that
  setting, the local snapshot is restored first on restart, then converged to the server-confirmed state by
  the next `turn/start` and `thread/settings/updated`.

### 8.1 User question response semantics

`item/tool/requestUserInput` is an independent user-question request, not a permission approval:

- The data layer maps it to `AgentQuestionRequest` via a question mapper and stores it in a separate pending
  question registry; it must never go into the approval mapper or the permission registry.
- The client response is fixed as `{answers: {questionId: {answers: [...]}}}`; empty `answers` means Skip.
  This protocol has no approve, deny or cancel-turn response variant.
- `serverRequest/resolved` and connection close must clear question state through the registry that owns the
  request, so a request already resolved by another client is not written back.
- Plan approval continues to use the separate `AgentPlanApprovalRequest/Decision` and never converts to or
  from user questions.

### 8.2 Local execution handoff after a plan completes

The current app-server protocol has no server request for "ask the user whether to execute after a plan turn
completes". Zeta creates a local `AgentPlanExecutionRequest` from the successful plan turn and the normalized
plan content; that request never enters JSON-RPC, JSONL history or the provider's pending registry. After
migration, the handoff decision belongs to `AgentConversationBloc` (see
[conversation state design §6.4](../architecture/agent_conversation_state_design.md)), while plan content
normalization stays in `agent_conversation_repository`.

- Run plan: switch the next turn's draft to Default first, then send the local handoff prompt through a
  normal `turn/start`.
- Keep planning: clear the handoff card, stay in plan mode and return to the composer; no RPC occurs.
- Dismiss: clears the local request only; no accepted/rejected/cancelled is sent to the server.
- Command, file and network permissions are still handled one by one through existing approval requests;
  Run plan does not constitute pre-authorization.
- `AgentPlanApprovalRequest` still represents only an independent plan approval initiated by the provider and
  must not be used for the local handoff.

### 8.4 Skills

Zeta maps Codex skills to neutral domain models and composer tokens:

| Codex | Zeta |
| --- | --- |
| `skills/list` | `AgentSkillsPort.listSkills` → `AgentSkillsCatalog` |
| `skills/changed` | `AgentSkillsPort.skillsChanged` (invalidation signal) |
| `UserInput` `{ type: "skill", name, path }` | `AgentUserInput.skill` |
| text marker `$<name>` | composer chip / serialized text; Codex user messages usually render as `[$name](path)`, flattened to `$name` in history |

When sending a turn, both the `$name` text and the structured `skill` item are included (Codex's recommended
path). `skills/extraRoots/set` is not wired up yet.

### 8.5 File-change evidence

Codex file changes arrive over four paths that never impersonate one another: structured app-server tools,
local JSONL `patch_apply_end`, live turn fallback, and command-only. `CodexFileChangeTracker` handles
identity, cumulative snapshots and priority inside `codex_app_server_client`;
`agent_conversation_repository` and the UI never read app-server or session JSONL raw fields.

| App-server input | Zeta mapping |
| --- | --- |
| `fileChange` ThreadItem, `item/fileChange/patchUpdated.changes[]` | `path`, `kind.type`, optional `move_path` and `diff` → a replayable tool-scoped `AgentFileChangeSnapshot` + unified patch evidence |
| local session JSONL `patch_apply_end.changes` | the map key is the provider's explicit path; `update.unified_diff` → unified patch, `add.content` → written content, `delete` keeps only an action summary when no suitable evidence exists, a non-empty `move_path` → moved; the result is a replayable tool snapshot |
| `item/fileChange/outputDelta` or missing valid `changes` | keeps ordinary tool progress only; an existing valid snapshot may still be carried, but evidence is never manufactured from text |
| `turn/diff/updated` | split in the Codex data layer into per-file typed `liveOnly` turn snapshots, used only as a live fallback when tool evidence is missing |
| `commandExecution` | an ordinary execute tool; the command, `commandActions`, approval params and workspace results are not parsed, and no file-change snapshot is produced |

When a turn already has a structured tool snapshot, a later turn aggregate is suppressed; if the turn fallback
became visible first, a later tool snapshot first emits an empty turn snapshot to clear the fallback. The
Repository and UI never deduplicate by path across owners, and never infer file identity or action from a
unified patch header. Structured `fileChange` data recoverable by `thread/read` is rebuilt with a separate
history tracker. When local JSONL takes priority, the call id of `patch_apply_end` is an independent
Apply-patch owner and need not match the outer `custom_tool_call(name: exec)`. Missing or corrupt `changes`
degrade to an ordinary tool without parsing exec input, stdout or raw patch evidence. The turn fallback is
explicitly not evidence of history completeness.

If the current environment only ever observes `commandExecution`, the correct degradation is to keep the
command card and show no file-change card. Schema fixtures prove only the structured compatibility path and
cannot stand in for a real runtime measurement. All malformed/ignored diagnostics record only
method/type/reason/count — never commands, paths, patches, raw payloads or raw stderr.
