# Codex app-server Protocol Pin

Documentation and paths checked: 2026-09-07. Protocol sample dates are recorded below; no real CLI was rerun for this edit.

> Translated from [the Chinese original](../../zh/protocols/codex_app_server_protocol.md), which is the source of truth if the two diverge.

## 1. Purpose

Zeta's default agent provider (`CodexAppServerAgentProvider`) is written against the JSON-RPC protocol of the Codex CLI `app-server`. That protocol evolves with the CLI: field names, notification methods and request schemas can all change silently.

This repository pins the adaptation baseline with a **pinned schema snapshot**. When upgrading Codex, diff the schema first and only then change the adapter — this prevents the drift where the local CLI has been upgraded while the code still parses the old protocol.

## 2. Currently pinned version

| Item | Value |
| --- | --- |
| Pinned Codex CLI | **0.144.5** (see `third_party/codex_app_server_schema/PINNED_VERSION`) |
| Export command | `codex app-server generate-json-schema --out <dir>` |
| Schema snapshot directory | [`third_party/codex_app_server_schema/`](../../../third_party/codex_app_server_schema) |
| Generator scripts | [`tool/gen_codex_schema.sh`](../../../tool/gen_codex_schema.sh), [`tool/gen_codex_schema.ps1`](../../../tool/gen_codex_schema.ps1) |

> Note: this snapshot was taken directly from the generated stable JSON Schema in the `codex-rust-v0.144.5` release source. Experimental APIs are not included, and the v2 aggregate files with unstable key ordering remain excluded.

At runtime `codex` is still resolved through `PATH` or the install directory. **The runtime CLI version does not have to match the pin exactly**, but you should run a schema diff before upgrading to confirm the adapter still covers the methods that matter.

Plan mode catalogs, `turn/start.collaborationMode`, `thread/settings/updated`, `item/plan/delta` and `item/tool/requestUserInput` are part of the experimental surface; `turn/plan/updated` is a pre-existing notification. Stable snapshots and experimental verification use two separate baselines:

| Baseline | Version / mode | Used for |
| --- | --- | --- |
| Repository contract | `0.144.5` stable | Code review and diffing stable methods; contains no experimental fields |
| Real-run verification | Experimental schema generated by the actual CLI, plus smoke tests | Probing plan capability at runtime; records the actual version and result |

An experimental schema generated locally from a CLI older than the pin counts only as compatibility evidence. It **must not** overwrite the stable pin in `third_party/codex_app_server_schema`.

## 3. What the snapshot contains

The generated output is mainly:

- Four union types: `ClientRequest.json`, `ClientNotification.json`, `ServerNotification.json`, `ServerRequest.json`
- An aggregate file: `codex_app_server_protocol.schemas.json`
- Per-method schemas under `v1/` and `v2/`
- Metadata: `PINNED_VERSION`, `GENERATED.json`

> Note: the `definitions` key order in the CLI-exported `codex_app_server_protocol.v2.schemas.json` is unstable, so the script excludes it deliberately. The same information is stored per method under `v2/*.json`.

Never hand-edit the JSON; always regenerate through the scripts.

## 4. Regenerating

### macOS / Linux / Git Bash

```sh
./tool/gen_codex_schema.sh
```

### Windows PowerShell

```powershell
./tool/gen_codex_schema.ps1
```

Common options:

| Option | Effect |
| --- | --- |
| `--diff` / `-Diff` | Only compare the current CLI export against the committed snapshot; write nothing |
| `--force` / `-Force` | Allow overwriting the snapshot when the CLI version differs from `PINNED_VERSION` |
| `--experimental` / `-Experimental` | Include experimental methods and fields |
| `CODEX_BIN` / `-CodexBin` | Point at a specific Codex executable |

On Windows, if the globally installed npm `codex` on `PATH` is outdated, the script prefers `%LOCALAPPDATA%\Programs\OpenAI\Codex\bin\codex.exe`. You can also pass it explicitly:

```powershell
./tool/gen_codex_schema.ps1 -CodexBin "$env:LOCALAPPDATA\Programs\OpenAI\Codex\bin\codex.exe"
```

## 5. Recommended upgrade process

1. Install the target Codex CLI version and confirm with `codex --version`.
2. Run the generator script (add `--force` / `-Force` when the version changed).
3. Run `git diff --stat third_party/codex_app_server_schema` and focus on:
   - Methods added to or removed from the four union types
   - Params / notification field changes on methods you already adapt
   - Server request response schemas, to avoid sending invalid replies
4. Update the adapter and tests under `packages/zeta_agent_provider_codex` according to the diff.
5. Update the Chinese and English protocol version notes and record actual verification results in `.workflow/`.
6. Smoke-test against a real `codex app-server` (stdio is the default; no extra flag is needed):
   - Core path: `python tool/smoke_codex_app_server.py --expected-version 0.144.5`
   - Experimental plan path: `python tool/smoke_codex_plan_mode.py --expected-version 0.144.5`
7. If your local version is not the target version, you may omit `--expected-version` for a compatibility diagnosis — but that result does not substitute for the target version's release gate, and must not be used to overwrite the stable schema.

## 6. Adaptation conclusions, 0.142.5 → 0.144.5

- `turn/steer` must send the active turn's `expectedTurnId` and must not send `cwd`.
- `thread/read` sends only `threadId` and `includeTurns`; it no longer carries `itemsView`.
- `thread/rollback` is no longer a Zeta product capability. Edit-and-retry creates a new branch through `thread/fork.lastTurnId`.
- `on-failure` is no longer emitted; the alias is normalised to `on-request` on protocol input.
- Permission profiles declare discovery as a stable capability only; experimental runtime selection is not promised.
- The `initialize` response is mapped to runtime version, compatibility status and dynamic capabilities. Unknown or older versions degrade conservatively.
- `account/rateLimits/read.rateLimitResetCredits.availableCount` maps to the available reset-credit count in the neutral quota snapshot. That total may exceed the length of the `credits` breakdown, so the statistics UI must not derive it from the breakdown length. It is currently read-only display and is not wired to `account/rateLimitResetCredit/consume`.

## 7. Relationship to the adapter

- UI and domain code consume only neutral models such as `AgentEvent`; they never read the schema JSON.
- The schema snapshot is the **diffable source of protocol truth for humans and CI**, not a runtime dependency.
- Fine-grained logs and diagnostic counters for unmatched notifications (A7) exist to surface methods outside the pin. Once one is confirmed to need adapting, update the snapshot and the mapper together.

## 8. Plan experimental protocol and degradation

Plan capability can only be negotiated through `experimentalApi: true` in the single `initialize` call. After the handshake, Zeta calls `collaborationMode/list` with no pagination and empty parameters, and only exposes the selector to the UI when the catalog contains at least Default and Plan. The explicit mode is sent with every new `turn/start`. When `collaborationMode.settings` is sent, the conflicting top-level model / effort fields are not. Leaving sticky Plan requires explicitly sending Default; omitting the field is not a substitute.

Degradation rules:

- If `initialize` rejects the experimental capability, the catalog method returns method-not-found, the response is corrupt, or built-in modes are missing: the mode port is treated as unavailable for this runtime generation, the selector is hidden, and the existing Default send path is used. Ordinary conversation, model selection and history reading remain available.
- Transport and timeout failures are temporary and the user can retry. The probe runs again after the provider or process is rebuilt; a failure from an old generation is never recorded as a permanent capability.
- If Plan has been entered but no `turn/plan/updated` arrives, the timeline may still use `item/plan/delta` and completed plan items. Structured steps must never be fabricated.
- Collaboration mode is sticky state in Zeta's local thread snapshot. When `thread/read` does not replay the setting, the local snapshot is restored first after a restart, and the next `turn/start` plus `thread/settings/updated` converge on the server-confirmed state.

### 8.1 User question response semantics

`item/tool/requestUserInput` is a standalone user question request, not a permission approval:

- The data layer maps it to an `AgentQuestionRequest` through the question mapper and stores it in a separate pending question registry. It must never go into the approval mapper or the permission registry.
- The client response is always `{answers: {questionId: {answers: [...]}}}`; an empty `answers` means Skip. The protocol has no approve, deny or cancel-turn response variant.
- `serverRequest/resolved` and connection close must clear question state from the registry the request belongs to, so that a request already resolved by another client is not written back.
- Plan approval continues to use the separate `AgentPlanApprovalRequest` / `Decision` and never converts to or from a user question.

### 8.2 Local execution handoff after a plan completes

The current app-server protocol has no server request that asks the user to confirm execution after a plan turn completes. Zeta creates a local `AgentPlanExecutionRequest` in the application layer, from the successful plan turn and the normalised plan content. That request never enters JSON-RPC, the JSONL history or the provider pending registry.

- **Run plan**: switch the next turn's draft to Default first, then send the local handoff prompt through a normal `turn/start`.
- **Keep planning**: clear the handoff card, stay in Plan, and return to the composer. No RPC is produced.
- **Dismiss**: clear the local request only. Nothing accepted / rejected / cancelled is sent to the server.
- Command, file and network permissions are still handled one at a time by the existing approval requests. Run plan is not a pre-authorisation.
- `AgentPlanApprovalRequest` still represents only a standalone plan approval initiated by the provider, and cannot be used for the local handoff.

### 8.4 Skills

Zeta maps Codex Skills to neutral domain models and composer tokens:

| Codex | Zeta |
| --- | --- |
| `skills/list` | `AgentSkillsPort.listSkills` → `AgentSkillsCatalog` |
| `skills/changed` | `AgentSkillsPort.skillsChanged` (invalidation signal) |
| `UserInput` `{ type: "skill", name, path }` | `AgentUserInput.skill` |
| Text marker `$<name>` | Composer chip / serialised text. Codex user messages often render as `[$name](path)`; history flattens to `$name` |

When sending a turn, both the text `$name` and the structured `skill` item are included (the path Codex recommends). `skills/extraRoots/set` is not wired up yet.

### 8.5 File change evidence

Codex file changes arrive through four paths that must never impersonate each other: structured app-server tools, local JSONL `patch_apply_end`, live turn fallback, and command-only. `CodexFileChangeTracker` resolves identity, cumulative snapshots and priority in the data layer. The shared timeline store and the UI never read raw app-server or session JSONL fields.

| App-server input | Zeta mapping |
| --- | --- |
| `fileChange` ThreadItem, `item/fileChange/patchUpdated.changes[]` | `path`, `kind.type`, optional `move_path` and `diff` → replayable tool-scoped `AgentFileChangeSnapshot` plus unified patch evidence |
| Local session JSONL `patch_apply_end.changes` | The map key is the provider-declared path. `update.unified_diff` → unified patch; `add.content` → written content; `delete` with no suitable evidence keeps only an action summary; a non-empty `move_path` → moved. The result is a replayable tool snapshot |
| `item/fileChange/outputDelta`, or missing valid `changes` | Keep ordinary tool progress only. An existing valid snapshot may continue to be carried, but evidence is never manufactured from text |
| `turn/diff/updated` | Split in the Codex data layer into per-file typed `liveOnly` turn snapshots, used only as a live fallback when tool evidence is missing |
| `commandExecution` | An ordinary execute tool. The command, `commandActions`, approval parameters and workspace results are not parsed, and no file change snapshot is produced |

When a structured tool snapshot already exists for a turn, a later turn aggregate is suppressed. If the turn fallback became visible first, a later tool snapshot emits an empty turn snapshot to clear the fallback. The store and UI never deduplicate across owners by path, and never infer file identity or action from a unified patch header. Structured `fileChange` entries recoverable through `thread/read` are rebuilt with a separate history tracker. When local JSONL takes priority, the call id of `patch_apply_end` acts as an independent "apply patch" owner and need not match the enclosing `custom_tool_call(name: exec)`. Missing or corrupt `changes` degrade to an ordinary tool; exec input, stdout and raw payloads are never parsed to fill the gap. Turn fallback is explicitly not evidence of history completeness.

If an environment only ever produces `commandExecution`, the correct degradation is to keep the command card and show no file change card. Schema fixtures prove the structured compatibility path only and cannot stand in for a real runtime observation. All malformed/ignored diagnostics record method, type, reason and count only — never commands, paths, patches, raw payloads or raw stderr.
