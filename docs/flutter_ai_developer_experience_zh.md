# Flutter AI 开发体验实践指南

来源：[Flutter Docs - Developer experience](https://docs.flutter.dev/ai/best-practices/developer-experience)  
整理日期：2026-07-03  
适用项目：`zeta`

## 核心观点

Flutter 官方建议把 AI 辅助开发从“随口让模型写代码”升级为“规格驱动开发”。好的流程不是直接要求 AI 一次性实现整个应用，而是先让 AI 和开发者一起明确需求、设计方案和任务拆分，再按小里程碑编码、验证、迭代。

这套流程可以概括为：

1. 计划：明确需求、规则、设计和任务。
2. 编码：按任务逐步实现可见功能。
3. 验证：运行、分析、测试、人工评审。
4. 迭代：把发现的问题交回给 AI 修正，再继续验证。

## 为什么不要直接跳到编码

AI 编码代理很容易根据模糊提示生成“看起来能跑”的代码，但它不一定符合你的产品目标、架构偏好、测试标准或维护习惯。官方教程强调，在写代码之前先沉淀几类文档：

- 需求文档：说明要做什么、面向谁、关键场景是什么。
- 项目规则：告诉 AI 每次工作都要遵守哪些工程原则。
- 设计文档：说明模块边界、数据流、UI 结构和技术取舍。
- 任务文档：把设计拆成用户可感知的小里程碑。

对于当前 `zeta` 项目，这些文档可以放在 `plans/` 或 `docs/` 下。建议后续功能开发时使用：

```text
plans/
  requirements.md
  design.md
  tasks.md
```

项目级 AI 规则已经放在根目录的 `AGENTS.md`，可以作为 AI 每次执行任务的默认约束。

## 阶段一：计划

计划阶段的目标是让 AI 在动手写代码前理解“你真正想要什么”。提示词里最好包含项目背景、目标用户、关键功能、约束条件，并明确要求 AI 先提问。

可用于当前项目的中文提示词模板：

```text
请在 plans/requirements.md 中创建当前功能的需求文档。

项目是一个 Flutter 应用，名称为 zeta。请基于下面的功能描述整理：

[在这里描述功能目标、用户场景、平台要求、已有约束]

开始写文档前，请先提出你需要澄清的问题。
```

需求文档完成后，再生成设计文档：

```text
请阅读 AGENTS.md 和 plans/requirements.md，在 plans/design.md 中整理设计方案。

设计方案需要说明：
- 用户流程
- 主要页面或组件
- 状态管理方式
- 数据结构
- 错误处理
- 测试策略

开始前请先提出需要澄清的问题。
```

最后把设计拆成任务：

```text
请阅读 AGENTS.md、plans/requirements.md 和 plans/design.md，在 plans/tasks.md 中创建任务拆分。

要求：
- 每个顶层任务都应该带来一个用户能看到或能验证的增量。
- 每个任务包含测试、验证和文档更新子任务。
- 优先从最小可运行功能开始。
```

## 阶段二：编码

当需求、设计和任务清楚后，再让 AI 编码。官方教程建议按任务文件逐步推进，而不是一次性要求完成所有功能。

推荐提示词：

```text
请阅读 plans/tasks.md，并实现第一个里程碑。

遵守 AGENTS.md 中的项目规则。实现后请运行格式化、静态分析和相关测试，并总结修改内容。
```

对 `zeta` 项目来说，默认工程约定是：

- 编辑 Dart 文件后运行 `dart format .`。
- 交付前运行 `flutter analyze`。
- 有测试或修改了行为时运行 `flutter test`。
- 优先使用 Flutter 内置能力，不要过早引入大型架构或第三方状态管理。
- 需要特定 Flutter/Dart 工作流时，使用 `.agents/skills` 中已安装的 skills。

## 阶段三：验证

编码完成后，不要只看 AI 的总结。验证阶段要从运行结果、代码质量和需求覆盖三个角度检查。

建议检查清单：

- `flutter analyze` 是否无错误、无警告。
- 应用是否能启动。
- 新功能是否符合需求文档。
- 用户可见流程是否完整。
- 测试是否通过。
- 代码是否符合 `AGENTS.md` 中的规则。
- 是否引入了不必要的依赖或复杂架构。
- UI 是否在桌面窗口和窄屏场景下都不会溢出。

如果验证过程中发现问题，把问题整理成明确反馈，再交给 AI 修正。

## 阶段四：迭代

迭代不是简单地说“修一下”，而是把验证结果转化成具体任务。官方教程还建议在代码初步完成后，使用一个新的 AI 上下文从架构角度重新审查变更，这样可以减少原编码上下文带来的路径依赖。

可用于当前项目的审查提示词：

```text
请查看当前代码变更，并根据 AGENTS.md 中的工程规则进行审查。

重点关注：
- 是否过度设计
- 是否存在重复逻辑
- 组件职责是否清晰
- 是否容易测试
- 是否符合 Flutter 最佳实践
- 是否有重要的缺失测试

请按严重程度列出需要改进的问题。
```

修复提示词：

```text
请根据上一轮审查意见修复问题。

保持改动范围尽量小。修复后运行格式化、静态分析和相关测试，并说明哪些问题已解决。
```

## 推荐的工程原则

官方教程中强调，项目规则文件应该保存团队希望 AI 长期遵守的原则。对 `zeta` 项目，建议沿用这些核心原则：

- DRY：避免重复逻辑，必要时提取共享函数或组件。
- 单一职责：一个类、函数、文件只承担清晰的职责。
- 关注点分离：UI、状态、业务逻辑和数据访问不要混在一起。
- 低耦合、高内聚：模块之间少知道彼此的内部细节。
- KISS：优先选择简单、直接、可维护的方案。
- YAGNI：不要为了未来可能发生的需求提前堆复杂度。
- 可观察、可测试：重要逻辑要便于验证，错误要可定位。

如果项目从样例逐渐变成真实产品，可以进一步加入测试驱动开发规则：先写测试，再实现功能；代码完成的标准是测试通过。

## 当前项目落地建议

`zeta` 现在还是一个非常轻量的 Flutter 项目，因此不需要一次性建立复杂目录结构。推荐按功能逐步演进：

```text
lib/
  main.dart
```

当第一个真实功能出现时，可以再拆分为：

```text
lib/
  main.dart
  app.dart
  features/
    example_feature/
      presentation/
      domain/
      data/
  core/
```

测试目录可以随功能增加：

```text
test/
  widget_test.dart
```

如果后续需要端到端验证，再添加：

```text
integration_test/
  app_test.dart
```

## 一次完整 AI 开发循环

可以把每个新功能按下面流程推进：

1. 写 `plans/requirements.md`，先让 AI 提问。
2. 写 `plans/design.md`，明确架构和测试策略。
3. 写 `plans/tasks.md`，拆成用户可见的小里程碑。
4. 让 AI 实现第一个里程碑。
5. 运行格式化、分析和测试。
6. 人工试用并检查需求覆盖。
7. 用新上下文做架构和代码审查。
8. 修复问题后进入下一个里程碑。

这套流程的价值在于让 AI 始终围绕明确规格工作，同时保留开发者的判断力和验收权。对 Flutter 项目来说，它尤其适合控制 UI 细节、平台差异、状态管理复杂度和测试覆盖。
