# 日常任务提示词

四类任务 × 三档复杂度。判档标准见 [README](README.md#三档复杂度)。

所有模板默认 AI 已读 `AGENTS.md`。收尾三件套（`dart format .` → `flutter analyze` → `flutter test` + 提交信息）是 AGENTS.md §0 的常驻要求，模板里只在需要强调时重复。

---

## 一、新增功能

### S · 小改

```text
在 <feature> 里新增 <一句话能力>。

先 codegraph explore "<相关符号>" 找到同类实现，照既有写法改，不要另起风格。
改完跑 format + analyze，补对应测试。
```

### M · 中改

```text
需求：<一句话>
验收：
- <可观察行为 1>
- <可观察行为 2>

动手前先给我改动清单：涉及哪些文件、各属哪一层、命中 AGENTS.md §2 路由表的哪几行。
我确认后再写代码。

实现时每层补测试（domain 单测 / controller 竞态与错误路径 / widget 行为）。
```

### L · 大改

```text
需求：<描述>

这次可能触及 <事件管线 / Provider 端口 / 持久化格式 / 权限语义>，属 L 档。
先不要写代码 —— 按 docs/prompts/workflow.md 的「阶段 2 方案设计」输出方案，
我确认后再进实现。
```

## 二、需求变更

改已有行为，风险主要在**旧调用方**和**已落盘的旧数据**。

### S · 小改

```text
把 <位置> 的 <旧行为> 改成 <新行为>。

改之前先 codegraph explore 确认还有哪些调用方依赖旧行为，一并列给我。
如果只有一处，直接改。
```

### M · 中改

```text
变更：<旧行为> → <新行为>
原因：<为什么>

先回答三个问题再动手：
1. 有哪些调用方依赖旧行为？
2. 有没有已落盘的旧数据受影响？需要宽容解码还是版本迁移？（G8）
3. 涉及的 capability 是否要跟着变？（G4）

然后改代码 + 改测试。行为变了，测试必须跟着变，不要为了让旧测试过而保留兼容分支。
```

### L · 大改

```text
契约变更：<描述>

这会改动 <domain 契约 / bundle 端口 / 持久化格式>。按 workflow.md 阶段 2 出方案，
重点说清楚：向后兼容策略（宽容解码 or 版本迁移）、旧字段的退场路径、
受影响的 Provider 各自要改什么。确认后再动手。
```

## 三、Bug 修复

### S · 小改

```text
现象：<操作> → 期望 <A>，实际 <B>
<报错或日志，已脱敏>

先定位根因再改，不要改症状。给我：根因一句话 + 最小修复 + 一个能复现该 bug 的回归测试。
```

### M · 中改

```text
现象：<操作路径> → 期望 <A>，实际 <B>
复现率：<必现 / 偶现，触发条件>
<脱敏日志>

流程：
1. 先写一个能稳定复现的失败测试，跑给我看它确实失败
2. 再定位根因，说明为什么会这样
3. 最后修复，同一个测试转绿

不要在没复现的情况下猜着改。
```

### L · 大改 —— 时序 / 竞态 / 流式类

这类 bug 是本项目最难的一类：状态在多个 generation、多个 session、多个进程之间流动，日志分散在三处。

```text
现象：<描述>，怀疑是时序或竞态问题
复现条件：<多会话 / 切换 thread / 快速重复操作 / 长回合>

先只读排查，不要改代码。按时间线交叉验证三处证据：
- Zeta：~/.zeta/logs/zeta-*.log（RPC 请求/响应 id 配对，看哪个请求没回）
- Provider CLI：<~/.grok/logs/unified.jsonl 或对应 CLI 日志>
- 会话目录：<对应 session 目录的 summary / events 尾部>

输出写入 .workflow/bugfix/<YYYY-MM-DD>-<现象简称>/01-时间线交叉验证.md：
事件时间线（对齐三处时间戳）+ 根因假设 + 支持该假设的证据 + 无法坐实的部分。

日志必须脱敏 —— 这个文件会入 git。写「RPC id 3f2 未返回」这类结论，
不要整段粘贴日志，不要留完整项目路径。

我确认根因后再谈修复。
```

修复阶段的固定约束：

```text
修复时守住 G3：reducer 保持纯同步，副作用走 EffectRunner，
所有异步路径校验 listener generation、runtime/epoch 和 disposed 状态。
如果修复要区分 Provider 行为差异（比如并发能力），
按 capability 建模，不要按 provider 名字硬编码（G4）。

根因结论和修复方案写入同一文件夹的 02-根因与修复.md。
```

> 时序类 bug 的排查产物值得留档：**同一类症状会反复出现**，下次先翻 `.workflow/bugfix/`
> 往往能直接命中。S/M 档 bug 不需要建文件夹。

## 四、重构

重构的定义：**行为不变。** 如果测试需要改，那不是重构，是需求变更 —— 换用第二类模板。

### S · 小改

```text
重构 <文件或类>：<提取方法 / 拆分 Widget / 重命名 / 消除重复>。

行为不变，现有测试一行都不要改。改完跑 analyze + 相关测试，全绿才算完。
```

### M · 中改

```text
重构目标：<把 X 的 Y 职责拆出去 / 收敛散落在多处的 Z>
动机：<为什么现在要做>

先给我拆分方案：新的职责边界、各自归哪一层、调用方要跟着改哪些。
确认后分步做，每步保持测试全绿。

行为不变，测试不改。纯重构不写 CHANGELOG。
```

### L · 大改

```text
重构范围：<跨层 / 跨 feature / 动共享层>

按 docs/prompts/refactoring.md 走完整六阶段，从「① 动机与止损线」开始。
不要跳过「③ 安全网加固」—— 没有安全网的重构是盲改。
```

> L 档重构（R3 契约收敛 / R4 结构改造）**必须**走 [`refactoring.md`](refactoring.md) 的完整流程，
> 不要套用 `workflow.md` 的功能开发流程 —— 两者的验收方式是相反的。

## 五、平台适配

Zeta 是三端桌面应用（macOS / Windows / Linux），任务栏未读、Dock、urgency、窗口框架各有独立实现。**平台相关改动的默认结论是「未验证」，不是「应该没问题」。**

### 修某一端的问题

```text
现象：<平台> 上 <行为>，其他端正常。

先确认这是平台差异还是通用 bug：找到对应的平台实现（MethodChannel / 平台目录），
说明三端各自是怎么做的、差在哪。

修的时候不要为了让这一端过而破坏另外两端。
改完明确告诉我：哪些端你实际验证过，哪些端没条件验证。
```

### 新增平台相关能力

```text
需求：<能力>，需要三端各自实现。

先给我三端的实现方案对比：各自用什么 API、有没有端上不支持的情况。
不支持的端按 G4 处理 —— capability=false，不要用 no-op 假装支持。

实现后给验证矩阵：平台 | 版本 | 验证结果（通过 / 失败 / 未验证）。
没条件验证的端如实写「未验证」，不要推断。
```

## 六、提交前自审

在交给 review 之前先让 AI 按项目门禁过一遍，省一轮往返。

```text
审一遍我这次的改动（git diff）。按 AGENTS.md §1 的九条门禁逐条检查，
命中的跑自查命令并贴结果。

重点看四件事：
1. 有没有 Provider 协议、raw payload 或 kind 分支漏出 data 层
2. 异步路径有没有漏掉 token/version guard、disposed 检查、generation 校验
3. 行为变了但测试没跟着变的地方
4. 该同步的文档（AGENTS.md §6 清单）

只报真问题，不要为了凑数报风格偏好。没问题就说没问题。
```

## 七、CI 失败排查

CI 跑的是 `dart format --set-exit-if-changed`、`flutter analyze`、`flutter test`，外加 `--enforce-lockfile`。

```text
CI 失败了：
<粘贴失败的 job 名和关键报错>

先判断是哪一类：
- format：本地跑 dart format . 后重新提交
- analyze：本地复现并修
- test：本地能复现吗？不能复现的话怀疑并发或环境依赖 —— 但**不要动
  dart_test.yaml 的 concurrency: 2**，先找测试自身的隐式依赖
- enforce-lockfile：pubspec.lock 和 pubspec.yaml 不一致，跑 flutter pub get 后提交 lock

先说明是哪一类和为什么，再修。
```

## 八、紧急修复

线上问题，时间紧。**越紧张越要缩小范围** —— 大改动在压力下出二次事故的概率极高。

```text
线上问题：<现象和影响面>

按最小风险处理：
1. 先给我最小可行修复（只堵这个问题，不做任何顺手改进）
2. 说明这个改动的风险面：还会影响什么
3. 如果根因修复风险大，先给缓解方案，根因修复单开跟进项

必须有的：一个能复现该问题的回归测试。
不接受的：为了赶时间跳过测试，或者顺手重构。
```

## 九、技术调研

评估「能不能做」「值不值得做」，产出是结论不是代码。

```text
调研：<问题，比如「能不能接入 XX CLI 作为新 Provider」>

只做调研，不写实现代码（验证性的一次性脚本可以）。输出：

1. 结论先行：能 / 不能 / 有条件能，一句话
2. 关键约束：卡点在哪，是协议限制、能力缺失还是架构冲突
3. 如果要做，对照 AGENTS.md §2 判断落在哪几层、命中哪些门禁、大概什么量级
4. 我没问但你觉得我应该知道的风险

不确定的地方明确标「不确定」，不要用推测填充。
```

## 十、其他高频场景

### 只读理解代码

```text
解释 <功能或链路> 是怎么工作的。用 codegraph explore 而不是逐个读文件。
输出：涉及的关键符号 + 调用链 + 各自属哪一层。不要改任何代码。
```

### 补测试

```text
给 <目标> 补测试。参照 AGENTS.md §3「测试」的分层要求，用 fake 不用 mock，AAA 结构。
共享层的测试必须用 Provider 无关 fixture。
先列测试用例清单给我确认，再写。
```

### 升级依赖

```text
把 <包> 升到 <版本>。

先看 changelog 找 breaking change，列出本项目实际用到的 API 里哪些受影响。
改完跑完整 flutter test（不只是相关测试），widget 测试全绿才算通过。
```

### 文档同步

```text
我刚改了 <架构边界 / 契约 / 持久化格式>。
按 AGENTS.md §6 的清单检查哪几份文档需要跟着改，列出来并逐个更新。
```
