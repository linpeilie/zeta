# 日常任务提示词

四类任务 × 三档复杂度。判档标准见 [README](README.md#三档复杂度)。

所有模板默认 AI 已读 `AGENTS.md`。收尾三件套（`dart format .` → `flutter analyze` → `flutter test` + 提交信息）是 AGENTS.md §0 的常驻要求，模板里只在需要强调时重复。

---

## 一、新增功能

### S · 小改

```text
在 <feature> 里新增 <一句话能力>。

先 codegraph explore "<相关符号>" 找到同类实现，照既有写法改，不要另起风格。
改完跑 format + analyze，补对应测试。
```

### M · 中改

```text
需求：<一句话>
验收：
- <可观察行为 1>
- <可观察行为 2>

动手前先给我改动清单：涉及哪些文件、各属哪一层、命中 AGENTS.md §2 路由表的哪几行。
我确认后再写代码。

实现时每层补测试（domain 单测 / controller 竞态与错误路径 / widget 行为）。
```

### L · 大改

```text
需求：<描述>

这次可能触及 <事件管线 / Provider 端口 / 持久化格式 / 权限语义>，属 L 档。
先不要写代码 —— 按 docs/prompts/workflow.md 的「阶段 2 方案设计」输出方案，
我确认后再进实现。
```

## 二、需求变更

改已有行为，风险主要在**旧调用方**和**已落盘的旧数据**。

### S · 小改

```text
把 <位置> 的 <旧行为> 改成 <新行为>。

改之前先 codegraph explore 确认还有哪些调用方依赖旧行为，一并列给我。
如果只有一处，直接改。
```

### M · 中改

```text
变更：<旧行为> → <新行为>
原因：<为什么>

先回答三个问题再动手：
1. 有哪些调用方依赖旧行为？
2. 有没有已落盘的旧数据受影响？需要宽容解码还是版本迁移？（G8）
3. 涉及的 capability 是否要跟着变？（G4）

然后改代码 + 改测试。行为变了，测试必须跟着变，不要为了让旧测试过而保留兼容分支。
```

### L · 大改

```text
契约变更：<描述>

这会改动 <domain 契约 / bundle 端口 / 持久化格式>。按 workflow.md 阶段 2 出方案，
重点说清楚：向后兼容策略（宽容解码 or 版本迁移）、旧字段的退场路径、
受影响的 Provider 各自要改什么。确认后再动手。
```

## 三、Bug 修复

### S · 小改

```text
现象：<操作> → 期望 <A>，实际 <B>
<报错或日志，已脱敏>

先定位根因再改，不要改症状。给我：根因一句话 + 最小修复 + 一个能复现该 bug 的回归测试。
```

### M · 中改

```text
现象：<操作路径> → 期望 <A>，实际 <B>
复现率：<必现 / 偶现，触发条件>
<脱敏日志>

流程：
1. 先写一个能稳定复现的失败测试，跑给我看它确实失败
2. 再定位根因，说明为什么会这样
3. 最后修复，同一个测试转绿

不要在没复现的情况下猜着改。
```

### L · 大改 —— 时序 / 竞态 / 流式类

这类 bug 是本项目最难的一类：状态在多个 generation、多个 session、多个进程之间流动，日志分散在三处。

```text
现象：<描述>，怀疑是时序或竞态问题
复现条件：<多会话 / 切换 thread / 快速重复操作 / 长回合>

先只读排查，不要改代码。按时间线交叉验证三处证据：
- Zeta：~/.zeta/logs/zeta-*.log（RPC 请求/响应 id 配对，看哪个请求没回）
- Provider CLI：<~/.grok/logs/unified.jsonl 或对应 CLI 日志>
- 会话目录：<对应 session 目录的 summary / events 尾部>

输出：事件时间线（对齐三处时间戳）+ 根因假设 + 支持该假设的证据 + 无法坐实的部分。
我确认根因后再谈修复。
```

修复阶段的固定约束：

```text
修复时守住 G3：reducer 保持纯同步，副作用走 EffectRunner，
所有异步路径校验 listener generation、runtime/epoch 和 disposed 状态。
如果修复要区分 Provider 行为差异（比如并发能力），
按 capability 建模，不要按 provider 名字硬编码（G4）。
```

## 四、重构

重构的定义：**行为不变。** 如果测试需要改，那不是重构，是需求变更 —— 换用第二类模板。

### S · 小改

```text
重构 <文件或类>：<提取方法 / 拆分 Widget / 重命名 / 消除重复>。

行为不变，现有测试一行都不要改。改完跑 analyze + 相关测试，全绿才算完。
```

### M · 中改

```text
重构目标：<把 X 的 Y 职责拆出去 / 收敛散落在多处的 Z>
动机：<为什么现在要做>

先给我拆分方案：新的职责边界、各自归哪一层、调用方要跟着改哪些。
确认后分步做，每步保持测试全绿。

行为不变，测试不改。纯重构不写 CHANGELOG。
```

### L · 大改

```text
重构范围：<跨层 / 跨 feature / 动共享层>

按 workflow.md 阶段 2 + 阶段 3 走：先出方案，再拆成可独立提交的步骤序列，
每步单独跑通门禁自查和测试。不要一次性大爆炸式提交。

特别注意：如果动到 G1 列出的共享适配层文件，先证明这是中立契约缺口，
而不是某个 Provider 的兼容逻辑漏上来了。
```

## 五、其他高频场景

### 只读理解代码

```text
解释 <功能或链路> 是怎么工作的。用 codegraph explore 而不是逐个读文件。
输出：涉及的关键符号 + 调用链 + 各自属哪一层。不要改任何代码。
```

### 补测试

```text
给 <目标> 补测试。参照 AGENTS.md §3「测试」的分层要求，用 fake 不用 mock，AAA 结构。
共享层的测试必须用 Provider 无关 fixture。
先列测试用例清单给我确认，再写。
```

### 升级依赖

```text
把 <包> 升到 <版本>。

先看 changelog 找 breaking change，列出本项目实际用到的 API 里哪些受影响。
改完跑完整 flutter test（不只是相关测试），widget 测试全绿才算通过。
```

### 文档同步

```text
我刚改了 <架构边界 / 契约 / 持久化格式>。
按 AGENTS.md §6 的清单检查哪几份文档需要跟着改，列出来并逐个更新。
```
