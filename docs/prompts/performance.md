# 性能优化流程

性能工作和其他场景的根本差别：**验收靠数值，不靠测试。** 测试能证明行为对，证明不了变快了。

和[重构](refactoring.md)一样，性能优化**行为不变**——所以现有测试断言同样一行都不改。但两者的失败模式不同：重构的坑是做不完，性能的坑是**自我欺骗**（改完感觉快了，其实没有；或者快了但不是你以为的那个原因）。

三条铁律，写在最前面：

- **先测量，再改。** 没有基线就没有结论。
- **Debug 数据不作结论。** 必须 `--profile`。
- **未达标就如实记录未达标。** 不补值、不用「主观感觉流畅」代替数字。

## Zeta 的性能指标

这些不是我编的，是 [工程规范 §6/§8](../architecture/engineering_standards.md) 定下的门槛。

| 指标 | 目标 |
|---|---|
| UI / Raster p95 | ≤ 16.7ms |
| 慢帧率 | ≤ 5% |
| 隐藏 retained page 的 layout 增量 | **0** |
| 数据未变化时 resize 的解析增量（grouping / diff / highlight） | **0** |
| 可见 item 构建数 | 受 viewport 限制，不随历史长度线性增长 |
| transient callback 数量 | 不随 resize 次数增长 |

标准采样场景：**Windows Profile，1280→1000→1280，10 秒**。

```sh
flutter run -d windows --profile
```

边界档位回归至少覆盖：外窗 **1197 / 1196 / 1195px**，Agent Canvas **641 / 640 / 639px**。

## 五个阶段

```
① 定位与基线 → ② 归因 → ③ 改动 → ④ 同基线复测 → ⑤ 固化
```

### ① 定位与基线

**目的：** 把「感觉卡」变成「哪个场景、哪个指标、多少」。

```text
现象：<什么操作下感觉卡 / 哪个页面 / 什么数据量>

先不要改代码，也不要猜原因。建立基线：

1. 把现象翻译成一个可重复的场景：具体操作序列、数据规模、窗口尺寸
2. 在 flutter run -d windows --profile 下跑这个场景，记录：
   UI p95、Raster p95、慢帧率
3. 如果和 resize 有关，用标准场景 1280→1000→1280 十秒
4. 记录环境：OS、机器、Flutter 版本、数据规模

输出基线表。这组数字后面每次复测都要能对齐，所以场景必须能一字不差地重跑。
```

**阶段门：** 场景可重复；基线数字有了；**知道自己要优化哪个指标**。

> 如果基线本来就达标 —— 停。你要优化的可能是别的东西，或者根本不存在这个问题。

### ② 归因

**目的：** 找到真正的开销来源。这一步的产出是**证据**，不是猜想。

```text
基线：<粘贴阶段 ① 的数据>

定位开销来源，先不要改代码。用 codegraph explore 摸清这条路径上有哪些环节。

按 Zeta 的常见嫌疑逐个排查，每条给出证据（计数器、timeline、日志）而不是推测：
- 隐藏的 retained page 有没有参与 layout？（应该是 0）
- 数据没变，grouping / unified diff / 代码高亮有没有被重新解析？（应该是 0）
- 时间线是不是还在虚拟化？可见 item 构建数有没有随历史长度增长？
- IdeConstraintBucketBuilder 的回调身份是不是每像素都在变，导致 child 无法复用？
- 有没有 post-frame 测量、GlobalKey 查高、layout 后 setState 的反馈环？
- 高频重绘区（流式 turn、语法高亮、diff）有没有 RepaintBoundary？
- 有没有事件风暴？CoalescingBuffer 的合并是不是失效了？

输出：开销分布 + 你认为的主因 + 支持它的证据 + 你排除掉的可能性。
```

**阶段门：** 主因有证据支撑。**「应该是 XX 慢」不算证据。**

### ③ 改动

```text
主因：<阶段 ② 的结论>

只针对主因改，一次改一处。行为不变 —— 现有测试断言一行都不改。

改完先跑 flutter analyze + flutter test 确认没改坏行为，再进复测。
不要顺手优化你觉得也慢的其他地方 —— 一次改多处，复测就分不清是哪个起了作用。
```

**阶段门：** 行为测试全绿；改动范围只针对主因。

### ④ 同基线复测

**目的：** 证明真的变快了，而且是因为你改的那个原因。

```text
改动完成，复测：

1. 用和阶段 ① **完全相同**的场景、数据规模、环境重跑
2. 贴出前后对比：UI p95、Raster p95、慢帧率
3. 贴出结构计数的前后对比（隐藏页 layout 增量、解析次数、
   viewport item 构建数、transient callback 数）
4. 明确说明：达标了 / 没达标 / 部分达标

规则：
- 环境变了（换机器、换数据规模、换窗口路径）就不能对比，重新测基线
- 没达到 16.7ms / 5% 时，只有在同构基线和结构计数都满足的前提下，
  才可以引用相对改善（比如「p95 从 32ms 降到 21ms」）
- 缺基线不得补值。测不到就写「未测」
```

**阶段门：** 有同基线前后对比；结论如实（含未达标）。

### ⑤ 固化

**目的：** 防止下一个人把你的优化改回去。性能优化最常见的结局是**几个月后被无声地退化掉**。

```text
性能改动完成，固化：

1. 把结构不变量写成测试 —— 这比记录数字更重要。至少覆盖：
   - 隐藏 retained page 的 build/layout 增量为 0
   - 数据未变化时 resize 的解析增量为 0
   - viewport item 构建数的上界
   - transient callback 不随 resize 增长
   - 边界档位：外窗 1197/1196/1195px、Agent Canvas 641/640/639px
2. 在关键位置加注释说明「这里为什么不能改成 XX」（中文，说清代价）
3. 采样数据写进 PR 描述，不入库
4. 用户可感知的改善写 CHANGELOG.md 的 [未发布]；内部微调不写
5. 给出提交信息（type 用 perf）
```

**阶段门：** 结构不变量有测试兜底。**只有数字没有测试的性能优化，等于没做。**

## 性能回归排查

「以前不卡，现在卡了」——方向和优化相反，从时间轴找变更点。

```text
回归现象：<场景> 以前流畅，现在卡

先不要改代码：
1. 在当前版本上测出数字，确认回归是真的（不是错觉）
2. 用 git log 找出这条路径上最近的改动，列出可疑提交
3. 二分定位：checkout 到可疑提交前后各测一次，对齐同一场景
4. 找到引入回归的那个提交后，说明它做了什么导致变慢

定位到再谈修复。不要在没定位的情况下"优化一下试试"。
```

## 常见自欺

这些都是本项目文档里明确点过名的：

| 说法 | 问题 |
|---|---|
| 「Debug 下测着快多了」 | Debug 数据不作结论,必须 `--profile` |
| 「手感明显流畅了」 | 主观感受不是验收依据 |
| 「没测基线,但肯定比原来快」 | 缺基线不得补值 |
| 「p95 是 21ms,虽然没到 16.7 但改善很大」 | 只有同构基线**且**结构计数都满足时才可引用相对改善 |
| 「我顺手还优化了另外两处」 | 一次改多处,分不清是哪个起作用 |
| 「加了缓存,快了」 | 缓存有没有失效路径?数据变了会不会读到旧值?先证明正确性 |

## 快速版

只是想确认某个改动有没有引入性能问题:

```text
我改了 <位置>,这属于 <resize / 时间线渲染> 热路径。
按 AGENTS.md §5 的额外验收要求跑一次 Windows Profile 采样,
对比改动前后的 UI/Raster p95 和慢帧率,如实报告是否达标。
```
