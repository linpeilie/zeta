# 重构开发流程

**重构的唯一定义：外部行为不变。**

这不是文字游戏。它决定了两件事：

- **验收方式是反的。** 功能开发证明「新行为出现了」，重构证明「行为一点没变」。
- **测试不能改。** 现有测试的断言一行都不动。如果某个断言必须改才能过 —— 停下来，那说明行为变了，你在做的是需求变更，换 [`daily.md` 第二类](daily.md#二需求变更)。

也因此，重构流程和 [`workflow.md`](workflow.md) 的五阶段不同：**安全网必须前置**。没有安全网的重构就是盲改。

---

## 重构分型

先定型，决定从哪个阶段起步。

| 型 | 范围 | 档 | 起始阶段 |
|---|---|---|---|
| **R1** 局部整理 | 单文件内：提取方法、提取私有 Widget、局部重命名、消除重复 | S | ③ |
| **R2** 职责搬迁 | 跨文件移动代码、拆分过大的类、把逻辑从 Widget 挪进 ViewModel | M | ② |
| **R3** 契约收敛 | 统一重复抽象、引入新端口、改 domain 模型形状 | L | ① |
| **R4** 结构改造 | 跨 feature 重排、动共享适配层、改事件流结构 | L | ①，且**先开 Issue** |

拿不准就按高一型处理。

**产出物落盘**（R1 通常一个都不需要，直接用[快速版](#快速版)）：

```
.workflow/refactor/<YYYY-MM-DD>-<任务简称>/
├── 01-动机与止损线.md
├── 02-现状测绘.md
├── 03-安全网.md
├── 04-目标态与步骤.md
├── 05-执行记录.md
└── 06-等价性验收.md
```

约定见 [`.workflow/README.md`](../../.workflow/README.md)。产物入 git，**贴日志和路径前先脱敏**。

## ① 动机与止损线

**目的：** 重构最大的失败模式不是做错，是**做不完、停不下来**。开工前先把边界钉死。

```text
我想重构 <目标>。

先不要看代码，也不要设计。回答四件事：

1. 具体痛点是什么？用一句可验证的话说，比如「改一个字段要同时动五个文件」
   —— 说不出具体痛点，就直接告诉我「不建议重构」
2. 不重构的代价是什么？接下来哪些需求会被它拖慢
3. 止损线：出现什么情况就放弃回滚，而不是硬做下去
4. 范围边界：这次明确**不碰**什么

写入 .workflow/refactor/<YYYY-MM-DD>-<任务简称>/01-动机与止损线.md（文件夹不存在就建），
然后贴要点给我。我确认后再进下一阶段。
```

**产出物：** `01-动机与止损线.md` —— 痛点陈述 · 不做的代价 · 止损线 · 范围边界

> **止损线要写进文件，不能只在脑子里。** 重构做到一半时人是最不愿意承认该停的，
> 那时候能救你的只有开工前白纸黑字写下的那条线。

**阶段门：** 痛点能用一句具体的话说出来。说不出来就不要重构 —— 「我觉得这样更好看」不是理由。

## ② 现状测绘与影响面

**目的：** 搞清楚炸开的范围。重构的意外几乎全部来自「没想到这里也依赖它」。

```text
重构目标：见 01-动机与止损线.md

用 codegraph explore 摸清现状，不要 grep + 逐个读文件。结果写入 02-现状测绘.md：

1. 当前结构：关键符号、职责划分、调用链
2. 影响面：所有调用方，逐个点名（不要写「等」）
3. 测试覆盖现状：哪些行为有测试钉住，哪些是裸奔的
4. Zeta 专项检查，逐条回答：
   - 搬迁后依赖方向会不会反向？（G6：domain 不能引入 Flutter / dart:io / Provider 协议）
   - 涉及的字段名有没有被持久化 codec 当作 JSON key？改名会不会读不出旧数据？（G8）
   - 涉及的 Widget 有没有参与 IdeHome 跨页保活或稳定 Key？
   - 涉及的 reducer 是不是 live/history/replay 共用算法但必须各自独立实例？（G3）
   - 有没有把 Provider 专属逻辑上提到共享层的动作？（G1）

先不要改代码。
```

**产出物：** `02-现状测绘.md` —— 现状结构 · 调用方清单 · 测试覆盖缺口 · 专项检查结论

> 调用方清单在阶段 ⑥ 还要用一次（逐个确认现在走的是哪条新路径），所以要写全、写准。

**阶段门：** 调用方逐个点名，测试缺口清单明确。

## ③ 安全网加固 ★

**这是重构特有、也最常被跳过的一步。** 先把行为钉住，再动结构。

```text
测试缺口：见 02-现状测绘.md

在**动任何结构之前**，先把要重构的行为路径用测试钉死：

1. 现有测试真的钉住当前行为了吗？还是只测了 happy path？
2. 缺口用 characterization test 补上 —— 目标不是「测得漂亮」，
   是「行为一旦变了就红」。边界条件、错误路径、空值都要覆盖
3. 补完跑一遍，确认**改动前**就是全绿的
4. 在 03-安全网.md 里列出：补了哪些测试、各自钉住什么行为、
   还有哪些路径是明知裸奔但决定不补的（以及为什么）

这一步连同 03-安全网.md 单独提交。补完等我确认，再进下一阶段。
```

**产出物：** `03-安全网.md` + 补齐的测试，单独一个提交

**阶段门：**

- 要动的每条行为路径都有测试覆盖
- 这些测试在**改动前**全绿（红的测试不是安全网，是待修的 bug）

> 这一步的产出可以独立合并。**就算重构后来放弃了，测试也留下了** —— 所以它从不白做。

## ④ 目标态与步骤编排

**目的：** 定终点，然后用「先加后删」把路径切碎。

```text
现状：见 02-现状测绘.md
安全网：已就位（见 03-安全网.md）

给出目标态 + 步骤编排，写入 04-目标态与步骤.md：

1. 目标结构：新的职责边界，各自归哪一层，为什么
2. 步骤序列，按**先加后删**排：
   新路径先建起来并跑通 → 调用方逐个切过去 → 旧路径没有调用方了再删
3. 每步给出：做什么 | 涉及文件 | 完成判据 | 回滚点 | 状态（先全填「待做」）

硬要求：每步之间仓库都必须是可编译、测试全绿的状态。
做不到就继续拆细。先不要开始做。
```

**产出物：** `04-目标态与步骤.md` —— 目标结构 · 有序步骤表（含回滚点与状态列）

**阶段门：** 每步可独立提交且全绿；每步有明确回滚点。

## ⑤ 逐步执行

```text
按 04-目标态与步骤.md 执行第 <N> 步。

做完这一步停下来：
1. 跑 dart format . && flutter analyze && flutter test
2. 把该步状态改成「完成」
3. 结果告诉我，等我确认再进下一步

三条硬约束：
- 现有测试的断言一行都不改（测试文件可以跟着移动位置，断言内容不能动）
- 某个断言必须改才能过 → 立刻停下来告诉我，那说明行为变了。
  这种情况**必须**记进 05-执行记录.md，写清楚是哪个断言、为什么会变
- 不顺手改无关代码，这次只做步骤表里的事
```

**产出物：** `05-执行记录.md` —— 只记三类事：断言被迫变动、偏离步骤表的改动、触碰止损线的时刻。顺利的步骤不用写。

**阶段门：** 全部步骤完成，**测试断言零修改**，`flutter test` 全绿。

> `05-执行记录.md` 如果攒了一堆「断言被迫变动」，说明这压根不是重构 —— 回到阶段 ① 重新定性。

## ⑥ 等价性验收与旧路径退场

**目的：** 证明行为没变，并且把旧路径删干净。

```text
重构做完了，走等价性验收。结果写入 06-等价性验收.md：

1. 跑**全量** flutter test（不是相关测试），贴结果
2. 跑本次命中的门禁自查命令（AGENTS.md §1），贴结果
3. 确认旧路径已无任何调用方，删干净 —— 不留「以防万一」的死代码和注释掉的旧实现
4. 确认行为等价：逐条走 02-现状测绘.md 的调用方清单，
   说明每个现在走的是哪条新路径
5. 按 AGENTS.md §6 检查文档 —— 改了分层边界或契约就要同步改
6. 纯重构**不写** CHANGELOG
7. 给出提交信息模块（type 用 refactor）

有任何一条没做到，在报告里如实写明。
最后检查整个任务文件夹，确认没有未脱敏的日志、完整路径或凭证。
```

**按型追加验收：**

| 型 | 额外要求 |
|---|---|
| R2（动了 Widget 树） | 用真实 `IdeHome` 跑集成级 Widget 测试：常驻骨架、AgentPane Element、当前 Thread、草稿、滚动位置、Pane 宽度与可见性都不能被重置 |
| R2/R3（动了 domain 字段） | 补一个「旧版本 JSON 能正常解码」的测试 |
| R3/R4（动了 reducer 或事件流） | Provider-local 序列测试 + Provider 无关 fixture 的共享层回归，两边都要绿 |
| R4（动了共享适配层） | 跑 G1 自查命令；并重新论证这是中立契约缺口而非 Provider 兼容逻辑上浮 |
| 任意型（动了时间线渲染或 resize 热路径） | Windows Profile 采样 1280→1000→1280 十秒场景。**Debug 数据不作结论** |

**阶段门：** 全量测试绿 · 门禁自查过 · 旧路径已删 · 文档已同步。

## Zeta 重构陷阱表

这些是本项目结构决定的、`flutter analyze` 抓不到的坑。

| 重构动作 | 隐藏风险 | 怎么防 |
|---|---|---|
| 重命名 domain 字段 | codec 若用字段名推导 JSON key，改名直接让旧数据读不出来（G8） | 先确认 codec 的 key 是显式字符串常量；补旧版本 JSON 解码测试 |
| 把 Provider 逻辑上提到共享层 | 直接违反 G1，且会让下一个 Provider 接入时被迫继续改共享层 | 上提前证明是跨 Provider 共同语义，否则退回 adapter/reducer |
| 拆分 reducer | 拆着拆着引入 `Future`/`Timer`，或让 live/history 共用了实例（G3） | 拆完确认无 Timer/Future/scheduler；确认三个入口各自 `new` 独立实例 |
| 重排 Widget 树 | 破坏 Element 复用 → 页面切换丢状态、丢滚动位置，且**测试不写就发现不了** | 稳定 Key 挂在会因 slot 增删而换位的 Flex 子节点上，不能只挂内部后代 |
| 提取 Widget | 意外扩大 rebuild 范围或丢掉 `RepaintBoundary` → 长时间线掉帧 | 热路径改动做 Profile 采样，不靠手感 |
| 合并「看起来重复」的抽象 | 把语义不同的东西合并 —— 四种审批就是典型，长得像但不共享模型（G5） | 合并前先说清两边的领域语义是不是真的同一个 |
| 移文件到别的层 | 依赖方向反向（G6） | analyze 抓一部分；还要人工确认 domain 里没混进 Flutter / `dart:io` / Provider 类型 |
| 收敛重复的 UI 代码 | 把 feature 私有视觉逻辑塞进 `ui/core`，变成没人敢改的公共组件 | 只有真正跨 feature 复用的原语才进 `ui/core` |

## 什么时候不该重构

四个明确的叫停信号：

- **说不出具体痛点** —— 停在阶段 ①。
- **正在赶功能的路上顺手重构** —— 把两件事的风险乘起来了。功能先合，重构单开分支。
- **没有安全网，也补不出来** —— 先补测试，这次不重构。测试本身就是有价值的交付。
- **只是觉得这样更好看** —— 风格偏好不是重构理由。

## 快速版

R1 级别的小整理不需要走六阶段。用这个就够：

```text
重构 <文件或类>：<提取方法 / 拆分 Widget / 重命名 / 消除重复>。

行为不变，现有测试断言一行都不改。
改完跑 format + analyze + 相关测试，全绿才算完。
```

更多小改模板见 [`daily.md` 第四类](daily.md#四重构)。
