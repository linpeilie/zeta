# 功能开发流程与阶段提示词

> **纯重构不走这套流程。** 重构的验收方式是相反的（证明行为没变，而不是验证新行为），
> 安全网也必须前置 —— 走 [`refactoring.md`](refactoring.md) 的六阶段。
> 判据：做完之后现有测试的断言需不需要改？需要改走本文，不需要改走重构流程。

一个需求从想法到可合并，走五个阶段。每个阶段有**固定产出物**和**阶段门** —— 门没过就不要进下一阶段，这是本流程唯一的强制约束。

```
① 需求分析 → ② 方案设计 → ③ 任务拆解 → ④ 实现 → ⑤ 验收交付
```

**按复杂度跳阶段**（判档见 [README](README.md#三档复杂度)）：

| 档 | 起始阶段 |
|---|---|
| **S** | 直接 ④，做完走 ⑤ |
| **M** | 从 ③ 开始（需求已清楚时），或从 ① 开始（需求含糊时） |
| **L** | **必须走完整五阶段**，①②③ 一个都不能跳 |

**产出物落盘：** 每个阶段的产出写成文件，跟代码一起提交。

```
.workflow/feature/<YYYY-MM-DD>-<任务简称>/
├── 01-需求分析.md
├── 02-方案设计.md
├── 03-任务拆解.md
├── 04-实现记录.md
└── 05-验收报告.md
```

跳过的阶段就不建文件。开工前先把任务文件夹起好，后面每个阶段提示词只要说「写入 `<路径>`」即可。目录约定、脱敏要求和生命周期见 [`.workflow/README.md`](../../.workflow/README.md) —— **产物入 git 历史，粘日志前务必脱敏。**

## ① 需求分析

**目的：** 把「我想要个功能」变成「可验证的行为清单 + 明确的边界」。含糊的需求会在阶段 ④ 变成返工。

```text
需求（我的原话）：<原始描述>

先不要设计，也不要写代码。帮我把它拆清楚：

1. 用户实际要解决什么问题？现在他们怎么绕过去的？
2. 可观察的验收标准（3-5 条，每条是「做 X 会看到 Y」的形式）
3. 明确不做的部分（划边界，防止范围蔓延）
4. 有歧义、需要我拍板的点（列出来，别自己替我决定）
5. 预判命中 AGENTS.md 的哪几条门禁，据此判 S/M/L 档

对照 docs/product/product_requirements.md，确认这个需求没和「明确不做」的部分冲突。

产出写入 .workflow/feature/<YYYY-MM-DD>-<任务简称>/01-需求分析.md（文件夹不存在就建），
然后把要点贴给我看。
```

**产出物：** `01-需求分析.md` —— 问题陈述 · 验收标准清单 · 非目标 · 待决策项 · 复杂度档位

**阶段门：** 验收标准每条都可观察、可测试。出现「体验更好」「更流畅」这种不可验证的表述，退回重写。

## ② 方案设计

**目的：** 在写代码之前，把分层归属和契约变更想清楚。**L 档的返工几乎全部来自跳过这一步。**

```text
需求和验收标准：见 .workflow/feature/<任务文件夹>/01-需求分析.md

出方案，先不要写代码。

方案要覆盖：
1. 现状：现在这块是怎么工作的，关键符号和调用链
2. 分层归属：新增/修改的代码各进哪一层，为什么
3. 契约变更：新增或修改的 domain 模型、bundle 端口、事件、持久化字段
4. 门禁合规：命中哪几条 G，逐条说明怎么满足。
   如果方案需要改共享适配层（G1），必须先论证这是中立契约缺口，
   而不是某个 Provider 的兼容逻辑漏上来了 —— 论证不成立就退回 Provider adapter/reducer
5. 兼容性：旧数据怎么读、旧调用方怎么办、capability 怎么变
6. 测试矩阵：哪一层测什么，各覆盖哪个风险点
7. 风险与取舍：你考虑过但否决的方案，以及为什么

给一个方案 + 你的推荐，不要列五个让我挑。

产出写入同一任务文件夹的 02-方案设计.md，然后把要点贴给我看。
```

**产出物：** `02-方案设计.md` —— 分层归属 · 契约变更清单 · 门禁合规论证 · 兼容性策略 · 测试矩阵 · 风险

**阶段门：**

- 每条契约变更都指明了归属层
- 每条命中的门禁都有明确的满足方式，不是「会注意」
- 如果方案要动共享层或新增 Provider 端口 —— **先开 Issue 讨论**，别在 PR 里直接推

---

## ③ 任务拆解

**目的：** 把方案切成一串可独立提交、可独立回滚的步骤。

```text
方案：见同一任务文件夹的 02-方案设计.md

拆成有序步骤。每步要满足：
- 单独可提交，提交后仓库处于可编译、测试全绿的状态
- 有明确的完成判据（跑什么命令、看到什么结果）
- 尽量做到「先加后删」：新路径先跑通，再摘掉旧路径

步骤表写入 03-任务拆解.md，格式：序号 | 做什么 | 涉及文件 | 完成判据 | 状态。
状态列先全部填「待做」。先不要开始做。
```

**产出物：** `03-任务拆解.md` —— 有序步骤表（含状态列）

**阶段门：** 每步都能独立通过 `flutter analyze` + `bash tool/test_affected.sh`。做不到就继续拆细。

---

## ④ 实现

**目的：** 按步骤落地，每步都保持绿。

```text
按 03-任务拆解.md 执行第 <N> 步。

做完这一步就停下来：
1. 跑 dart format . && flutter analyze && bash tool/test_affected.sh
2. 把 03-任务拆解.md 里这一步的状态改成「完成」
3. 有偏离方案的地方（改了别的文件、发现方案不对、临时决策），
   追加到 04-实现记录.md，一行一条，没有就不写
4. 把结果告诉我，等我确认再进下一步

不要一口气做完所有步骤。
```

连续推进时用这个：

```text
按 03-任务拆解.md 往下做，每完成一步跑一次 format + analyze + tool/test_affected.sh，
并更新该步状态。

遇到以下情况**立刻停下来问我**，不要自己拍板：
- 方案和实际代码对不上
- 发现必须改共享适配层或 Provider 端口
- 某步的改动量明显超出预估

停下来的原因写进 04-实现记录.md。
```

**产出物：** `04-实现记录.md` —— 只记偏离和临时决策。**顺利做完的步骤不用写**，步骤表的状态列已经说明了。

**实现期的固定要求**（AGENTS.md §3 的高频项，容易忘）：

- 异步加载加 token/version guard，通知监听者前检查 disposed
- 对外暴露集合用不可变快照
- `ChangeNotifier` / `ValueNotifier` / timer 在 `dispose` 里释放
- 新代码优先中文注释，重点覆盖协议适配、状态机、错误处理和不直观分支
- 行为变了就改测试；测试不该为了「让它过」而保留兼容分支

**阶段门：** 全部步骤完成，`bash tool/test_affected.sh` 全绿（全量交给 CI）。

## ⑤ 验收交付

**目的：** 自查一遍再交出去，省一轮 review 往返。

```text
改动做完了，走验收。结果写入 05-验收报告.md：

1. 跑 AGENTS.md §1 里本次命中的门禁的自查命令，贴出结果
2. 逐条对照 01-需求分析.md 的验收标准，说明各自由哪个测试或哪次手动验证覆盖
3. 按 AGENTS.md §6 检查是否需要同步文档；需要就一并改
4. 用户可感知的变化写进 CHANGELOG.md 的 [未发布]（纯重构不写）
5. 给出提交信息模块

如果有任何一条没做到，在报告里如实写明，不要含糊带过。
最后确认一遍报告里没有未脱敏的日志、路径或凭证。
```

**额外验收**（按需触发）：

| 触发条件 | 额外要求 |
|---|---|
| 改了 resize 热路径或时间线渲染 | Windows Profile 采样 1280→1000→1280 十秒场景，记录 UI/Raster p95、慢帧率。**Debug 数据不作结论；未达标数据如实保留** |
| 改了主要页面切换或保活 | 用真实 `IdeHome` 补集成级 Widget 测试：常驻骨架、AgentPane Element、当前 Thread、草稿、滚动位置、Pane 宽度与可见性都不能被重置 |
| 改了 Codex 适配层 | `python tool/smoke_codex_app_server.py --expected-version <版本>` + 必要时 `smoke_codex_plan_mode.py`；无设备或凭据时标记「待执行/阻塞」，**不得推断通过** |
| 改了持久化格式 | 覆盖损坏输入、缺字段、旧版本三种解码路径 |

**阶段门：** 门禁自查全过 · 验收标准逐条有覆盖 · 文档已同步。

## 专项流程 A：接入新 Provider

本项目的招牌 L 任务。**正常改动范围 = 自有 data 文件 + 中立 domain 契约 + factory 组合 + 契约测试。** 如果发现非改共享层不可，说明抽象没做对 —— 先开 Issue。

产物落在 `.workflow/feature/<日期>-接入-<CLI名>/`。

```text
要接入 <CLI 名称> 作为新 Provider，协议是 <ACP / JSON-RPC / 其他>。

分三轮，每轮产出写成文件后停下来等我确认。

第一轮 → 01-能力盘点.md（不写代码）：
对照 lib/src/features/agent/domain/agent_provider_bundle.dart 的现有端口，
逐个判断这个 CLI 支持哪些、不支持哪些。输出能力矩阵，
并说明不支持的能力打算怎么表达（capability=false + UnsupportedError，不是 no-op）。

第二轮 → 02-契约缺口.md：
现有端口不够用的地方，设计新的可选端口。名称和语义必须是 Provider 无关的。
说明为什么这是跨 Provider 的共同语义，而不是这一家的特殊需求。

第三轮 → 03-实现计划.md：
按 docs/guides/developer_guide.md §7 的十二步给出实现顺序和测试计划。
```

实现期反复强调这一句：

```text
守住 G1 和 G2：这个 Provider 的 source id 语义、message segment、reasoning phase、
去重和终态判定，全部在它自己的 adapter/reducer 里消化掉，输出语义完整的 AgentEvent。
不要让 TimelineStore、CoalescingPolicy 或 Buffer 知道这个 Provider 的存在。
```

必做的验证：

```text
1. Provider-local 序列测试：用带 CLI 版本的脱敏 fixture 证明 raw update → AgentEvent
   已完成身份、边界和终态决策
2. 共享层回归：用 Provider 无关 fixture 跑 CoalescingPolicy/Buffer/Pipeline/TimelineStore，
   这些测试不应该依赖新 Provider 的任何类或 fixture
3. 运行时复用测试：同一 scope（`global` 或同一个 `session(entryId)`）内并发租约只创建
   一个实例，不同 session scope 各自独立；多 session 并存时任一 session 的恢复、发送
   或结束不破坏其他 session
4. 跑 G1 自查命令，贴结果

结果写入同一任务文件夹的 04-验收报告.md。
```

## 专项流程 B：新增或修改 AgentEvent

事件是整条管线的契约。改动前有一份 **16 问清单**，不是走过场。

```text
要新增/修改 AgentEvent：<描述这个事件代表什么>

先不要写代码。逐项回答 docs/guides/developer_guide.md §7「新增 AgentEvent 接入清单」
的 16 个问题，每个都给明确答案 —— 「暂不确定」等于没答完。

答完之后，把每个答案对应到一个具体测试：这 16 条要用测试固定下来，
而不是写在注释里。

输出「问题 → 答案 → 用哪个测试固定」的对照表，
写入 .workflow/feature/<日期>-<事件名>/01-十六问.md。
```

后续阶段的产物同样落在这个文件夹：`02-实现记录.md`、`03-验收报告.md`。**`01-十六问.md` 是这类改动最有价值的留档** —— 半年后有人问「这个事件为什么是 immediate 不是 next-frame」，答案在这里。

16 问里最容易含糊、也最容易出事的四条，可以单独追问：

```text
再确认这四条，答案要具体：
- 第 1 条：规范化 identity 由哪个 Provider adapter/reducer 产生？（不能是「Store 推断」）
- 第 4-6 条：合并 key 是否覆盖 thread/turn/item/kind/detail？是不是 barrier？
  处理前要 flush 哪些 pending？
- 第 10 条：UI urgency 选 next-frame 还是 immediate，理由是什么？
- 第 16 条：有没有 raw payload、source id 推断或 Provider 分支漏到 presentation/Store？
```

## 专项流程 C：协议升级

Agent CLI 发新版时的跟版本流程。**顺序不能变**：先 diff schema，再改代码，最后真机验证。反过来做会把「协议真的变了」和「我理解错了」混在一起。

当前 pin：Codex CLI `0.144.5`（schema 快照在 `third_party/codex_app_server_schema/`）；Grok CLI 基线 `0.2.119`。

产物落在 `.workflow/protocol/<日期>-codex-<新版本>/`：`01-schema-diff.md` · `02-适配改动.md` · `03-smoke-记录.md` · `04-收口.md`。

### 第一步 · Diff（不写代码）

```text
要把 Codex 从 <旧版本> 升到 <新版本>。

先只做 schema diff，不要改任何适配层代码：

./tool/gen_codex_schema.sh --diff        # Windows: ./tool/gen_codex_schema.ps1 -Diff

把差异按四类分门别类，逐条列出：
- A 新增字段/方法：我们要不要用？不用就明确说不用
- B 改名/移位：影响哪些 mapper/codec
- C 删除：我们有没有在依赖它？没有替代品的话是 breaking
- D 语义变化（字段名没变但含义变了）—— 这类最危险，schema diff 看不出来，
  要结合 changelog 和实际抓包判断

分类表 + 影响面写入 01-schema-diff.md。先不要动代码。
```

**阶段门：** 每条差异都归了类；D 类（语义变化）单独标出并说明判断依据。

### 第二步 · 改适配层

```text
差异分类：见 01-schema-diff.md

改适配层，改了什么记到 02-适配改动.md。守住 G1/G6：

- 协议字段的解析、兼容、默认值只能出现在 data 层的 mapper/codec/client
- domain 模型和 AgentEvent 的形状不因协议升级而暴露新的协议字段
- 如果新协议带来的是全新语义（不只是字段搬家），先停下来说明，
  可能需要走「专项流程 B：新增 AgentEvent」

先用 fake contract test 覆盖新旧两种 payload，跑绿了再进真机验证。
```

**阶段门：** fake contract test 覆盖新旧 payload 且全绿；`flutter analyze` 干净。

### 第三步 · 真机 smoke

```text
适配层改完，跑真实 CLI 冒烟：

python tool/smoke_codex_app_server.py --expected-version <新版本>
python tool/smoke_codex_plan_mode.py --expected-version <新版本>

记录写入 03-smoke-记录.md：OS/架构、CLI 版本、Schema/包装器类型、逐项通过或失败。

硬要求：
- 记录里不得出现 prompt、回复、文件内容、凭证、原始 payload、
  thread/turn id 或 stderr 原文
- 实验协议缺少预期事件时，保留实际方法名级差异并**返回失败**，
  不能用 stable schema 或 fake peer 的结果顶替
- 没有设备或凭据跑不了的部分，标「待执行/阻塞」，**不得推断通过**
```

**阶段门：** smoke 记录完整；失败项如实保留。

### 第四步 · 收口

```text
1. 更新 third_party/codex_app_server_schema/ 的 pin 快照
2. 更新 docs/protocols/codex_app_server_protocol.md 的版本与升级记录
3. 如果最低版本要求变了，同步改 CONTRIBUTING.md、docs/guides/developer_guide.md §2
   和 AGENTS.md §5 的事实清单
4. 用户可感知的兼容性变化写进 CHANGELOG.md
5. 收口清单和最终版本对照写入 04-收口.md
6. 给出提交信息
```

> Grok / ACP 升级同理，只是没有 schema 导出工具：用 changelog + 脱敏 fixture 抓包代替第一步，其余不变。**Grok 的多会话隔离是 `0.2.119` 才有的**，降低基线要重新验证并发行为。

## 专项流程 D：持久化格式演进

改 `~/.zeta` 下任何落盘结构。**失败代价是用户数据读不出来，且通常不可逆** —— 所以这个流程的核心是「先想清楚旧数据怎么办」。

产物落在 `.workflow/migration/<日期>-<文件名>-v<新版本>/`：`01-变更定性.md` · `02-兼容策略.md` · `03-实现与验证.md` · `04-收口.md`。**这类产物尤其值得留** —— 下次再演进同一个文件时，上次的兼容决策就是起点。

### 第一步 · 定性变更

```text
要改的持久化结构：<文件名 + 改什么>

先定性，不要写代码。这次属于哪一类：

- 加字段 → 给默认值就行，不用升版本
- 改字段语义（名字没变，含义变了）→ **必须升版本**，否则旧数据会被误读
- 改字段名 / 改结构 → 升版本 + 迁移
- 删字段 → 确认没有读取方，decoder 要能忽略未知字段

然后回答：
1. 已经落盘的旧数据长什么样？（列出实际的旧版本 JSON 形状，字段值脱敏）
2. 用户升级后第一次启动，读到旧数据会发生什么？
3. 用户降级回旧版本，读到新数据会发生什么？（至少不能崩）

写入 01-变更定性.md。
```

**阶段门：** 变更定性明确；旧数据的读取路径想清楚了。

> 「加字段」是唯一不用升版本的情况。**拿不准就升版本** —— 版本号很便宜，数据丢了很贵。

### 第二步 · 设计兼容策略

```text
变更定性：见 01-变更定性.md

设计兼容策略，写入 02-兼容策略.md：

1. 版本号怎么变（参考 AgentProviderSettings.currentVersion = 2 的做法）
2. tryDecode 的宽容路径：缺字段、损坏 JSON、旧版本、未知字段，
   四种情况分别怎么处理 —— 任何一种都不能阻断应用启动
3. 需要迁移的话：迁移在哪一层做？
   （只能在 data/config 边界，domain 不认识 legacy 字段）
4. 迁移必须幂等，且**以已存在的目标文件为准**，不能用空值覆盖待迁移数据
5. 写不写 migration marker？部分失败怎么办？
   （本次运行用内存状态，不标完成，不阻断启动，下次继续重试）
```
