# 文档维护

文档需要回答读者的问题。记录同一件事时，选择一个长期维护的位置，其他页面链接过去。

## 按读者放置

| 位置 | 读者与内容 |
| --- | --- |
| 根 README、中英文 `guide/` | 使用者：能做什么、在哪里操作、结果和限制 |
| `product/` | 产品讨论：需求、边界和可观察的验收结果 |
| `architecture/` | 开发者：职责、依赖、不变量与设计理由 |
| `development/` | 贡献者：开发步骤、测试和专项接入清单 |
| `protocols/` | 适配维护者：版本、字段、真实证据与尚未验证的差异 |
| `release/` | 发布维护者：构建、发布和验收步骤 |
| `AGENTS.md` / `CLAUDE.md` | AI：核心规则 / 指向规则的入口 |

## 用户文档的写法

先写用户能做什么和下一步操作，再补结果与限制。用界面上的名称指路，必要时解释一次，例如“Skill 是助手预先准备的一组任务说明”。

逐段念出正文，假设听者不会编程，也看不到代码。如果听完仍不知道该做什么，就重写。菜单名、文件名和诊断命令可以保留，但要说明用途，不能用它们代替解释。

不向用户解释 adapter、reducer、runtime、payload、typed、握手、分层、渲染或状态所有者。不要写“按能力渲染”，直接写“所选助手不支持时，不会显示这个按钮”。

不承诺“所有操作都会询问”“代码不出本机”“任意长对话都不卡”“完整恢复所有内容”。说明权限、助手提供的数据、网络和历史文件等实际条件。

删掉口号、夸张比较、反复强调和写作过程，例如“核心卖点”“一条底线”“无需担心”“不是 X 而是 Y”“本文全面梳理”。每段只保留事实、操作和必要原因。

## 清理旧材料

- 已完成计划移出工作树；需要长期维护的规则和协议证据归入现行文档，已提交的过程记录从 Git 历史查阅。本地工作草稿不作为文档引用来源。
- 历史记录标明日期和适用阶段，不把旧测试数、旧路径或旧版本当作当前事实。
- 被当前实现和规范替代的提案可删除，历史由 Git 保存。删除前把独有的约束、例外或未完成事项迁到对应现行文档。
- 未完成、已跳过、失败、未验证分别标注。自动化通过不代表真实 CLI 或跨平台验收通过。
- 截图放在实际引用的位置；没有图片时，不保留假图片链接或单独占位目录。截图应使用演示数据并检查私人信息。

## 提交前自查

- [ ] 每页有明确读者；用户文档通过逐段朗读检查。
- [ ] 菜单、功能支持、数据位置和权限说明与当前代码及界面文案一致。
- [ ] 不把协议取样版本写成最低版本承诺，也不把未知值写成零。
- [ ] 中英文的操作、限制和数据说明一致；未翻译工程页明确链接中文。
- [ ] 本地链接、图片、标题锚点有效；引用已删除文件的入口已更新。
- [ ] 代码围栏闭合，表格列数一致，无空占位、重复标题和失效任务链接。
- [ ] 工程规则不依赖已完成的工作计划；AGENTS 只留核心约束，CLAUDE 不复制正文。
- [ ] 现行文档不依赖已删除的计划或未提交的本地草稿。
- [ ] `git diff --check` 通过，改动不含凭据、私人路径或原始对话。

纯文档改动不用运行 Flutter 测试。涉及代码或脚本行为时，仍按 [AGENTS.md](../../../AGENTS.md)执行相应检查。
