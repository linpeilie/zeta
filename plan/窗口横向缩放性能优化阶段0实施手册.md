## 2. Flutter 性能术语速查

在开始操作前，只需要理解以下概念。

### 2.1 Frame

Frame 是 Flutter 生成的一次完整画面更新。60Hz 显示器约每 16.7ms 需要一帧；
超过这个时间就可能出现掉帧或鼠标拖动不跟手。

如果显示器是 120Hz，单帧预算约为 8.3ms。为了让不同机器可比较，本文仍以
60Hz 的 16.7ms 作为第一验收线，同时记录实际显示器刷新率。

### 2.2 UI 线程

UI 线程执行 Dart 和 Flutter Framework 工作，主要包括：

- Widget `build`；
- RenderObject `layout`；
- 生成 paint 命令；
- 业务 Dart 计算；
- 创建本帧的 Layer Tree。

本项目当前怀疑的时间线分组、Markdown Widget 创建和文本布局主要发生在这一侧。

### 2.3 Raster 线程

Raster 线程把 Layer Tree 转换成屏幕像素。大量阴影、Clip、Opacity、`saveLayer`
等可能使 Raster 变慢。

### 2.4 Build、Layout、Paint

```text
Build
    把当前状态转换成 Widget / Element 结构
Layout
    根据宽高约束计算每个 RenderObject 的尺寸和位置
Paint
    生成绘制命令
Raster
    把绘制命令真正栅格化到屏幕
```

窗口横向 resize 会改变宽度约束，因此即使数据完全不变，也会触发 Layout。优化目标
不是让 Layout 完全消失，而是减少参与 Layout 的页面和文本数量，并避免宽度每变化
1px 就重新执行无关的 Build 和数据计算。

### 2.5 Profile 模式

Flutter 有 Debug、Profile、Release 三种主要模式：

- Debug：便于开发和热重载，但包含大量断言和调试开销，不能用于性能结论。
- Profile：接近 Release，同时保留 DevTools 所需追踪能力。
- Release：最终发布模式，但不能进行完整 DevTools 性能分析。

本阶段所有性能数据必须来自：

```sh
flutter run -d windows --profile
```

只使用普通 `flutter run` 得到的是 Debug 数据，应直接废弃。

官方参考：

- [Flutter build modes](https://docs.flutter.dev/testing/build-modes)
- [Flutter DevTools Performance view](https://docs.flutter.dev/tools/devtools/performance)

## 3. 整体执行顺序

第一次执行时严格按以下顺序：

```text
步骤 1：保护当前工作区
步骤 2：记录机器、Git 和 Flutter 环境
步骤 3：准备四个固定场景
步骤 4：创建仓库外临时采集目录
步骤 5：以 Windows Profile 模式启动 Zeta
步骤 6：完成预热，排除首次 Shader / 首次页面初始化
步骤 7：采集不带增强追踪的干净基线
步骤 8：采集 Build / Layout 诊断 trace
步骤 9：分析 UI / Raster 和场景差异
步骤 10：填写基线表和阶段 0 结论
```

建议预留 60–90 分钟。第一次 Flutter Profile 编译可能较慢，不要因为编译等待时间
而误以为应用运行性能有问题。

## 4. 步骤 1：保护当前工作区

### 4.1 查看工作区状态

在 PowerShell 中进入项目：

```powershell
Set-Location "D:\Development\Workspace\zeta"
git status --short
git branch --show-current
git rev-parse HEAD
```

把输出复制到稍后创建的 `environment.md`。

### 4.2 不要清理用户改动

如果 `git status --short` 有输出：

- 不要执行 `git reset --hard`；
- 不要执行 `git checkout -- .`；
- 不要删除不认识的文件；
- 不要为了得到“干净仓库”覆盖当前改动。

如果未提交改动只涉及 `test/` 或文档，通常不会影响 `flutter run` 的生产运行路径，
但必须在环境记录中写明。

如果未提交改动涉及 `lib/`、`windows/`、`pubspec.yaml` 或资源文件，建议：

1. 先由改动所有者提交或暂存到安全分支；或者
2. 在单独 Git worktree 中基于明确 commit 采集。

不熟悉 `git worktree` 时不要自行尝试清理，优先请求熟悉 Git 的同事协助。

### 4.3 固定基线 commit

记录完整 commit：

```powershell
git rev-parse HEAD
```

阶段 0、后续优化后的复测必须分别记录 commit。不能只写“最新代码”。

## 6. 步骤 3：准备固定场景

### 6.1 为什么要固定场景

如果基线只有 1 个短会话，而优化后使用 6 个长会话，两组数据没有可比性。必须固定：

- 会话数量；
- 当前活动会话；
- 可见历史 turn 数；
- Markdown 和 diff 内容规模；
- Inspector 状态；
- 起始窗口大小；
- 拖动时长和方向。

### 6.2 四个必测场景

| ID | 会话数量 | 右侧 Inspector | 目的 |
|---|---:|---|---|
| S1 | 1 | 关闭 | 最小业务负载 |
| S2 | 6 | 关闭 | 验证隐藏 AgentPane 放大效应 |
| S3 | 1 | 打开 | 验证中央 Canvas 变窄后的文本重排 |
| S4 | 6 | 打开 | 当前最坏场景 |

### 6.3 对话内容最低要求

当前活动会话至少包含：

- 3 个已加载历史 turn；
- 每个 turn 至少一段 20 行左右的 Markdown；
- 至少一个列表；
- 至少一个代码块；
- 至少一组工具调用；
- 至少一组文件编辑或 diff。

其余 5 个隐藏会话也应至少加载 3 个历史 turn。

### 6.4 数据安全

- 优先使用无敏感信息的测试项目和测试会话。
- 不要为了准备场景删除、归档或改名真实用户会话。
- 不要把真实源代码、密钥、客户路径放进截图。
- DevTools snapshot 按敏感开发数据处理，只放临时目录。

### 6.5 如果暂时没有 6 个合适会话

不要为了“凑数”立即修改生产代码。先完成 S1 和 S3，并在记录中写：

```text
S2 / S4 blocked: deterministic six-session fixture unavailable
```

之后可以单独增加只用于 Widget test 的 fake fixture。不能把不稳定的真实 Provider
请求当成每次性能回归的前置条件。

### 6.6 固定起始状态

每次录制前：

1. 窗口恢复到应用默认约 1280 × 800。
2. 左侧 Projects Pane 保持打开。
3. 根据场景打开或关闭右侧 Inspector。
4. 选择同一个活动会话。
5. 时间线滚动到同一位置，建议靠近底部但不要处于流式输出中。
6. 等待所有 Provider 请求和历史加载完成。
7. 确保没有 Popover、Dialog、Toast 或上下文菜单。
8. 输入框保持无焦点，除非本轮明确测试有草稿场景。

## 7. 步骤 4：定义统一拖动动作

人工拖动无法做到像自动化测试一样完全一致，但可以控制误差。

### 7.1 标准动作

一次标准录制持续约 14 秒：

```text
前 2 秒：窗口保持静止
第 2–4 秒：右边框从约 1280px 匀速拖到约 1000px
第 4–6 秒：从约 1000px 匀速拖回约 1280px
第 6–8 秒：再次拖到约 1000px
第 8–10 秒：再次拖回约 1280px
第 10–12 秒：第三次拖到约 1000px
第 12–14 秒：窗口保持静止
```

这个范围会跨过约 1180px 的 Wide / Medium 变化区，既能观察持续 resize，也能观察
断点切换的单次尖峰。

### 7.2 如何控制节奏

- 在手机或另一块屏幕上打开秒表。
- 以“2 秒完成一次单向拖动”为目标。
- 不要快速左右抖动鼠标。
- 不要在不同 run 中改变拖动次数。
- 如果鼠标中途松开或误触其他控件，废弃该 run。

### 7.3 每个场景采集三次

每个 S1–S4 的干净基线执行 3 次。后续取中间水平的 run 作为代表，不使用最好或最坏
的单次结果冒充整体表现。

## 8. 步骤 5：以 Profile 模式启动

### 8.1 依赖准备

在仓库根目录执行：

```powershell
flutter pub get
```

不要习惯性执行 `flutter clean`。它不能解决运行时布局问题，还会增加不必要的完整
重编译。只有构建缓存明确损坏时才考虑 clean。

### 8.2 启动 Windows Profile

```powershell
flutter run -d windows --profile
```

确认终端输出包含 Profile，而不是 Debug。应用启动后不要关闭该终端。

### 8.3 打开 DevTools

`flutter run` 启动后会输出 VM Service 和 DevTools 地址。打开终端中类似下面的地址：

```text
http://127.0.0.1:<port>?uri=...
```

如果终端没有显示：

1. 在终端输入 `h` 查看当前 Flutter CLI 快捷键；
2. 使用帮助中对应的 DevTools 命令；或者
3. 从 IDE 的 Flutter / Dart DevTools 入口连接当前 Profile 进程。

不要连接到另一个旧的 Flutter 实例。DevTools 顶部应显示当前 Zeta 进程。

### 8.4 进入 Performance

在 DevTools 左侧选择 `Performance`。

如果没有 Performance：

- 确认目标是 Windows desktop，而不是 Chrome；
- 确认使用 `--profile`；
- 确认 DevTools 连接的 VM Service 属于本次 Zeta。

Flutter 官方说明 Performance view 支持 Flutter mobile 和 desktop 应用，并要求使用
Profile build 进行有效分析。

## 9. 步骤 6：预热

第一次显示某个页面时可能包含：

- 首次 Widget 创建；
- 首次 Markdown 解析；
- 首次字体加载；
- 首次 Shader 编译；
- 首次 Provider 历史加载；
- 首次代码高亮。

这些事件会污染持续 resize 的基线。

### 9.1 预热动作

正式录制前：

1. 等待应用启动完成至少 10 秒。
2. 打开本轮要测试的项目和活动会话。
3. 从时间线顶部滚动到底部一次。
4. 展开并收起一次本轮会出现的 diff。
5. 打开并关闭一次右侧 Inspector。
6. 将窗口从 1280 左右拖到 1000 左右，再拖回一次。
7. 等待 5 秒，直到界面没有加载指示。

### 9.2 Shader 判断

DevTools 会把 Shader compilation 相关慢帧标成深红色。若慢帧只在第一次操作出现，
第二次不再出现，应把第一次作为预热，不作为本轮持续 resize 根因。

## 10. 步骤 7：采集干净基线

干净基线用于比较“优化前”和“优化后”的真实帧耗时。

### 10.1 关闭增强追踪

在 Performance 页找到 `Enhance tracing`。不同 DevTools 版本可能显示为
`Track` 或 `Trace`，确认以下选项全部关闭：

- Widget builds；
- Layouts；
- Paints；
- 其他会为每个 Widget / RenderObject 增加事件的细粒度追踪。

官方文档明确说明增强追踪会对 frame time 产生负面影响。因此带增强追踪的记录不能
用来比较 p95、最大帧耗时或掉帧率。

### 10.2 清空旧记录

在 Performance 页：

1. 点击 Clear / Trash 清除旧 Timeline。
2. 等待 Frames chart 为空或从当前时刻重新开始。
3. 如果当前版本提供显式 Record 按钮，点击开始。
4. 如果 Frames chart 自动更新，则直接进入下一步。

### 10.3 执行标准动作

按第 7.1 节完成 14 秒标准动作。期间：

- 不切换页面；
- 不滚动；
- 不输入文字；
- 不触发 Provider；
- 不打开菜单；
- 只拖动最右侧外边框。

### 10.4 暂停并检查

动作结束后：

1. 暂停 Frames chart 更新。
2. 找到拖动区间。
3. 观察：
   - UI 条是否大量变红；
   - Raster 条是否大量变红；
   - 是否只有跨 1180px 附近的个别尖峰；
   - 静止区间是否迅速恢复。
4. 选择最慢的一个红色 frame。
5. 查看 `Frame analysis`：
   - UI duration；
   - Raster duration；
   - 是否标记 Shader compilation；
   - DevTools 给出的诊断提示。

### 10.5 导出 snapshot

点击 Performance 页右上角 Export，保存到：

```text
<临时目录>\clean\
```

命名格式：

```text
S1_one_session_inspector_off_run1.json
S1_one_session_inspector_off_run2.json
S1_one_session_inspector_off_run3.json

S2_six_sessions_inspector_off_run1.json
...

S3_one_session_inspector_on_run1.json
...

S4_six_sessions_inspector_on_run1.json
...
```

DevTools 只保证能重新导入由 DevTools 自己导出的 snapshot。不要手工修改 JSON。

### 10.6 截图

至少保存：

- 完整 Flutter frames chart；
- 最慢 frame 的 Frame analysis；
- 如果能看见，拖动前静止区和拖动区的对比。

截图文件名与 snapshot 使用相同场景前缀。

### 10.7 重复三次

清空 Timeline，恢复固定起始状态，再进行 run2 和 run3。

如果某次发生以下情况，应废弃并重新录制：

- Provider 正在流式输出；
- 系统弹窗出现；
- 鼠标误触；
- 页面切换；
- DevTools 自身卡死或断开；
- 第一次 Shader 编译集中出现；
- 窗口没有回到约定起始宽度。

## 11. 步骤 8：采集诊断 Trace

诊断 Trace 用于回答“慢在哪里”，不用于回答“到底有多慢”。

选择最坏场景 S4，只需要分别录制 Build 和 Layout。每个诊断 run 缩短到 4–6 秒，
避免事件过多使 DevTools 本身变慢。

### 11.1 Build Trace

1. 清空 Performance Timeline。
2. 在 Enhance tracing 中只打开 `Track/Trace Widget Builds`。
3. 确认 Layouts 和 Paints 关闭。
4. 执行一次：
   - 1280 → 1000；
   - 1000 → 1280。
5. 暂停。
6. 选择一个慢 UI frame。
7. 打开 `Timeline events`。
8. 展开本帧的 build 事件。
9. 搜索或观察是否反复出现：
   - `AgentPane`；
   - `_AgentConversationLayout`；
   - `_AgentConversationTimeline`；
   - `_AgentTurnSection`；
   - `_AgentMarkdownMessage`；
   - `MarkdownWidget`；
   - `MarkdownDocumentView`；
   - diff / Highlight 相关 Widget。
10. 导出为：

    ```text
    diagnostic\S4_trace_builds.json
    ```

11. 截图最有代表性的 Widget build 调用段。

### 11.2 Layout Trace

1. 关闭 Widget Builds。
2. 清空 Timeline。
3. 只打开 `Track/Trace Layouts`。
4. 重复同样的 4–6 秒动作。
5. 选择慢 UI frame。
6. 在 Timeline events 中观察：
   - `RenderIndexedStack`；
   - `RenderFlex`；
   - `RenderParagraph`；
   - Markdown block 对应 RenderObject；
   - `RenderConstrainedBox`；
   - 多个非活动 AgentPane 是否同时出现布局事件。
7. 导出为：

   ```text
   diagnostic\S4_trace_layouts.json
   ```

### 11.3 Paint Trace

只有满足下面条件才录制 Paint：

```text
干净基线中 Raster 大量红色，
并且 UI 大部分保持在预算内。
```

步骤：

1. Build 和 Layout tracing 全部关闭。
2. 只打开 Paints。
3. 重复短动作。
4. 观察 Clip、Opacity、Physical Shape 或大 RepaintBoundary。
5. 导出：

   ```text
   diagnostic\S4_trace_paints.json
   ```

当前静态代码分析更怀疑 UI build/layout，所以 Paint trace 不是默认必做项。

### 11.4 不要同时打开全部追踪

同时打开 Builds、Layouts、Paints 会：

- 明显增加运行时开销；
- 生成极大的 Timeline；
- 让真正的调用关系更难阅读；
- 使 DevTools 页面本身卡顿；
- 产生不能和 clean baseline 比较的数字。

## 12. 步骤 9：如何阅读结果

### 12.1 先判断 UI 还是 Raster

| 观察 | 初步结论 | 下一步 |
|---|---|---|
| UI 大量红，Raster 正常 | Dart build/layout 过重 | 看 Build / Layout trace |
| Raster 大量红，UI 正常 | 绘制层过重 | 补 Paint trace 和 Layer 开关实验 |
| UI、Raster 都红 | 先处理 UI | UI 生成复杂 Layer Tree 也会拖慢 Raster |
| 只有第一次深红 | 可能是 Shader 编译 | 预热后重测 |
| 只在断点附近单帧很高 | 模式切换整树替换 | 对应总方案阶段 1 |
| 整个拖动过程持续红 | 全量 build/layout | 对应阶段 2–5 |

### 12.2 比较四个场景

#### S2 明显差于 S1

```text
会话数量增加
→ 当前页面内容相同
→ resize 更慢
```

这强烈支持“隐藏 AgentPane 仍参与 IndexedStack 布局”，对应总方案阶段 3。

#### S3 明显差于 S1

打开 Inspector 会压缩 Canvas，正文更容易换行。这支持文本宽度重排是主要放大因素。

#### S4 显著差于 S2 和 S3

说明“隐藏页面布局”和“活动页文本重排”同时发生，两个成本叠加。

#### 四个场景差异不明显

需要重新检查：

- 是否真的存在 6 个已挂载 AgentPane；
- 隐藏会话是否已经加载历史；
- 当前页面是否为 Project Home 而不是 AgentPane；
- Profile 是否连接正确；
- 是否被 GPU、系统合成器或驱动问题主导。

### 12.3 识别当前代码假设

| Trace 信号 | 对应问题 |
|---|---|
| 每帧大量 `_AgentTurnSection.build` | resize 重复 grouping |
| 每帧出现全部 Markdown Widget | AgentPane 子树逐像素重建 |
| Layout 中多个 `RenderIndexedStack` child | 隐藏页面继续布局 |
| 大量 `RenderParagraph` | 文本重新断行 |
| diff 相关 Highlight build | 代码高亮重复解析 |
| 拖动停止后仍连续多一帧 | Footer post-frame 测量反馈 |
| 断点处 AgentPane State 重新创建 | Workbench Row key 变化 |

### 12.4 GC 事件怎么理解

频繁创建 render block、列表和 Widget 可能产生更多短生命周期对象，从而伴随 GC。

不要仅因为看到 GC 就得出“垃圾回收是根因”。应确认：

1. GC 是否与慢帧时间重合；
2. Build trace 是否同时显示大量对象创建路径；
3. 场景规模增加是否同时增加 GC 和 UI frame time。

## 14. 可选：代码级结构性计数

这一节不是首次阶段 0 的必做项。只有在 DevTools 无法确认“哪些隐藏 Pane 参与了
build/layout”时才实施。

### 14.1 为什么不要先用 `print`

不要在 resize 高频路径加入：

```dart
print('build');
```

原因：

- 控制台 I/O 会显著扭曲性能；
- 每帧可能产生数千行；
- 项目规范也不允许保留 `print`；
- 很难按 entry id 和 frame 聚合。

### 14.2 推荐的测试专用诊断接口

可在 presentation 层增加可选接口：

```dart
abstract interface class AgentPaneBuildDiagnostics {
  void onResponsiveBodyBuilt(String entryId);
  void onTimelineItemBuilt(String itemId);
  void onTurnProjected(String turnId);
  void onDiffParsed(String itemId);
}
```

约束：

- `AgentPane` 默认传 `null`；
- 生产运行不记录内容；
- 测试使用内存 fake 累加计数；
- 不记录用户消息、文件路径或 raw payload；
- 不写磁盘；
- 不放进 application/domain。

### 14.3 测试思路

构造两个 AgentPane：

1. A 为活动页面；
2. B 为 IndexedStack 隐藏页面；
3. 改变父容器宽度 100 次；
4. 记录 A、B 的 responsive build 和 turn projection 次数。

阶段 0 只记录当前结果，不要提交“期待低效行为”的永久断言。例如不要写：

```dart
expect(hiddenPaneBuildCount, greaterThan(0));
```

这种断言会阻止后续优化。正确方式是：

- 当前计数写进阶段 0 记录；
- 在对应优化阶段把目标行为写成新测试；
- 优化后断言隐藏 Pane 次数为 0。

## 15. 常见问题排查

### 15.1 `flutter run` 很慢

第一次 Profile 编译慢属于构建时间，不是窗口 resize 性能。等待应用真正启动后再预热。

### 15.2 DevTools 连接不上

检查：

```powershell
flutter devices
```

确认 Windows device 存在。然后重新执行：

```powershell
flutter run -d windows --profile
```

使用本次终端新打印的 DevTools URL，不要复用旧 URL。

### 15.3 Performance 页没有 Flutter Frames

可能原因：

- 连接到 Chrome/Web；
- 使用 Release；
- 连接到错误进程；
- 应用已退出；
- DevTools 页面暂停。

### 15.4 拖动时没有生成很多 frame

检查：

- 是否拖到了真正的窗口最右侧外边框；
- 是否只在内部 Inspector 分隔条上拖动；
- Frames chart 是否暂停；
- Windows 是否启用了“拖动窗口时只显示边框”等特殊辅助设置。

本文目标是外部窗口 resize。内部右侧 Pane 拖拽属于另一条 `setState` 路径，应单独
录制，不能混在同一个 run 中。

### 15.5 Build Trace 太大，DevTools 卡住

- 将动作缩短到一次往返；
- 只打开 Builds；
- 关闭 Layouts 和 Paints；
- 清空旧 Timeline 后重试；
- 不把 trace run 当 clean baseline。

### 15.6 结果每次差别很大

检查：

- 电源模式是否变化；
- 笔记本是否进入温控降频；
- 是否有 Provider 流式输出；
- 是否每次窗口起始宽度不同；
- 是否有首次 Shader；
- 是否把 1 会话和 6 会话数据混在一起；
- DevTools 增强追踪是否忘记关闭。

若仍有明显波动，增加到 5 次 run，取中位结果。

### 15.7 UI 正常但 Raster 很慢

这与当前静态诊断不完全一致。应：

1. 补 Paint trace；
2. 分别关闭 DevTools More debugging options 中的 Clip、Opacity、
   Physical Shape 渲染层做短实验；
3. 每次只改变一个选项；
4. 不把关闭渲染层后的画面当最终解决方案；
5. 记录 Raster 是否显著下降。

Flutter 官方 Performance view 文档提供这些 Layer 开关用于诊断 Clip、Opacity 和
Physical Shape 成本。

## 17. 进入阶段 1 时如何使用这些数据

而应复测：

主要来自阶段 2–5。基线的价值就在于能区分每个阶段实际解决了哪一部分问题。
