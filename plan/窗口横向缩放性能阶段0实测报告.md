> 采集状态：已完成重载真实场景的 clean baseline、Build 诊断和 Layout 诊断
> 对应方案：`plan/窗口横向缩放性能优化改造方案.md`

## 1. 结论先行

本次已经在 Windows Profile 模式下稳定复现“拖动窗口最右侧边框时明显卡顿”，并获得
足以解释问题的运行时证据：

1. **主瓶颈在 UI 线程的 Layout，不在 Paint。**
   - Inspector 关闭代表轮：UI P95 为 `331.218ms`，Layout P95 为
     `316.070ms`；
   - Inspector 打开代表轮：UI P95 为 `390.760ms`，Layout P95 为
     `354.697ms`；
   - Paint P95 分别只有 `2.168ms` 和 `3.163ms`。
2. **不是只在某一个响应式断点出现一次尖峰。**
   连续宽度变化期间会重复出现 200–500ms 的 Layout 帧，窗口尺寸消息因此发生明显
   积压。
3. **保留式 `IndexedStack` 是明确的高成本路径。**
   Layout 诊断中 `RenderIndexedStack` 的 6 次匹配调用全部超过 16.67ms，平均
   `504.28ms`，P95/最大值为 `609.59ms`。
4. **长对话的 Markdown 和文本树在 resize 时发生大规模重新 build/layout。**
   约 1.32 秒的 Build 诊断窗口内，至少记录到：
   - `_AgentMessageEntry`：135 次 build；
   - `_AgentMarkdownMessage`：170 次 build；
   - `_AgentMarkdownBody`：195 次 build；
   - `MarkdownDocumentView`：121 次 build；
   - `MarkdownWidget`：117 次 build。
5. **少数超重 `RenderParagraph` 会把整帧拖到数百毫秒。**
   在截断后的 Layout 诊断窗口内，1007 次可配对的 `RenderParagraph` 中只有 4 次
   超过 16.67ms，但最慢一次达到 `450.41ms`。这说明普通文本布局很快，真正致命的是
   少量长 Markdown/富文本段落在新宽度下重新换行。
6. **Inspector 是放大器，不是根因。**
   同一精确宽度协议下，打开 Inspector 后 UI P95 增加约 `18.0%`，Layout P95
   增加约 `12.2%`，但 Inspector 关闭时已经存在 300ms 以上的 Layout P95。

因此，后续改造应优先处理：

1. 非活动 `AgentPane` 不参与持续 resize 的 layout；
2. 活动 timeline 只构建/布局可见范围；
3. Markdown 投影和文本布局不因顶层宽度变化而整树重算；
4. 最后再处理 Raster 和 `saveLayer` 等次要成本。

## 3. 场景与协议

### 3.1 本次真实场景

- 左侧 Projects 面板打开；
- 选择一个已完成、约 15.4m-token 的长会话；
- 采集前先打开过当前活动会话，再切换到已完成会话，因此运行时至少保留两个
  Agent workspace entry；
- 分别采集 Files Inspector 关闭和打开；
- 当前另一个 retained entry 仍有运行状态动画，因此本次是“真实重载场景”，不是完全
  静止的单会话 S1。

### 3.2 Clean baseline 输入协议

- 起始窗口：约 1280×800 逻辑像素；
- 结束宽度：约 1000 逻辑像素；
- 每次变化：4 逻辑像素；
- 投递间隔：约 28ms；
- 单程目标时长：约 2.2 秒；
- 每轮：收缩一次、恢复一次；
- 使用 Win32 异步尺寸投递，避免采集脚本自身被 UI 线程同步阻塞；
- 每个单程结束后轮询真实窗口宽度，只有确实到达目标端点才开始反向动作；
- 三轮宽度序列分别平移 0、1、2 像素，避免完全相同宽度序列命中段落/栅格缓存。

### 3.3 指标计算

- UI 帧：配对 `Animator::BeginFrame` 的 `B/E` 事件；
- Layout：配对 `LAYOUT` 的 `B/E` 事件；
- Paint：配对 `PAINT` 的 `B/E` 事件；
- Raster：配对 `Rasterizer::DoDraw` 的 `B/E` 事件；
- 配对键：事件名称和线程 id；
- 时间单位：VM Timeline 微秒换算为毫秒；
- P95：nearest-rank，索引为 `ceil(N × 0.95) - 1`；
- 慢帧阈值：`16.67ms`。

## 7. Layout 诊断

Layout 诊断只打开 `profileRenderObjectLayouts`，使用 8 个此前未回放的离散宽度。
每次尺寸投递后到达目标宽度的等待时间如下：

```text

```

诊断 trace 同样到达 Timeline 环形缓冲区上限。下表仅统计能成功匹配 `B/E` 的事件。
时长是**包含子树的 inclusive time**，不同 RenderObject 之间不能相加。

| RenderObject | 配对次数 | 平均 | P95 | 最大 | >16.67ms |
|---|---:|---:|---:|---:|---:|
| `RenderIndexedStack` | 6 | 504.28ms | 609.59ms | 609.59ms | 6 |
| `_RenderSnapshotWidget` | 12 | 508.42ms | 613.82ms | 613.82ms | 12 |
| `_RenderLayoutBuilder` | 570 | 13.29ms | 34.25ms | 641.19ms | 81 |
| `RenderFlex` | 1349 | 12.53ms | 30.70ms | 641.20ms | 98 |
| `RenderParagraph` | 1007 | 1.26ms | 0.76ms | 450.41ms | 4 |
| `_RenderScaledInlineWidget` | 349 | 0.02ms | 0.09ms | 0.96ms | 0 |
| `_RenderDecoratedInlineText` | 349 | <0.01ms | 0.01ms | 0.08ms | 0 |

关键解释：

- `RenderIndexedStack` 每次都很慢，说明成本不是单一可见段落，而是整个 retained
  subtree 的尺寸重新计算；
- `RenderParagraph` 的 P95 很低但 Max 极高，说明只有少量长段落决定最坏帧；
- `_RenderLayoutBuilder` 和 `RenderFlex` 的大量调用说明约束变化向下传播得很深；
- inline 装饰自身不是主要成本，真正昂贵的是段落换行和包含这些段落的 retained
  layout 子树。

## 8. 与当前代码的对应关系

运行时热点与代码结构可以直接对应：

1. `IdeHome._buildRetainedCanvasStack()` 返回外层 `IndexedStack`，同时保留 Home、
   Settings 和 Usage Statistics 页面。
2. `IdeHome._buildRetainedAgentPaneStack()` 返回第二层 `IndexedStack`：
   - children 包含 Project Home；
   - 对每个 `agentWorkspaceEntries` 都创建一个 `AgentPane`；
   - 仅通过 `index` 控制显示项。
3. `IndexedStack` 为确定自身尺寸仍会布局保留的非活动 child，因此窗口宽度变化会把
   约束传播到多个 retained `AgentPane`。
4. Build trace 中大量 `_AgentMessageEntry`、`_AgentMarkdownBody` 和
   `MarkdownDocumentView` 与长 timeline 的宽度重排完全吻合。

相关代码：

- `lib/src/ui/features/ide/views/ide_home.dart`
  - `_buildRetainedCanvasStack`
  - `_buildRetainedAgentPaneStack`
- `lib/src/features/agent/presentation/agent_conversation.dart`
- `lib/src/features/agent/presentation/agent_timeline.dart`
- `lib/src/features/agent/presentation/widgets/agent_timeline_markdown.dart`

诊断 trace 只有 RenderObject 类型名，无法区分两个 `RenderIndexedStack` 各自占多少。
若后续需要定量拆分，可在测试/诊断构建中为两个 stack 增加独立 timing hook，但不应在
生产 resize 热路径中加入 `print`。

## 9. 无效样本与排除规则

本次主动排除了以下样本：

1. **DPI 单位错误样本**：最初用 1280/1000 物理像素操作 200% DPI 窗口，宽度被
   Windows 最小尺寸钳制，实际没有 resize。
2. **未验证端点样本**：异步投递结束后立即反向，窗口只收缩到约 1206–1232px，
   未到目标 1000px。
3. **窗口最小化样本**：`GetWindowRect` 返回 `-32000` 附近的 iconic 坐标，
   不能用于性能比较。
4. **环形缓冲区溢出样本**：事件数接近 32768 且 `timeExtentMicros` 只保留后半段。
   这类样本只用于发现热点名称，不用于 clean P95。
5. **Inspector-on Run 3**：端点有效，但投递耗时和 Raster 2 秒尖峰明显受外部调度
   干扰，不选作代表轮。

这些排除项同时说明后续自动化必须记录“实际窗口宽度”，不能只记录脚本请求宽度。

## 11. 对改造阶段的影响

### 阶段 1：可以继续，但不要高估收益

断点切换中的 key/slot identity 仍应修正，以消除一次性 subtree 替换；但实测慢帧
在持续 resize 中反复出现，阶段 1 不可能单独把 300ms Layout P95 降到目标范围。

### 阶段 2：应提升为最高优先级

必须改变 retained session 的布局策略，使非活动 `AgentPane`：

- 保留必要 State、草稿、滚动位置和任务状态；
- 不参与每个窗口宽度的 layout；
- 不因为另一个 session 的动画或状态变化而重建。

验收时至少增加：

- 非活动 AgentPane layout 计数为 0；
- 切回后 State/草稿/滚动位置不丢失；
- 6-session 与 1-session 的 resize P95 差距受控。

### 阶段 3：timeline 虚拟化同样是主路径

Build 诊断已经证明大量 `_AgentMessageEntry` 和 Markdown Widget 被卷入。需要确保：

- timeline 只构建/布局可见窗口及有限 cacheExtent；
- 展开态和稳定 key 不丢失；
- 长 Markdown 投影缓存不以窗口宽度为无界 key；
- 文字换行仅对可见段落发生。

### Raster 优化延后

Raster P95 已有 19–26ms 的次要压力，但 Paint P95 很低。应先消除 UI/Layout
300ms 级尖峰，再补 Paint trace 判断 `saveLayer`、Clip、Opacity 或阴影成本；否则
Raster 优化会被主线程瓶颈淹没。

## 12. 下一次复测要求

1. 当前任务完全结束，确保没有 Provider streaming。
2. 使用明确的 1-session 和 6-session fixture。
3. 保持 200% DPI、1280×800、相同 Profile 命令。
4. 使用 0/1/2 像素平移的三组宽度，避免宽度缓存产生假性改善。
5. 每个单程必须验证实际端点。
6. Clean run 仍保持全部增强追踪为 `false`。
7. 对比以下核心指标：
   - UI P95；
   - Layout P95；
   - >16.67ms 帧占比；
   - 收缩/恢复端点积压；
   - 非活动 AgentPane layout 次数；
   - `_AgentMessageEntry` / Markdown build 次数。

建议阶段 2/3 完成后的最低目标：

- 1280→1000→1280 期间 UI P95 < 16.67ms；
- 最慢 UI 帧 < 33.33ms；
- 端点积压 < 100ms；
- 非活动 AgentPane 不参与 layout；
- Inspector 打开相对关闭的 UI P95 增幅 < 20%。
